# ADR-011：串口协议集中化（每模块协议定义沉淀到 drivers 层）

## Background

`ATS/modules/*.py` 各模块的**原始串口命令**与**成功/失败判据字符串**大量内联在业务逻辑里：`exec_sync("mkfs -t elm sd")`、`exec_async("dfs_capture_start", expect=r"Capture completed successfully.")`、`exec_async("ftp_server", expect=r"service launched success")` 等散落在各模块 `run()` 中。

这些字符串本质是**与 EVB 固件之间的协议**，而非业务逻辑。固件日志格式已变过一次（`[RTMP] f_index` → `I/App Rtmp: f_index`），当时的修法是散点改正则，易漏且难审计。用户实测反馈：调整命令/判据需直接在业务代码里找字符串改，风险高、易遗漏。

`video` 模块已于 commit `d7cee21` 率先完成集中化：新增 `ATS/drivers/video_commands.py`，把 11 种 size 组合命令、启动/停止命令、启动/停止/清理判据、错误正则、超时值全部集中，`video.py` 只剩 `commands.VIDEO_STOP_EXPECT` 这类引用。这是本 ADR 的既定参照。

## Problem

1. 协议字符串与业务逻辑耦合，改一处判据要在业务代码里翻找，容易漏改、改错。
2. 各模块集中程度不一致（video 已集中，photo/rtmp/ftp/wifi/emmc 散落），风格割裂。
3. 同一协议字符串在模块内多处重复（如 photo 的 `Capture completed successfully.` 在 expect 与注释里各出现一次），无单一来源。

## Decision

1. **协议定义位置**：每模块新增 `ATS/drivers/<module>_commands.py`（drivers 层，与 `video_commands.py`、`rtmp_receiver.py`、`ftp_client.py` 同级），作为该模块串口协议（命令 + 判据 + 超时 + 错误正则）的**唯一来源**。业务代码只 import 引用，不再内联协议字符串。

2. **命名规范**（对齐 `video_commands.py` 现状）：
   - 命令：`<ACTION>_COMMAND`（如 `FTP_START_COMMAND = "ftp_server"`）
   - 判据：`<ACTION>_EXPECT`（如 `PHOTO_CAPTURE_EXPECT = r"Capture completed successfully."`）
   - 错误正则：`<ACTION>_ERROR`（如 `VIDEO_SET_ERROR`）
   - 超时：`<ACTION>_TIMEOUT`
   - 路径常量：`_XXX_DIR`（如 `_PIC_DIR = "/emmc/PIC"`）
   - 枚举/映射：用 `MappingProxyType` 不可变映射（如 `VIDEO_PROFILES`、`PHOTO_MODES`）

3. **覆盖范围**（本次除 video 已完成为外，其余全部迁移）：

   | 模块 | 迁移到 | 需集中的协议 |
   |------|--------|-------------|
   | video | `video_commands.py`（已完成，不重复） | — |
   | photo | `photo_commands.py` | `cam_set photo {mode}`、`dfs_capture_start`、`Capture completed successfully.`、`/emmc/PIC`、photo_modes 枚举、超时 |
   | rtmp | `rtmp_commands.py` | `rtmp_video_start {url}`、`rtmp_video_stop`、`publish ready\|Push Start`、`Push Stop\|Stop requested`、heartbeat 正则（迁移自 rtmp_monitor 的 `_HEARTBEAT_RE`）、超时 |
   | ftp | `ftp_commands.py` | `ftp_server`、`service launched success`、`service go wrong`、`/emmc` 验证路径、超时 |
   | wifi | `wifi_commands.py` | `ifconfig`、`wifi scan`、`wifi join {ssid} {pwd}`、`_SCAN_HEADER_RE`/`_SCAN_ROW_RE`/`_GOT_IP_RE`/`_IFCONFIG_IP_RE` 正则、超时 |
   | emmc | `emmc_commands.py` | `mkfs -t elm sd`、`mount sd /emmc elm`、`cd /emmc`、超时 |

4. **边界**：
   - `drivers/<module>_commands.py` **只存协议常量**（命令/判据/超时/正则/路径/枚举），**不写 IO、不写编排、不 import console/ftp/ctx**（对齐 `video_commands.py` 的 docstring 承诺：不发送串口、不连接 FTP、不读 YAML、不安排次数时长）。
   - 判据逻辑（如 ffprobe 的 codec/分辨率判据、H265 三阶段诊断）**不迁**——那些是 driver 的计算逻辑，不是字符串协议，保持在 `rtmp_receiver.py`/`h265_validator.py`。
   - 协议字符串**不进 yaml**（见 Alternative）：yaml 是运行时可配置的参数（时长、开关、SSID、IP），协议是固件契约，属代码，放 yaml 反而散失单一来源且无法类型化。

5. **渐进迁移**：本次一次性落地 photo/rtmp/ftp/wifi/emmc 五个模块，但**不改任何判据值/命令值**——纯搬移（moved, not changed）。搬移过程中若发现某字符串可疑，只加 `TODO-CONFIRM` 注释，不在本 ADR 范围内改动协议语义。

## Alternative

- **放 yaml 配置**：协议作为可配置项。否决——协议是固件契约，需代码类型化 + 单一来源 + 版本控制与代码同源；yaml 放协议会让「改判据」与「改运行参数」混在同一层，且丢失 `MappingProxyType` 不可变性、正则预编译等收益。运行参数（时长/开关/SSID）与协议（命令/判据）必须分层。
- **每个模块内顶部集中（不新建 drivers 文件）**：如 wifi.py 现有 `_SCAN_HEADER_RE` 在文件顶部。否决——模块文件仍承担「协议 + 业务」两个职责，跨模块不统一，且 `video_commands.py` 已确立「drivers 层 = 协议唯一来源」范式。
- **维持现状**：改动成本低，但每次固件字符串调整都是散点修改，易漏、难审计，且与已完成的 video 模块风格不一致。

## Impact

- 新增：`ATS/drivers/photo_commands.py`、`rtmp_commands.py`、`ftp_commands.py`、`wifi_commands.py`、`emmc_commands.py`（5 个文件）。
- 修改：`ATS/modules/photo.py`、`rtmp.py`、`ftp.py`、`wifi.py`、`emmc.py`（改内联为 import 引用）；`rtmp_monitor.py`（`_HEARTBEAT_RE` 迁移至 rtmp_commands，若选择集中）。
- 行为不变：纯搬移，命令/判据值逐字一致，不影响真机判据与结果。
- 后续新增/调整协议：只改对应 `drivers/<module>_commands.py` 一处。
- 文档：本 ADR 登记到 `02_design/decision_record/README.md` 索引；实施后由 Code Agent 写 devlog。
