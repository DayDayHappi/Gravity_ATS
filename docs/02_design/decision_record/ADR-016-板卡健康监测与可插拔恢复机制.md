# ADR-016：板卡健康监测与可插拔恢复机制

## Background

ADR-015 已交付串口上下电控制能力（`PowerSwitch`，`ATS/drivers/power_switch.py` + `ATS/drivers/power_commands.py`），但该能力职责边界明确：只提供 `power_on()` / `power_off()` / `reboot()`，只回答「如何给板子上下电」，**不感知**板子是否死机、什么时候需要重启、重启后测试如何继续。

`system.yaml` 中已有 `power_switch.enabled` 开关，`enabled=false` 时不探测、不打开控制器串口，对原测试链路零影响。该增量语义必须继续保持。

## Problem

需要新增一个 **Scenario 生命周期级 EVB 健康监测与恢复机制**，用于 stress / aging 等长时间运行场景中识别 EVB 运行期失去响应，并在策略允许时执行恢复。

目标不是简单实现「检测不到板子就 `PowerSwitch.reboot()`」，而是建立完整链路：**检测 → 确认 → 恢复决策 → 恢复执行 → 环境重新收敛 → 测试流程恢复或终止**。

## Decision

### 1. Detection / Decision / Execution 三层分离

| 组件 | 职责 | 不负责 |
|------|------|--------|
| `BoardHealthMonitor` | 只判断 EVB 是否健康，输出 `HealthEvent` | 不调用 PowerSwitch、不决定是否重启、不决定 Task 重跑、不恢复 WiFi/FTP、不改 Scenario |
| `RecoveryCoordinator` | 消费健康状态，决定异常后怎么办，协调恢复流程 | 不负责健康判据本身、不负责上下电二进制协议、不负责 photo/video/rtmp 业务逻辑 |
| `RecoveryBackend` | 把统一恢复请求适配到具体恢复能力 | 不决定何时恢复 |
| `PowerSwitch` | 只执行上下电 | 不关心触发原因和测试策略 |

推荐关系：`BoardHealthMonitor → HealthEvent → RecoveryCoordinator → RecoveryBackend → PowerCycleBackend → PowerSwitch`。

最终目标：Monitor 只监测；Coordinator 只协调；Backend 只适配恢复能力；PowerSwitch 只上下电。Monitor 不认识 PowerSwitch，Module 不认识 Recovery，PowerSwitch 不认识 Monitor，Runner 不认识具体硬件。

### 2. BoardHealthMonitor

- **负责**：监听 EVB 串口活动、记录最后有效 RX 时间、检测长时间无活动、维护 `HEALTHY / SUSPECTED / UNRESPONSIVE` 状态、保存证据、请求进一步健康确认。
- **状态机**：`HEALTHY →（超过 inactivity_timeout）→ SUSPECTED →（主动健康确认连续失败）→ UNRESPONSIVE`。
- 「无串口输出」**不能直接等价于**「整板死机」：`UNRESPONSIVE` 只表示 ATS 无法通过当前 EVB 控制链路取得有效响应，不推断根因。

### 3. Monitor 禁止直接调用 PowerSwitch 的原因

1. **职责耦合**：Monitor 同时承担检测、恢复策略、硬件选择和执行，未来替换 USB Relay / Network PDU / Soft Reset 时会不断膨胀。
2. **reader thread 阻塞**：当前 `SerialConsole` listener 在 reader thread 中同步回调（RTMPMonitor / StringHitMonitor 都保持极轻量）。若 callback 中执行 `PowerSwitch.reboot()`（含下电、sleep、上电阻塞动作），可能阻塞 EVB 串口 reader thread，反而放大「无响应」现象。

**红线**：Monitor listener 中禁止 sleep、exec_sync、exec_async、PowerSwitch、FTP、网络 IO 和其他阻塞操作。

### 4. RecoveryCoordinator

- 推荐位置：`ATS/application/recovery_coordinator.py`。
- **负责**：接收 BoardHealthMonitor 状态、防重复恢复、统计恢复次数、根据 Scenario Recovery Policy 选择 RecoveryBackend、暂停/恢复监测、失效板端运行状态、执行恢复、等待 EVB ready、恢复环境、通知 Runner 恢复结果、决定 retry 或 abort。
- **状态机**：`IDLE → REQUESTED → RECOVERING → RECONCILING → HEALTHY`；恢复失败进入 `FAILED`。
- 必须有 `recovery_in_progress` 或等效互斥，同一时间只允许一个恢复流程，防止多个 health event 并发触发多次 reboot。

### 5. RecoveryBackend 抽象

- 统一恢复能力接口：`name`、`available(ctx)`、`recover(ctx)`。
- 第一阶段只实现 `PowerCycleBackend`；未来可扩展 `SoftResetBackend`、`NetworkPduBackend`、`UsbRelayBackend`、`ManualRecoveryBackend` 等。
- Coordinator 只调用 `backend.recover()`，更换电源机制无需修改 Monitor、Runner 或业务模块。
- `PowerCycleBackend`（`ATS/application/recovery_backends/power_cycle.py`）：仅把统一 `recover()` 请求映射成 `ctx.power_switch.reboot()`。PowerSwitch 本身保持 ADR-015 原职责不变。

### 6. 配置职责边界

| 配置 | 放什么 | 禁止 |
|------|--------|------|
| `system.yaml` | 只描述「当前机器有什么硬件能力」：`power_switch.enabled`、`baudrate`、`reboot_delay` | 禁止放「死机后是否重启、最大恢复次数、当前 Task 是否 retry」等策略 |
| `config/modules/board_health.yaml` | Monitor 参数（Scenario 生命周期级能力参数，沿用 PreviewManager 模式）：`check_interval`、`inactivity_timeout`、`confirm_failures`、`confirm_interval` | — |
| `config/scenarios/*.yaml` | Recovery Policy（测试策略）：`health_monitor.enabled`、`recovery.enabled`、`recovery.backend`、`recovery.max_attempts`、`recovery.after_recovery`、`recovery.on_exhausted`、`recovery.restore` | — |

- `after_recovery` 第一阶段建议 `retry_current_task`；`on_exhausted` 建议 `abort_scenario`。
- `inactivity_timeout` 等默认值必须通过真实 stress 日志校准，不应凭经验拍死。
- **禁止静默 fallback**：若 `recovery.enabled=true` 且 `backend=power_cycle`，但 `power_switch.enabled=false` 或探测失败，应在正式 tasks 前明确报 `RecoveryBackendUnavailable`，不得偷偷改成 soft reset，也不得静默关闭 recovery。自动化行为必须确定、可审计。

### 7. 生命周期

- BoardHealthMonitor 属 Scenario 生命周期能力，不是 Task。复用 prepare/cleanup 注册表新增 `health_monitor_start` / `health_monitor_stop`。
- 推荐 prepare 顺序：`serial_init → power_switch_init → wifi_connect → preclean → ftp_ready → preview_start → health_monitor_start`。
- 推荐 cleanup 首先执行 `health_monitor_stop`，然后 `stop_stream → preview_stop → power_switch_close → close_serial`，防止正常清理被误判为死机。

### 8. 健康确认机制

- `last_rx` 超时只进入 `SUSPECTED`。真正的主动健康确认在安全点复用 `console.health_check()`：`echo EVBTEST_HELLO → 收到有效响应`。
- probe 成功 → Monitor 回到 `HEALTHY`；连续 probe 失败达到 `confirm_failures` → 进入 `UNRESPONSIVE`。
- **主动 probe 必须在安全点执行**：当前 `SerialConsole` 的底层 write lock 只保护单次写，不提供完整 `exec_sync/exec_async` 命令事务的全局排他。若后台 Monitor 同时 `exec_sync` 而业务模块正在 `exec_async`，可能发生命令和响应交叉。因此 Monitor 线程只观察；主动 probe 由 Runner 控制流在不存在其他命令事务时执行。

### 9. Runner 接入方式

- Runner 仍负责「什么时候执行」。新增 recovery checkpoint 属调度职责。
- 流程：Task 完成 → Runner checkpoint → 若 `HEALTHY` 则继续；若 `SUSPECTED` 则在安全点执行 active probe；probe 成功继续，失败达阈值后交给 RecoveryCoordinator。
- Runner 不认识 PowerSwitch、115200 波特率或控制帧，只认识 coordinator 的统一接口。

### 10. Context 状态失效与恢复收敛

- Power Cycle 后，与板端运行实例绑定的 ctx 状态必须视为失效：`ctx.evb_ip`、`ctx.wifi_ready`、`ctx.skip_wifi`、`ctx.ftp_client`、`ctx.ftp_server_started` 等。
- **不能直接调用 `ctx.cleanup()`**（会清空 `system_config`、`console`、`power_switch`、`recovery_coordinator` 等仍有效对象）。应新增局部状态失效机制（如 `invalidate_board_runtime_state()`），只清理板端 reboot 后失效的状态。
- **Power Cycle 后仍有效**：`ctx.system_config`、`ctx.power_switch`、`ctx.recovery_coordinator`、`ctx.board_health_monitor`；`ctx.pc_ip` 通常仍保持；PreviewManager 属 PC 侧 Scenario 生命周期能力且已有断流重连 wrapper，原则上无需因 EVB reboot 销毁。
- 恢复后环境重新收敛完整流程：`PowerCycle → 等 EVB ready → Serial health check → WiFi 状态重新收敛 → preclean → FTP 服务重新建立 → 恢复任务执行`。RecoveryCoordinator 应**复用现有 prepare action**，避免复制第二套 Recovery WiFi / Recovery FTP 逻辑。
- 新增轻量 `board_ready` action：`console.wait_for_ready() → console.health_check()`；第一阶段不重新执行完整 `serial_init`（控制串口预计保持打开）。若真机发现 Power Cycle 导致 USB 串口重新枚举，再独立扩展 `serial_reconnect`，不提前假设。
- `recovery.restore` 由 Scenario 声明（如 normal/stress：`board_ready、wifi_connect、preclean、ftp_ready`；no_network 只需 `board_ready、preclean`）。Coordinator 只按策略调用已有 Action，不知道场景是否需要 WiFi/FTP，保持低耦合。

### 11. Recovery Event 独立留痕

- 建议新增 `ctx.recovery_history`，每条记录含：timestamp、scenario、cycle、task、rep、health_state、reason、backend、attempt、recovery_result、restore_result。
- Reporter 可增量增加 `recovery_events`，不改变现有 results 结构；HTML 增加 Recovery Events 区域。
- **恢复事件不能被 PASS 覆盖**：即使 retry 后 PASS，也必须保留原 Hang 事件。
- 日志职责：`serial.log`=EVB 原始串口；`power_switch.log`=电源控制器原始 TX/RX；`recovery.log`=恢复控制流；`run.log`=整体运行轨迹。Monitor/Coordinator 禁止把分析信息写入 serial.log。

### 12. 推荐新增文件

```
ATS/application/board_health_monitor.py
ATS/application/recovery_coordinator.py
ATS/application/recovery_backends/__init__.py
ATS/application/recovery_backends/base.py
ATS/application/recovery_backends/power_cycle.py
ATS/config/modules/board_health.yaml
```

Phase 2 可加入 `ATS/application/runtime_control.py`。第一阶段**不**创建 `modules/board_health.py`（它不是 Scenario Task）。

### 13. 长时间 Task 的 Cooperative Control

现有 video 存在 `time.sleep(duration)` 等长等待，纯 Task 边界检查会导致恢复延迟。Phase 1 先只做 Task/repeat/cycle 边界安全检查，控制风险；Phase 2 再引入 RuntimeControl（如 `runtime.wait(duration)`，内部按小周期 sleep + 检查全局 recovery request，实现 cooperative cancellation）。业务模块仍不能直接执行 recovery。

### 14. RTMPMonitor 与 BoardHealthMonitor 的关系

- RTMPMonitor **不被替代**：RTMPMonitor 判断 RTMP 业务 heartbeat 是否正常；BoardHealthMonitor 判断 EVB 整板控制链路是否可响应。
- RTMP heartbeat timeout 但 shell `health_check` PASS 时，应只判 RTMP FAIL，**禁止 PowerCycle**。业务故障不能自动升级为整板故障。

### 15. 分阶段实施

- **Phase 0**：文档与契约冻结，不改代码。
- **Phase 1**：Monitor Only，只实现 HEALTHY/SUSPECTED/UNRESPONSIVE，不接 PowerSwitch。
- **Phase 2**：RecoveryCoordinator + RecoveryBackend + PowerCycleBackend，打通 UNRESPONSIVE→power cycle→board_ready。
- **Phase 3**：Context invalidation + wifi_connect/preclean/ftp_ready 环境重新收敛。
- **Phase 4**：Runner Recovery Policy，支持 max_attempts、retry_current_task、abort_scenario、recovery history。
- **Phase 5**：长时间 Task Cooperative Control，引入 RuntimeControl。

## Alternative

### 可选能力组合与优雅退化

| 组合 | 语义 |
|------|------|
| monitor=false, recovery=false, power_switch=false | 完全保持当前行为 |
| monitor=true, recovery=false, power_switch=false | 只检测并记录，不自动恢复 |
| monitor=true, recovery=true, power_switch=true, backend=power_cycle | 自动 power cycle |
| 未来不用串口控制器时新增其它 Backend | HealthMonitor/RecoveryCoordinator/Runner/业务模块无需推翻 |

HealthMonitor 可以长期存在，但 PowerSwitch 可以不存在。

### 禁止的设计

- 禁止 `BoardHealthMonitor → PowerSwitch`
- 禁止 `photo/video/rtmp → PowerSwitch`
- 禁止 `PowerSwitch → BoardHealthMonitor`
- 禁止 Monitor listener 内执行串口命令/sleep/reboot/FTP
- 禁止仅凭串口静默直接判整板死机
- 禁止 backend 不可用时静默 fallback
- 禁止 PowerCycle 后继续信任 `ftp_server_started`/`ftp_client`/`wifi_ready`
- 禁止 recovery 成功后删除原 Hang 记录
- 禁止 photo/video/rtmp 等模块直接 `ctx.power_switch.reboot()`

## Impact

- **不破坏当前架构**：现有 Config → ScenarioManager → Runner → Module → Driver 仍保持。新增 Application Service 只承担跨模块系统级协调。
- **职责保持**：Scenario=测试怎么组合及异常恢复策略；Runner=什么时候执行及什么时候进入恢复；Module=怎么测；Driver=怎么和硬件交互；Application Service=跨模块协调系统级行为。
- **预计修改**：`core/scenario.py`、`core/scenario_manager.py`、`core/runner.py`、`core/reporter.py`、`application/*`、`config/modules/board_health.yaml`、启用该能力的 scenario yaml。
- **原则上不修改**：photo/video/rtmp/emmc/ftp/utest 业务模块；`power_commands.py` 不改；`power_switch.py` 第一阶段也尽量保持现状。
- **向后兼容红线**：所有现有 Scenario 若没有 health_monitor/recovery 配置，默认 disabled，旧 YAML 可保持当前行为。`power_switch.enabled=false` 继续保证不探测、不打开、不产生 `power_switch.log`、不影响原测试。所有新增能力默认关闭。
- **第一阶段 Scope**：只处理 Scenario 已成功启动后的运行期故障，**不解决**「ATS 启动时 EVB 已死」（当前 normal/stress 先 serial_init 再 power_switch_init，脚本启动前 EVB 已完全死机时 serial_init 无法识别板子，PowerSwitch 尚未初始化）。启动前 recovery 涉及 EVB 未识别时如何可靠区分 PowerSwitch 端口，应单独做后续 ADR。

## Acceptance Criteria

- **TC-BH-001** Monitor 关闭回归：monitor/recovery/power_switch 全关闭时行为与当前版本一致。
- **TC-BH-002** 仅 Monitor：人为 EVB 无响应，HEALTHY→SUSPECTED→主动 probe→UNRESPONSIVE；不得出现 PowerSwitch TX。
- **TC-BH-003** 正常静默不误判：可进入 SUSPECTED，但 probe 成功后恢复 HEALTHY，不能重启。
- **TC-RCV-001** PowerCycle 恢复：UNRESPONSIVE→recovery→power_switch.log 有上下电帧→EVB boot→board_ready PASS→环境收敛。
- **TC-RCV-002** PowerSwitch 不存在：backend=power_cycle 但能力关闭时，tasks 前明确 BackendUnavailable，不静默降级。
- **TC-RCV-003** RTMP 单模块故障：heartbeat timeout 但 shell health_check PASS，只判 RTMP FAIL，禁止 PowerCycle。
- **TC-RCV-004** 连续 Hang 超上限：max_attempts=2，第三次 abort_scenario，禁止无限重启。
- **TC-RCV-005** Context 失效：PowerCycle 后 ftp_server_started=false、ftp_client=None、wifi_ready=false、skip_wifi=false，之后 restore 正确重建。

**修复顺序**（验收报告 §10）：统一 `continue` 语义 → PowerCycle 严格回帧 → dry-run 契约校验 → 源码快照纳入 tests → 真机（先验 HW-RISK-01 再跑 TC-BH/TC-RCV）。验收报告建议完成后停止扩功能，直接进真机。

**架构红线不变**：Runner 负责 `RecoveryOutcome → retry/continue/abort/framework TestResult`，不认识具体硬件；`RecoveryCoordinator` 只返回 Outcome 不生成 TestResult；`PowerSwitch` 只负责上下电（可新增 `reboot_checked()`，不感知 health/Scenario/policy）；`ScenarioManager` 负责生命周期静态契约校验，但不偷偷自动补 action；`serial_reconnect`（如需）不进 PowerSwitch。

**能力边界（不变）**：当前只能识别「串口静默型整板无响应」，不能覆盖「串口仍刷日志但控制链路已死」的故障。
