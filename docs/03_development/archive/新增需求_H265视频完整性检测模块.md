## 0. 评审结论（先读这里）

本设计与现有工程**无架构冲突**，完全落在既有 `Scenario/Runner/Module/Config/Driver` 边界内，按「模块扩展机制」实现即可：

```text
Scenario = 怎么组合测试   → 新增 task `- module: video_integrity`
Runner   = 什么时候执行   → 原样调度，不感知 H265
Module   = 怎么测         → 新增 video_integrity（选择文件 + 聚合结果）
Config   = 参数是什么     → 新增 config/modules/video_integrity.yaml
Driver   = PC 端底层能力  → 新增 h265_validator（FFmpeg 诊断）
```

**唯一必须处理的冲突**：当前 `base.TestModule._merge()` 是**顶层浅合并**，嵌套 `override.input.*` 会整体替换 `input` 子 dict。解决方式见 §7，**不得改 core**。

**不需要新 ADR**：本需求不改变任何既有模块职责/边界/数据流/生命周期/系统边界，仅按 `@register` 扩展机制新增能力。

## 1. 目标

在 Ubuntu PC 上对已下载的 `.h265/.hevc` 本地文件做 **HEVC 码流完整性检测**，识别：

- HEVC 解码异常；
- 参考帧缺失（`Could not find ref with POC <N>`）；
- RPS 构造异常；
- NAL 解析异常；
- POC discontinuity；
- 固定 GOP 下的 missing picture；
- 失败位置的大致时间定位（约 `xx.xxs`）。

**两种使用方式**：

1. 嵌入 `normal` / `stress` 等现有场景：`video` 录完并下载后，下一 task 执行检测；**不修改 VideoModule 的录像职责**。
2. 独立场景：不连板子 / 不探串口 / 不连 WiFi / 不启动 FTP / 不连 nginx，只扫本地目录做检测。

- **不得**在 Runner 硬编码「video 后自动检测」；**不得**在 ScenarioManager 硬编码视频检测。
- **不得**新增调度机制 / 架构层；**不得**改 `SerialConsole` / 污染 `serial.log`。

- **不得**把「是否检测」开关放进 core；**不得**新增 `enabled=true/false` 第二套启用机制。
- 是否检测**只由** `scenario.tasks` 里有没有 `- module: video_integrity` 决定；没有该 task → 完全不执行。

> 若实施中发现必须改 core（如 deep-merge 必须放进 `base.py`、需要 `ctx.latest_video` 等）→ 这是 Level 2/3 架构影响，**STOP**，按 `code-agent.md` 产出 `Document Agent Request`，不要自己改。

## 3. 组件与职责

```text
ATS/
├── modules/video_integrity.py      # 模块：选择文件 + 聚合结果 + 出 TestResult
├── drivers/h265_validator.py       # Driver：FFmpeg 子进程 + 三阶段诊断 + 结构化结果
├── config/modules/video_integrity.yaml
├── config/scenarios/video_integrity.yaml
└── modules/__init__.py             # 追加一行 import 触发 @register
```

### `modules/video_integrity.py`（模块）

- 读模块配置（含 deep-merge，见 §7）；
- 选择本次待检测视频（§6）；
- 逐个调用 `H265Validator`，聚合结果（§11）；
- 输出 aggregate `TestResult`；
- 打运行日志（写 `run.log`，**绝不写 `serial.log`**）。
- **不得**自己实现大量 FFmpeg 日志解析（交给 driver）。

### `drivers/h265_validator.py`（Driver）

- FFmpeg 可执行文件检查；
- FFmpeg 子进程管理（argv list、无 shell、timeout + kill）；
- Stage1 全文件 decode、Stage2 showinfo 定位、Stage3 trace_headers 分析；
- HEVC 错误解析、POC/GOP 分析；
- 返回结构化 `H265ValidationResult`。
- **不得**感知 Scenario / normal / stress / Runner / FTP / 串口；**不得**直接生成 `TestResult`。

## 4. 与 VideoModule 的解耦契约（关键）

二者通过**本地文件目录约定**解耦，而非代码互相调用。

已核实的事实：

- `video.py` 下载到：`os.path.join(logger.log_dir() or "logs", "videos")`，文件名为 `Video_<n>_0.h265`。
- `logger.log_dir()` 返回本次 run 的 `<log_root>/<run_ts>/`（含 run_ts），整个 run 内稳定。

因此模块定位「当前 run 产生的视频」：

```text
logger.log_dir() + current_run_subdir("videos")  →  <log_dir>/videos/
```

即 `input.source: current_run` + `current_run_subdir: "videos"` 扫描该目录下的 `*.h265`。

**禁止**为传文件路径新增 `ctx.latest_video` / `ctx.video_result` 等 Context contract（当前 `context.py` 无此键，不要加）。

## 5. 模块配置设计

新建 `ATS/config/modules/video_integrity.yaml`（建议结构，Code Agent 可按需微调但保持字段语义）：

```yaml
# H.265 本地视频完整性检测模块

ffmpeg_path: "tools/ffmpeg/ffmpeg"

input:
  source: "current_run"          # current_run | directory
  current_run_subdir: "videos"   # current_run 时相对 logger.log_dir() 的子目录
  directory: ""                  # directory 时扫描的绝对目录
  patterns:
    - "*.h265"
    - "*.hevc"
  selection: "latest_unchecked"  # all | latest | latest_unchecked | explicit
  explicit_files: []             # selection=explicit 时使用
  recursive: false               # 是否递归扫描子目录
  empty_input_policy: "fail"     # fail | skip

analysis:
  decode_check: true
  locate_on_error: true
  trace_headers_on_error: true
  decode_timeout: 900
  showinfo_timeout: 900
  trace_timeout: 900

hevc:
  expected_fps: 30
  expected_gop_size: 30
  poc_policy: "fixed_gop"        # 当前产品固定 GOP；非固定 GOP 时退化为 REFERENCE_CHAIN_ERROR

diagnostic:
  keep_failure_logs: true
  keep_full_trace: false
```

字段职责：

- `input.source`：
  - `current_run`：`logger.log_dir()/current_run_subdir` 下查找（normal/stress/aging 用）。
  - `directory`：直接扫 `input.directory`（独立检测已有视频用）。
- `input.patterns`：匹配 `*.h265`、`*.hevc`。

---

## 6. 文件选择语义

- `all`：检测匹配目录下所有 `*.h265/*.hevc`。
- `latest`：只检测最新 1 个文件。
- `latest_unchecked`：检测「当前目录最新 且 本次 run 尚未检测过」的文件（normal/stress 推荐）。
  - 动机：stress 每轮 `video→video_integrity`；若本轮录像失败没生成新文件，`latest` 会重复检测上一轮文件，`latest_unchecked` 必须避免。
  - 机制：在 `<logger.log_dir()>/video_integrity/manifest.json` 维护本次 run 已检测文件（`logger.log_dir()` run 内稳定，跨 cycle 去重）。
  - 文件 identity 至少用：**绝对路径 + size + mtime_ns**（避免同名被覆盖后误判已检测）。
- `explicit`：只检测 `explicit_files`；相对路径相对于 `input.directory`，绝对路径直接用。

manifest.json 形如：

```json
{ "checked": [ { "path": "...", "size": 123456, "mtime_ns": 123456789 } ] }
```

## 7. 浅合并冲突与解决方案（关键）

**现状（已核实）**：

- `base.py` `_merge()` = `{**(self.config or {}), **(params or {})}`，顶层浅合并。
- `runner.py` `_run_tasks` 传 `params = dict(task.override or {})`。
- 因此 `override: {input: {source: directory, ...}}` 会**整体替换**模块 yaml 里的 `input` dict，丢失 `patterns/recursive/empty_input_policy/current_run_subdir`。

**解决方案（二选一，推荐 A，均不改 core）**：

- **A（推荐）模块内 deep-merge**：在 `VideoIntegrityModule` 子类覆盖 `_merge()`，对 `input/analysis/hevc/diagnostic` 等嵌套 dict 做**递归合并**（dict 逐 key 深合并，list/scalar 以 override 优先）。这样既保留嵌套配置结构，又不动 `base.py/runner.py/config.py`。
- B 扁平参数结构：把 override 写成顶层 key（如 `input_source: directory`），避开嵌套——但可读性差，不推荐。

> 明确要求：**不得顺手重构整个 Config/Runner 的合并机制**。

`duration_key`：本模块**不设** `duration_key`（保持 None），避免 `task.duration` 误覆盖某参数。

## 8. 检测算法（三阶段，分层执行）

```text
文件选择
  ↓
Stage 1 完整解码（全文件）
  ↓
PASS?
 ├─ YES → 文件 PASS（不跑 Stage2/3）
 └─ NO  → Stage 2 showinfo 定位 → Stage 3 trace_headers → 分类错误
```

不要对所有正常文件直接跑 `trace_headers`（日志量巨大）。

### Stage 1：全文件 decode

```bash
ffmpeg -hide_banner -v error -err_detect explode -i <video.h265> -f null -
```

- 判据：`returncode == 0` 且 error stderr 为空 → PASS；否则 FAIL 进入详细诊断。
- 重点识别：`Could not find ref with POC` / `Error constructing the frame RPS` / `Error parsing NAL unit` / `Invalid NAL unit` / `Invalid data found when processing input` / `Error submitting packet to decoder`。
- 不要只靠固定字符串定死所有结果；保存 `return code / stderr / first relevant error`。

### Stage 2：showinfo 定位（仅 Stage1 失败时）

```bash
ffmpeg -hide_banner -threads 1 -loglevel info -err_detect explode \
       -i <video.h265> -vf showinfo -f null -
```

- 目的：回答「问题在人类播放时间轴的大约位置」+「错误前最后成功输出的 decoded frame 是什么」。
- 解析 `Parsed_showinfo ... n:<N> ... pts_time:<T>`。
- **注意**：`n` 是 FFmpeg 成功输出的 decoded-frame 序号，**不是** sensor frame id / coded-picture index / 日志行号。
- 产出：`last_good_decoded_frame`、`last_good_pts_time`、`first_decode_error`。
- **禁止**用 `grep -n` 文本行号当视频帧号。

### Stage 3：trace_headers 码流分析（仅 Stage1 失败且配置允许时）

先检查 `ffmpeg -bsfs` 是否支持 `trace_headers`（本机已确认支持）。

```bash
ffmpeg -hide_banner -loglevel debug -i <video.h265> \
       -map 0:v:0 -c:v copy -bsf:v trace_headers -f null -
```

- 必须 `-c:v copy`，避免重编码。
- 重点解析：`nal_unit_type`、`slice_pic_order_cnt_lsb`、SPS 中 POC LSB 位宽、IRAP/IDR 边界。

## 9. POC gap 判定（不要造假精度）

产品已观测到典型固定 GOP（IDR + POC1..POC29，GOP≈30），异常样本 `POC14→15→17→18` 且 decoder 报 `Could not find ref with POC 16` → 分类 `MISSING_PICTURE / missing_poc=16`。

**但禁止**实现 `if current_poc != previous_poc + 1: FAIL`。通用 HEVC 存在 IDR reset / CRA / POC LSB wrap-around / B 帧重排 / temporal layer / multi-slice picture。

第一版至少满足：

1. 不跨 IDR/IRAP 边界比较连续性；
2. 同一 Picture 多 Slice 不得误判为多帧；
3. POC reset 不得判为丢帧；
4. POC wrap-around 不得判为丢帧；
5. 仅当当前 GOP 内已建立稳定连续关系时才报告 missing POC；
6. 无法高置信重建时，退化为 `REFERENCE_CHAIN_ERROR`。

### 全局 coded picture index（可选）

仅当 `fixed GOP + GOP size 已确认 + POC gap 明确 + IRAP 边界明确` 时才计算：

```text
expected_gop_size = 30, gop_index = 55, missing_poc = 16
  → coded_frame_index = 1666   # 0-based
  → frame_number      = 1667   # 1-based
  → approx_timestamp ≈ 55.533s
  → confidence = "fixed_gop"
```

- 若 GOP/POC 无法确认 → `coded_frame_index = null`，**不要硬算**。
- **特别禁止**把 trace 日志的 `nl` 行号当视频帧号。

## 10. 错误分类（driver 的 `error_type`）

```text
PASS
TOOL_NOT_FOUND            # ffmpeg 不存在
INPUT_NOT_FOUND           # 指定目录/文件不存在
NO_MATCHING_VIDEO         # 目录下无匹配文件
PROCESS_TIMEOUT           # ffmpeg 卡住超时
DECODE_ERROR
MISSING_REFERENCE         # e.g. Could not find ref with POC 16
REFERENCE_CHAIN_ERROR     # 无法高置信重建时的退化分类
NAL_PARSE_ERROR
MISSING_PICTURE           # 仅 trace_headers 高置信确认 15→17 且 16 缺失
TRACE_HEADERS_UNAVAILABLE
UNKNOWN_HEVC_ERROR
```

- `MISSING_PICTURE` **只**在 trace_headers 高置信确认「15→17 且 16 未出现」时用；**不要**仅凭 decoder 的 `Could not find ref with POC16` 就叫 `MISSING_PICTURE`（可能 POC16 存在但数据损坏 → 那是 `MISSING_REFERENCE`）。

### error_type → TestResult.status 映射（模块层）

| error_type | TestResult.status |
|---|---|
| PASS | PASS |
| TOOL_NOT_FOUND / INPUT_NOT_FOUND | ERROR（环境/配置问题，带清晰路径） |
| NO_MATCHING_VIDEO | 依 `empty_input_policy`：fail→FAIL / skip→SKIP |
| PROCESS_TIMEOUT 及 DECODE 家族、MISSING_*、NAL_*、REFERENCE_CHAIN_ERROR、TRACE_HEADERS_UNAVAILABLE、UNKNOWN_HEVC_ERROR | FAIL |

## 11. Driver 返回结构

定义内部 dataclass（字段按项目风格可微调，**不要为第一版改 core `TestResult`**）：

```python
@dataclass
class H265ValidationResult:
    file_path: str
    ok: bool
    error_type: str = ""
    reason: str = ""
    decode_returncode: int = 0
    first_decode_error: str = ""
    last_good_decoded_frame: Optional[int] = None
    last_good_pts_time: Optional[float] = None
    missing_poc: Optional[int] = None
    gop_index: Optional[int] = None
    coded_frame_index: Optional[int] = None
    frame_number: Optional[int] = None
    approx_timestamp: Optional[float] = None
    expected_fps: Optional[float] = None
    expected_gop_size: Optional[int] = None
    confidence: str = ""
    diagnostic_logs: list = field(default_factory=list)
```

## 12. Module 返回策略（聚合，不逐文件改变 Runner 语义）

- 一次 `video_integrity` task → 返回**一个 aggregate `TestResult`**。
- 例：检测 5 个文件，4 PASS 1 FAIL → 模块整体 `FAIL`。
  - `message`: `H265检测 5 个：PASS=4 FAIL=1`
  - `detail`: 逐文件一行（`[PASS] good1.h265` / `[FAIL] problem.h265` + `error_type/missing_poc/timestamp`）
- **任意一个选中文件失败 → task FAIL**；不能因为另一个文件 PASS 而整体 PASS。
- 每个文件结果同时打到 `run.log`。

## 13. 日志 / manifest 约定

**禁止写入 `serial.log`**（H265 检测属 PC 本地诊断）。

```text
<logger.log_dir()>/
└── video_integrity/
    ├── manifest.json
    ├── summary.log
    └── <video-name>/
        ├── decode.log
        ├── showinfo.log
        ├── trace_headers.log
        └── diagnostic.txt
```

- PASS 文件默认**不生成**大量 showinfo/trace 日志；只有 FAIL 才执行详细诊断。

## 14. 大文件 / 内存 / 安全要求

- **严禁** `subprocess.run(..., capture_output=True)` 捕获完整 showinfo/trace_headers 大日志到内存。
- decode 的 error stderr 可**有限**捕获；showinfo/trace 输出**直接写文件**，Python 按行解析。
- 所有 ffmpeg 调用必须有 `timeout`；超时后必须 `kill` + `wait` 子进程，**不留僵尸进程**。
- 用 `subprocess.run([...])` / `subprocess.Popen([...])` 的 **argv list**；**不要 `shell=True`**、**不要拼接 shell 命令**。
- 正确支持**路径含空格 / 中文目录 / 特殊字符文件名**。

## 15. empty input 行为

- `empty_input_policy: fail`（默认）：无匹配文件 → FAIL（standalone 明确要求检查目录时用）。
- `empty_input_policy: skip`：本轮无新的完整本地视频 → SKIP，避免重复检测上一轮视频（normal/stress 用）。

## 16. Scenario 配置示例

### normal（录像后检测，覆盖为 skip）

```yaml
scenario:
  name: normal
  preview: {enabled: true}
  prepare: [serial_init, wifi_connect, preclean, ftp_ready, preview_start]
  tasks:
    - module: emmc
    - module: photo
    - module: video
    - module: video_integrity
      override:
        input:
          source: "current_run"
          selection: "latest_unchecked"
          empty_input_policy: "skip"
    - module: rtmp
  cleanup: [stop_stream, preview_stop, close_serial]
```

### stress（每轮检测本轮的 Video_N）

```yaml
scenario:
  name: stress
  preview: {enabled: true}
  prepare: [serial_init, wifi_connect, preclean, ftp_ready, preview_start]
  loop: {enable: true, count: 20}
  tasks:
    - module: photo
      repeat: 50
    - module: video
      duration: 180
    - module: video_integrity
      override:
        input:
          source: "current_run"
          selection: "latest_unchecked"
          empty_input_policy: "skip"
    - module: rtmp
      duration: 600
  cleanup: [stop_stream, preview_stop, close_serial]
```

时序（cycle 仍由 Runner 控制，模块内不写 cycle 循环）：

```text
cycle1: video(A) → video_integrity(A) → rtmp
cycle2: video(B) → video_integrity(B) → rtmp
...
```

### standalone（独立检测，脱机可跑）

`ATS/config/scenarios/video_integrity.yaml`：

```yaml
scenario:
  name: video_integrity
  prepare: []
  tasks:
    - module: video_integrity
      override:
        input:
          source: "directory"
          directory: "/home/gravity/h265_cases"
          selection: "all"
  cleanup: []
```

运行：

```bash
python3 -m ATS.main --scenario video_integrity
```

该场景：不探串口 / 不开串口 / 不等 msh / 不连 WiFi / 不启动 ftp_server / 不连 nginx；只「扫描本地文件 → H265 检测 → 输出报告」，真机断开也能跑。

## 17. 验证用例（Case A~I）

> 前置：准备两个真实样本 `good.h265`、`problem.h265`（problem 已知 `Could not find ref with POC 16` + trace 观察到某 GOP `...14,15,17,18...`）。样本不在仓库内（`downloads/` 已 gitignore），Code Agent 若拿不到需向用户确认样本路径。

| Case | 场景 | 期望 |
|---|---|---|
| A | 模块未加入 Scenario | 完全不执行（无 `video_integrity` task） |
| B | normal | video 下载完成后检测最新视频 |
| C | stress ≥2 cycle | cycle2 检测 Video_B，不重检 Video_A |
| D | standalone 拔板/不连串口 | 仍能检测本地目录 |
| E | directory + all（good + problem） | overall FAIL，PASS=1 FAIL=1 |
| F | explicit 只选 good.h265 | 不扫 problem.h265 |
| G | ffmpeg 不存在 | ERROR + 清晰路径 |
| H | trace_headers 不可用且 Stage1 已失败 | 仍 FAIL，仅详细诊断降级（不得反而 PASS） |
| I | 模拟 ffmpeg 卡住 | PROCESS_TIMEOUT 且无残留 ffmpeg 进程 |

离线验证最低要求：

- `good.h265`：`ffmpeg -v error -err_detect explode -i good.h265 -f null -` 无错误 → 期望 PASS。
- `problem.h265`：期望 FAIL，`error_type = MISSING_PICTURE`、`missing_poc = 16`；若固定 GOP 映射能高置信确认 → `coded_frame_index ≈ 1666 / frame_number ≈ 1667 / timestamp ≈ 55.53s`，否则**不输出**全局 index（绝不输出错误 index）。

- Remaining Limitations：明确「检测的是 H265 bitstream integrity，不是通用视觉马赛克 AI 检测」。

## 20. 增补：与第二版设计文档的差异对齐（评审后合并）

> 本节合并用户随后补充的第二版设计文档（含两条口头收紧）与本文档 §0~§19 的差异。
> 核心结论（架构边界 / 启用策略 / 去重 / 内存安全 / 视觉边界）两边一致，**不重复**；
> 只记录【新增细节】与【冲突/纠正】两类。实施时以本节 + 本文档前文为准，第二版示例若与前文冲突以前文为准。

### 20.1 两条口头收紧（硬性验收点，优先级最高）

1. **禁止在 `VideoModule.run()` 末尾调用检测器**：录像后检测必须用 `video` → `video_integrity` 两个 task 表达，由 Runner 按 task 声明顺序调度。任何「在 `video.run()` 里调 `H265Validator`」都破坏模块边界，直接否决。→ 与 §2/§4 一致，此处显式点名禁止该实现模式。
2. **浅合并**：`base._merge()` 是浅层 dict 覆盖，嵌套 `override.input.*` 会把模块默认 `input` **整段覆盖**。Agent 必须在 `video_integrity` 模块内部做局部嵌套合并（deep-merge），或改成扁平键；**不得**为这点重构 Runner/Config。→ 与 §7 一致，作为验收必查项。

### 20.2 新增：Stage 0 文件预检查（补入 §8 管线）

在 Stage 1 全文件 decode 之前增加文件预检查：

- 文件存在 → 否则 `INPUT_NOT_FOUND`；
- 是普通文件 → 否则 `INVALID_INPUT`；
- 大小 > 0 → 否则 `INVALID_INPUT`；
- 扩展名匹配 `patterns` → 否则 `INVALID_INPUT`；
- 可读 → 否则 `INPUT_NOT_READABLE`。

说明：预检查失败只能报环境/输入问题，**不得**宣称「编码器损坏」（文件尚未进入 HEVC 解码）。→ §10 错误分类表补充 `INPUT_NOT_READABLE`、`INVALID_INPUT` 两个分类。

### 20.3 新增：文件匹配细节（补入 §6/§9）

- 忽略目录本身（只匹配文件）；
- 默认不递归（`recursive: false`）；
- **不处理临时/下载中的 `.part` 文件**（FTP 断点续传会留下部分文件，需从匹配结果排除）；
- 支持中文路径、路径含空格、特殊字符文件名（argv list 已保证，见 §14）。

### 20.4 新增：trace_headers 与 showinfo 的观测位置区别（补入 §8 说明）

- `showinfo` 挂在 **Decoder 之后**：看「解码后的 picture」，只能证明「解码在 POC16 处出错」；
- `trace_headers` 是 bitstream filter，挂在 **Decoder 之前**：看「H.265 压缩码流 syntax」，能证明「POC16 在码流中确实不存在」。

这正是 §9 区分 `MISSING_PICTURE`（码流确实缺图）与 `MISSING_REFERENCE`（图存在但数据损坏）的依据。

### 20.5 新增：错误级联（Error Cascade）——只报首个 missing POC

若 POC16 缺失：POC17 依赖 16 → 17 失败；18 依赖 17 → 18 失败；19 依赖 18 → 19 失败…… 于是 decoder 会连报 `Could not find ref with POC16/17/18…`。

**这不代表 17/18/19 全部在文件中缺失。** 真正的 missing picture 必须由 trace_headers 确认。因此：

- 错误分类只报**首个** missing POC（本例为 16）；
- 级联错误作为 `reason`/`detail` 附注，**不得**逐条报 `MISSING_PICTURE`。

→ 与 §9「不要只靠固定字符串定死结果」「避免假精度」一致。

### 20.6 强化：`coded_frame_index` 命名红线

`coded_frame_index` 是「按当前 H.265 coded-picture 结构推算的理论位置」，**不是** Sensor 原始采集帧号。报告字段**必须**用 `coded_frame_index`，**禁止**命名为 `sensor_frame_id`。→ 与 §9 一致，此处显式强化命名红线。

### 20.7 字段命名一致性

第二版示例出现 `first_decoder_error`，与本文档 §11 dataclass 的 `first_decode_error` 不一致。**统一用 `first_decode_error`**（以 §11 dataclass 字段为准），`last_good_decoded_frame` / `last_good_pts_time` / `expected_gop_size` / `gop_index` / `coded_frame_index` / `frame_number` / `approx_timestamp` / `confidence` 两边一致，无需改。

### 20.8 新增：20 项验收清单（与 §17 Case A~I 互补，作为硬标准）

1. scenario 未配置 `video_integrity` 时不运行；
2. normal 可放在 `video` 后运行；
3. stress 每 cycle 检测新录像；
4. standalone 完全脱离 DUT；
5. 可配置目录（`directory`）；
6. 可配置 glob（`patterns`）；
7. 可配置 exact files（`explicit_files`）；
8. 可只检测最新（`latest`）；
9. 不重复检测 stress 上一轮文件（`latest_unchecked` + manifest）；
10. `good.h265` → PASS；
11. `problem.h265` → FAIL；
12. `problem` 可识别 missing POC16；
13. trace 支持时能区分 missing picture 与 reference error；
14. 工具缺失明确 ERROR；
15. timeout 后无 ffmpeg 残留进程；
16. 不污染 serial.log；
17. 不改 VideoModule 核心职责；
18. 不改 Runner 的 H265 特判；
19. 不改 ScenarioManager 的 H265 特判；
20. 所有结果进入现有 ATS 报告链路。

### 20.9 冲突/纠正：第二版 §33/§34 的 normal/stress 示例已过时

第二版文档的 normal 示例仍把 `wifi_check` / `wifi_scan` / `wifi_join` / `ftp` 列为 tasks，stress 示例缺失 `preview` 段。这**与当前 `new_arch` 分支现状冲突**：

- ADR-008：WiFi 移出 normal tasks（`wifi_connect` 是 prepare 收敛器，`wifi_check` 由其内部调用，`wifi_scan/join` 退出默认流程）；
- normal 已移除重复 ftp task（`prepare.ftp_ready` 保证）；
- ADR-010：`preview` 是 prepare/cleanup 动作（`preview_start`/`preview_stop`），tasks 不含 preview。

**以本文档 §16 的示例为准**（基于当前 `normal.yaml`/`stress.yaml`）：

- tasks 仅 `emmc / photo / video / [video_integrity] / rtmp`；
- `wifi_connect` / `preclean` / `ftp_ready` / `preview_start` 属 prepare；
- `preview.enabled` 保留在 scenario 层。
