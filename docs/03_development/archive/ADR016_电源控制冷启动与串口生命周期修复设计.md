# 1. 问题结论

当前 `recovery_validation` 存在启动依赖顺序反转：

```text
serial_init
→ power_switch_init
```

但真实硬件依赖关系是：

```text
PowerSwitch 串口可用
→ PowerSwitch 给 EVB 上电
→ EVB UART/USB 串口出现
→ 才能打开 EVB SerialConsole
```

如果 EVB 初始处于断电状态，则：

```text
serial_init
→ EVB 无电
→ EVB 串口不存在/不可打开
→ Scenario 直接失败
→ 永远执行不到 power_switch_init
```

这是必现的 bootstrap dependency inversion，不是偶发 race。

同时，由于 EVB 断电时 EVB 串口能力不可用，运行中的：

```text
Power OFF
→ Power ON
```

也意味着原 EVB 串口设备/句柄可能失效。

因此当前恢复链路：

```text
PowerCycle
→ 继续复用旧 SerialConsole
→ wait_for_ready_since()
```

也存在结构性缺陷。

本次必须同时修复：

1. **NEW-P0-05：Power-controlled EVB 冷启动顺序错误**；
2. **NEW-P0-06：PowerCycle 后 EVB 串口没有重新建立**。

只交换 YAML 中两行顺序不能视为完整修复。

# 2. 当前代码事实

## 2.1 EVB 串口与 PowerSwitch 串口是两套独立能力

当前 EVB：

```text
ATS/core/serial_console.py
SerialConsole
→ pyserial
→ 2000000 baud
→ msh 文本协议
→ exec_sync / exec_async / sentinel / health_check
```

当前上下电控制器：

```text
ATS/drivers/power_switch.py
PowerSwitch
→ pyserial
→ 115200 baud
→ 4-byte binary frame
```

PowerSwitch 明确不走 `SerialConsole`。

两者仅共享底层 `pyserial` 库，不共享上层协议和生命周期。

所以架构上不存在“必须先建立 EVB SerialConsole，才能建立 PowerSwitch”的技术依赖。

真正依赖关系应当相反：

```text
PowerSwitch
    ↓
EVB 电源
    ↓
EVB SerialConsole
```

# 3. 当前错误启动链路

当前 `ATS/config/scenarios/recovery_validation.yaml`：

```yaml
prepare:
  - serial_init
  - power_switch_init
  - wifi_connect
  - preclean
  - ftp_ready
  - health_monitor_start
```

真实执行：

```text
Scenario start
    ↓
serial_init
    ↓
detect EVB UART
    ↓
open SerialConsole
    ↓
wait msh
    ↓
health_check
    ↓
power_switch_init
```

如果板子初始 OFF：

```text
EVB OFF
    ↓
EVB UART 不存在
    ↓
serial_init 必然失败
    ↓
PowerSwitch 永远得不到初始化机会
```

形成死锁式依赖：

```text
要执行 power_switch_init
    ↓
必须先通过 serial_init

要让 serial_init 成功
    ↓
必须先执行 power_switch_init 给 EVB 上电
```

# 4. 正确的启动依赖模型

必须把启动分成两个电源域。

## 4.1 Phase A：基础设施 / 电源域

```text
PC
 ↓
PowerSwitch UART
 ↓
识别 PowerSwitch
 ↓
发送 POWER ON
 ↓
确认 POWER_STATE_ON
```

完成后才能假设：

```text
EVB 正在上电
```

## 4.2 Phase B：EVB 控制域

```text
EVB 上电
 ↓
等待 EVB UART 枚举
 ↓
识别 EVB UART
 ↓
建立 SerialConsole
 ↓
wait_for_ready
 ↓
health_check
```

完成后才能进入：

```text
WiFi
FTP
HealthMonitor
Tasks
```

# 6. power_switch_init 的新契约

对于：

```text
recovery.enabled=true
backend=power_cycle
```

`power_switch_init` 成功返回时必须满足：

```text
1. PowerSwitch 串口已打开；
2. 控制器身份已确认；
3. POWER ON 已发送；
4. 已确认 POWER_STATE_ON；
5. ctx.power_switch 有效。
```

不能出现：

```text
找不到控制器
→ 仅 WARN
→ 继续 serial_init
```

因为在 EVB 初始 OFF 时，这会直接把失败推迟到 EVB 串口阶段，掩盖真正根因。

# 8. 新增 PowerSwitch 端口配置

当前 `system.yaml`：

```yaml
power_switch:
  enabled: false
  baudrate: 115200
  reboot_delay: 3.0
```

建议新增：

```yaml
power_switch:
  enabled: true
  port: "auto"
  baudrate: 115200
  reboot_delay: 3.0
```

生产/固定测试机更推荐：

```yaml
power_switch:
  enabled: true
  port: "/dev/serial/by-id/<controller-id>"
  baudrate: 115200
  reboot_delay: 3.0
```

EVB 串口同理可使用稳定路径：

```yaml
serial:
  port: "/dev/serial/by-id/<evb-uart-id>"
  baudrate: 2000000
```

目的：

```text
避免 /dev/ttyUSB0 / ttyUSB1 因枚举顺序变化互换
```

如果当前硬件尚未获得稳定 `by-id`，仍保留 `auto`。

禁止凭猜测硬编码 USB VID/PID；只有真机确认后才可写入识别规则。

# 9. power_switch_init 在 serial_init 前时的端口识别

当 PowerSwitch 正确地提前到 `serial_init` 前：

```text
ctx.console == None
```

因此不能再依赖：

```text
“先识别 EVB，再排除 EVB”
```

正确策略：

## 9.1 显式端口优先

如果：

```yaml
power_switch.port != auto
```

只验证指定端口：

```text
open 115200
→ POWER_ON_FRAME
→ POWER_STATE_ON
→ success
```

## 9.2 auto 模式

如果：

```yaml
power_switch.port: auto
```

使用控制器协议本身识别：

```text
候选串口
→ 115200
→ POWER_ON_FRAME
→ 只有返回 POWER_STATE_ON 才认定为 PowerSwitch
```

如果 `system.serial.port` 已明确配置，则应提前从 PowerSwitch 候选中排除该端口，即使 `ctx.console` 尚未创建。

如果 EVB 也已经上电且 serial.port=auto，PowerSwitch auto 探测仍可能访问 EVB 串口，因此正式测试机优先推荐固定 PowerSwitch 端口。

# 10. serial_init 必须支持“上电后等待 UART 枚举”

PowerSwitch 返回 ON 后：

```text
EVB UART
```

不一定瞬间出现。

真实时序可能是：

```text
T+0s   POWER ON
T+1s   EVB 电源稳定
T+2s   USB-UART 枚举开始
T+3s   /dev/ttyUSB* 出现
T+5s   boot log
T+8s   msh ready
```

如果 `serial_init` 只扫描一次：

```text
T+0.1s detect_port()
→ 没发现串口
→ 失败
```

依旧存在 race condition。

---

# 11. 推荐实现：增强 serial_init，不复制第二套串口探测

EVB 串口的：

```text
发现
识别
打开
等待 ready
health_check
```

仍属于 `serial_init` 职责。

建议新增配置：

```yaml
serial:
  port: "auto"
  baudrate: 2000000
  power_on_detect_timeout: 30
  power_on_detect_interval: 0.5
```

语义：

```text
PowerSwitch 已存在 / recovery cold boot
    ↓
在 power_on_detect_timeout 内循环等待 EVB UART 出现并识别
    ↓
找到 EVB
    ↓
open
    ↓
wait_for_ready
    ↓
health_check
```

达到 timeout 仍无 EVB UART：

```text
ScenarioError(
  "PowerSwitch 已上电，但 EVB UART 在规定时间内未出现"
)
```

# 14. 不允许直接创建新 SerialConsole 替换 ctx.console

当前 Runner 初始化时保存：

```python
self.console = ctx.console
```

RecoveryCoordinator 也持有 console 引用。

如果恢复时：

```python
ctx.console = SerialConsole(...)
```

会导致：

```text
ctx.console         → new console
Runner.self.console → old console
Coordinator.console → old console
listener            → old console
```

形成引用分裂。

因此必须：

> **保持 SerialConsole object identity 不变，只重建底层 pyserial transport。**

---

# 15. 推荐：SerialConsole 增加 reconnect()

示意：

```python
def reconnect(self, port=None, baudrate=None):
    self.close()

    if port is not None:
        self.port = port
    if baudrate is not None:
        self.baudrate = baudrate

    self.open()
```

实施要求：

```text
1. listener 集合不被清空；
2. buffer sequence 保持单调递增；
3. old reader thread 正确停止；
4. old pyserial handle 释放；
5. new reader thread 正确启动；
6. 不清空日志系统；
7. 不创建第二个 SerialConsole。
```

RecoveryCoordinator 当前在 PowerCycle 前：




# 17. 新增恢复 action：serial_reconnect

推荐增加：

```text
serial_reconnect
```

职责：

```text
只负责 EVB UART transport 重建
```

不负责：

```text
PowerSwitch
WiFi
FTP
health policy
Task retry
```

流程：

```text
serial_reconnect
    ↓
ctx.console 必须存在
    ↓
关闭旧 pyserial transport
    ↓
等待/重新识别 EVB UART
    ↓
排除 ctx.power_switch.port
    ↓
同一个 SerialConsole.reconnect(new_port, baud)
    ↓
return
```

`serial_reconnect` 不做 `board_ready`。

职责分开：

```text
serial_reconnect = transport 恢复
board_ready      = msh ready + health_check
```

在 power_cycle recovery 场景禁止。

# 33. 架构红线

## BoardHealthMonitor
只检测，不控制电源，不做 serial reconnect。

## RecoveryCoordinator
只做策略与 restore 编排，不直接操作 pyserial 或 115200 帧。

## RecoveryBackend
只映射统一 recover() 到具体恢复能力。

## PowerSwitch
只负责控制器 UART、ON/OFF、严格回帧。

## SerialConsole
只负责 EVB UART transport、msh、buffer、listener、transport reconnect。

## Scenario
显式声明 bootstrap / restore / cleanup 顺序。

# 35. 完成判定

只有以下全部满足才能关闭 NEW-P0-05 / NEW-P0-06：

```text
EVB 初始 OFF
→ recovery_validation 可直接启动
→ 无需人工先上电
```

并且：

```text
PowerSwitch UART
→ ON
→ POWER_STATE_ON
→ EVB UART 枚举
→ SerialConsole
→ msh
→ health_check
```

运行中 PowerCycle 后：

```text
EVB UART 即使消失并重新枚举
→ ATS 也能自动恢复 transport
```

同时：

```text
SerialConsole object identity 不变
```

恢复顺序：

```text
serial_reconnect
→ board_ready
→ wifi_connect
→ preclean
→ ftp_ready
```

任一关键阶段失败：

```text
PowerSwitch
EVB UART
board_ready
restore
```

必须：

```text
Recovery FAIL/ERROR
ScenarioAbort（按 policy）
exit code 非 0
```

不得静默继续。

# 36. 最终原则

> **电源控制能力是 EVB 串口能力的基础设施前置条件；EVB 串口不能反过来成为 PowerSwitch 初始化的前置条件。**

这条依赖必须同时贯彻到：

```text
首次冷启动
+
运行中 PowerCycle 恢复
```

两个生命周期中。
