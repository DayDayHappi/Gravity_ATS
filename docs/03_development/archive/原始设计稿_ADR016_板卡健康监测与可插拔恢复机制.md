# Gravity_ATS 全局板卡健康监测与可插拔恢复机制设计方案

> 建议 ADR-016｜基线：all_source(10)｜状态：Design Accepted / 待 Code Agent 实施

---

## 1. 背景

当前 Gravity_ATS 已实现 ADR-015 串口上下电控制能力。PowerSwitch 位于 ATS/drivers/power_switch.py，协议位于 ATS/drivers/power_commands.py。其职责边界已经明确：只提供 power_on() / power_off() / reboot()，只回答“如何给板子上下电”，不感知板子是否死机、什么时候需要重启、重启后测试如何继续。

system.yaml 中已有 power_switch.enabled 开关，enabled=false 时不探测、不打开控制器串口，对原测试链路零影响。该增量语义必须继续保持。

## 2. 本次需要解决的问题

需要增加一个 Scenario 生命周期级 EVB 健康监测与恢复机制，用于 stress / aging 等长时间运行场景中识别 EVB 运行期失去响应，并在策略允许时执行恢复。

目标不是简单实现“检测不到板子就 PowerSwitch.reboot()”，而是建立完整链路：检测 → 确认 → 恢复决策 → 恢复执行 → 环境重新收敛 → 测试流程恢复或终止。

## 3. 核心架构决策

采用 Detection / Decision / Execution 三层分离：

BoardHealthMonitor：只判断 EVB 是否健康并输出 HealthEvent。
RecoveryCoordinator：消费健康状态，决定异常以后怎么办，并协调恢复流程。
RecoveryBackend：把统一恢复请求适配到具体恢复能力。
PowerSwitch：只执行上下电，不关心触发原因和测试策略。

推荐关系：
BoardHealthMonitor → HealthEvent → RecoveryCoordinator → RecoveryBackend → PowerCycleBackend → PowerSwitch。

## 4. BoardHealthMonitor 职责

BoardHealthMonitor 只负责观察和判断，不负责处理。

负责：监听 EVB 串口活动、记录最后有效 RX 时间、检测长时间无活动、维护 HEALTHY / SUSPECTED / UNRESPONSIVE 状态、保存证据、请求进一步健康确认。

禁止：直接调用 PowerSwitch、power_on/power_off/reboot、决定是否重启、决定 Task 是否重跑、恢复 WiFi/FTP、修改 Scenario。

状态建议：HEALTHY →（超过 inactivity_timeout）→ SUSPECTED →（主动健康确认连续失败）→ UNRESPONSIVE。

“无串口输出”不能直接等价于“整板死机”。UNRESPONSIVE 只表示 ATS 无法通过当前 EVB 控制链路取得有效响应，不推断根因。

## 5. Monitor 禁止直接调用 PowerSwitch 的原因

第一，职责会耦合：Monitor 同时承担检测、恢复策略、硬件选择和执行，未来替换 USB Relay、Network PDU、Soft Reset 时会不断膨胀。

第二，当前 SerialConsole listener 在 reader thread 中同步回调。现有 RTMPMonitor / StringHitMonitor 都保持极轻量。若 Monitor callback 中执行 PowerSwitch.reboot()，会包含下电、sleep、上电等阻塞动作，可能阻塞 EVB 串口 reader thread，反而放大“无响应”现象。

红线：Monitor listener 中禁止 sleep、exec_sync、exec_async、PowerSwitch、FTP、网络 IO 和其他阻塞操作。

## 6. RecoveryCoordinator 职责

推荐位置：ATS/application/recovery_coordinator.py。

负责：接收 BoardHealthMonitor 状态、防重复恢复、统计恢复次数、根据 Scenario Recovery Policy 选择 RecoveryBackend、暂停/恢复监测、失效板端运行状态、执行恢复、等待 EVB ready、恢复环境、通知 Runner 恢复结果、决定 retry 或 abort。

不负责：健康判据本身、PowerSwitch 二进制协议、具体上下电实现、photo/video/rtmp 业务逻辑。

## 7. RecoveryBackend 抽象

RecoveryCoordinator 不直接依赖 PowerSwitch。定义统一恢复能力接口：name、available(ctx)、recover(ctx)。

第一阶段只实现 PowerCycleBackend。未来可扩展 SoftResetBackend、NetworkPduBackend、UsbRelayBackend、ManualRecoveryBackend 等。

Coordinator 只调用 backend.recover()，因此更换电源机制无需修改 Monitor、Runner 或业务模块。

## 8. PowerCycleBackend

推荐目录：ATS/application/recovery_backends/。

PowerCycleBackend 的职责仅是把统一 recover() 请求映射成 ctx.power_switch.reboot()。PowerSwitch 本身保持 ADR-015 原职责不变。

## 9. 可选能力与优雅退化

允许以下组合：

1) monitor=false, recovery=false, power_switch=false：完全保持当前行为。
2) monitor=true, recovery=false, power_switch=false：只检测并记录，不自动恢复。
3) monitor=true, recovery=true, power_switch=true，backend=power_cycle：自动 power cycle。
4) 未来不用串口控制器时，可新增其它 Backend；HealthMonitor、RecoveryCoordinator、Runner、业务模块无需推翻。

HealthMonitor 可以长期存在，但 PowerSwitch 可以不存在。

## 10. 配置职责边界

system.yaml 只描述“当前机器有什么硬件能力”。power_switch.enabled 继续只表达串口上下电控制器是否可用，baudrate/reboot_delay 仍属于硬件参数。

禁止在 system.yaml 的 power_switch 段放“死机后是否重启、最大恢复次数、当前 Task 是否 retry”等策略。

## 11. BoardHealthMonitor 参数

建议新增 ATS/config/modules/board_health.yaml。虽然 BoardHealthMonitor 不作为 Task，但可沿用 PreviewManager 的模式存放 Scenario 生命周期级能力参数。

建议字段：check_interval、inactivity_timeout、confirm_failures、confirm_interval。具体默认值必须通过真实 stress 日志校准，尤其 inactivity_timeout 不应凭经验拍死。

## 12. Scenario Recovery Policy

“本次测试遇到板子异常以后怎么办”属于测试策略，放入 config/scenarios/*.yaml。

建议字段：health_monitor.enabled、recovery.enabled、recovery.backend、recovery.max_attempts、recovery.after_recovery、recovery.on_exhausted、recovery.restore。

after_recovery 第一阶段建议支持 retry_current_task；on_exhausted 建议 abort_scenario。恢复成功后原 Hang 事件必须保留，不能被后续 PASS 覆盖。

## 13. 配置合法性约束

禁止静默 fallback。若 recovery.enabled=true 且 backend=power_cycle，但 power_switch.enabled=false 或探测失败，应在正式 tasks 前明确报 RecoveryBackendUnavailable，不得偷偷改成 soft reset，也不得静默关闭 recovery。自动化行为必须确定、可审计。

## 14. 生命周期

BoardHealthMonitor 属 Scenario 生命周期能力，不是 Task。建议复用 prepare/cleanup 注册表新增 health_monitor_start / health_monitor_stop。

推荐 prepare 顺序：serial_init → power_switch_init → wifi_connect → preclean → ftp_ready → preview_start → health_monitor_start。

推荐 cleanup 首先执行 health_monitor_stop，然后 stop_stream → preview_stop → power_switch_close → close_serial，防止正常清理被误判为死机。

## 15. 第一阶段 Scope：不处理启动前已死机

当前 normal/stress 是先 serial_init 再 power_switch_init。如果脚本启动前 EVB 已完全死机、serial_init 无法识别板子，则 PowerSwitch 尚未初始化。

因此 ADR-016 第一阶段只处理 Scenario 已成功启动后的运行期故障，不解决“ATS 启动时 EVB 已死”。启动前 recovery 涉及 EVB 未识别时如何可靠区分 PowerSwitch 端口，应单独做后续 ADR。

## 16. Monitor 数据来源与线程红线

第一阶段主要使用 SerialConsole.add_listener() 观察 EVB UART。listener callback 只能做时间戳、计数、轻量状态更新。

禁止在 reader thread 中下发 shell 命令。主动 probe 必须进入 Runner / RecoveryCoordinator 的安全控制流。

## 17. 健康确认机制

last_rx 超时只进入 SUSPECTED。真正的主动健康确认建议在安全点复用 console.health_check()：echo EVBTEST_HELLO → 收到有效响应。

probe 成功：Monitor 回到 HEALTHY；连续 probe 失败达到 confirm_failures：进入 UNRESPONSIVE。

## 18. 为什么主动 probe 必须在安全点执行

当前 SerialConsole 的底层 write lock 只保护单次写，不提供完整 exec_sync/exec_async 命令事务的全局排他。如果后台 Monitor 同时 exec_sync，而业务模块正在 exec_async，可能发生命令和响应交叉。

因此 Monitor 线程只观察；主动 probe 由 Runner 控制流在不存在其他命令事务时执行。

## 19. Runner 接入方式

Runner 仍负责“什么时候执行”。新增 recovery checkpoint 属于调度职责，不越界。

基本流程：Task 完成 → Runner checkpoint → 若 Monitor=HEALTHY 则继续；若 SUSPECTED，则在安全点执行 active probe；probe 成功继续，失败达到阈值后交给 RecoveryCoordinator。

Runner 不认识 PowerSwitch、115200 波特率或控制帧，只认识 coordinator 的统一接口。

## 20. 长时间 Task

现有 video 存在 time.sleep(duration) 等长等待，纯 Task 边界检查会导致恢复延迟。

Phase 1 先只做 Task/repeat/cycle 边界安全检查，控制风险。Phase 2 再引入 RuntimeControl，例如 runtime.wait(duration)，内部按小周期 sleep + 检查全局 recovery request，实现 cooperative cancellation。业务模块仍不能直接执行 recovery。

## 21. RTMPMonitor 与 BoardHealthMonitor 的关系

RTMPMonitor 不被替代。RTMPMonitor 判断 RTMP 业务 heartbeat 是否正常；BoardHealthMonitor 判断 EVB 整板控制链路是否可响应。

RTMP heartbeat timeout 但 shell health_check PASS 时，应只判 RTMP FAIL，禁止 PowerCycle。业务故障不能自动升级为整板故障。

## 22. RecoveryCoordinator 状态机

推荐状态：IDLE → REQUESTED → RECOVERING → RECONCILING → HEALTHY；恢复失败进入 FAILED。

Coordinator 必须有 recovery_in_progress 或等效互斥，同一时间只允许一个恢复流程，防止多个 health event 并发触发多次 reboot。

## 23. Power Cycle 后 Context 状态失效

Power Cycle 后，与板端运行实例绑定的 ctx 状态必须视为失效：ctx.evb_ip、ctx.wifi_ready、ctx.skip_wifi、ctx.ftp_client、ctx.ftp_server_started 等。

不能直接调用 ctx.cleanup()，因为它会清空 system_config、console、power_switch、recovery_coordinator 等仍有效对象。

应新增局部状态失效机制，例如 invalidate_board_runtime_state()，只清理板端 reboot 后失效的状态。

## 24. Power Cycle 后仍有效的状态

应保持：ctx.system_config、ctx.power_switch、ctx.recovery_coordinator、ctx.board_health_monitor。ctx.pc_ip 通常仍可保持。PreviewManager 属 PC 侧 Scenario 生命周期能力，且已有断流重连 wrapper，原则上无需因 EVB reboot 销毁。

## 25. 恢复后的环境重新收敛

PowerSwitch 完成 OFF→ON 不等于 ATS 环境恢复。完整流程应为：PowerCycle → 等 EVB ready → Serial health check → WiFi 状态重新收敛 → preclean → FTP 服务重新建立 → 恢复任务执行。

RecoveryCoordinator 应复用现有 prepare action，避免复制第二套 Recovery WiFi / Recovery FTP 逻辑。

## 26. board_ready Action

建议新增轻量 board_ready action：console.wait_for_ready() → console.health_check()。第一阶段不要重新执行完整 serial_init，因为控制串口预计保持打开。

若真机发现 Power Cycle 导致 USB 串口重新枚举，再独立扩展 serial_reconnect，不提前假设。

## 27. Recovery Restore Actions

Scenario 可声明 recovery.restore，例如 normal/stress：board_ready、wifi_connect、preclean、ftp_ready；no_network 只需 board_ready、preclean。

Coordinator 只按策略调用已有 Action，不知道场景是否需要 WiFi/FTP，从而保持低耦合。

## 28. 恢复后当前 Task 的处理

当前 Task 一旦发生整板 UNRESPONSIVE，其运行状态已不可继续。应通过框架级 RecoveryRequested 或等效控制信号结束当前 Task 生命周期，Runner 执行 teardown/收尾后进入 recovery，再按 policy 决定 retry_current_task 或 abort。

禁止 video/photo/rtmp 等模块直接 ctx.power_switch.reboot()。

## 29. Recovery Event 不能被 PASS 覆盖

恢复事件必须独立留痕。建议新增 ctx.recovery_history，每条记录包含 timestamp、scenario、cycle、task、rep、health_state、reason、backend、attempt、recovery_result、restore_result。

Reporter 可增量增加 recovery_events，不改变现有 results 结构；HTML 增加 Recovery Events 区域。即使 retry 后 PASS，也必须保留原 Hang。

## 30. 日志原则

继续保护 serial.log 纯净性。建议职责：serial.log=EVB 原始串口；power_switch.log=电源控制器原始 TX/RX；recovery.log=恢复控制流；run.log=整体运行轨迹。Monitor/Coordinator 禁止把分析信息写入 serial.log。

## 31. 推荐新增文件

ATS/application/board_health_monitor.py
ATS/application/recovery_coordinator.py
ATS/application/recovery_backends/__init__.py
ATS/application/recovery_backends/base.py
ATS/application/recovery_backends/power_cycle.py
ATS/config/modules/board_health.yaml

Phase 2 可加入 ATS/application/runtime_control.py。第一阶段不要创建 modules/board_health.py，因为它不是 Scenario Task。

## 32. 对现有代码的影响范围

预计修改：core/scenario.py、core/scenario_manager.py、core/runner.py、core/reporter.py、application/*、config/modules/board_health.yaml、启用该能力的 scenario yaml。

原则上不修改 photo/video/rtmp/emmc/ftp/utest 业务模块；power_commands.py 不改；power_switch.py 第一阶段也尽量保持现状。

## 33. 对当前架构的影响

不会破坏当前架构。现有 Config → ScenarioManager → Runner → Module → Driver 仍保持。新增 Application Service 只承担跨模块系统级协调。

职责保持：Scenario=测试怎么组合及异常恢复策略；Runner=什么时候执行及什么时候进入恢复；Module=怎么测；Driver=怎么和硬件交互；Application Service=跨模块协调系统级行为。

## 34. 向后兼容红线

所有现有 Scenario 若没有 health_monitor/recovery 配置，默认 disabled，旧 YAML 可保持当前行为。power_switch.enabled=false 继续保证不探测、不打开、不产生 power_switch.log、不影响原测试。所有新增能力默认关闭。

## 35. 禁止的设计

禁止 BoardHealthMonitor → PowerSwitch；禁止 photo/video/rtmp → PowerSwitch；禁止 PowerSwitch → BoardHealthMonitor；禁止 Monitor listener 内执行串口命令/sleep/reboot/FTP；禁止仅凭串口静默直接判整板死机；禁止 backend 不可用时静默 fallback；禁止 PowerCycle 后继续信任 ftp_server_started/ftp_client/wifi_ready；禁止 recovery 成功后删除原 Hang 记录。

## 36. 分阶段实施建议

Phase 0：文档与契约冻结，不改代码。
Phase 1：Monitor Only，只实现 HEALTHY/SUSPECTED/UNRESPONSIVE，不接 PowerSwitch。
Phase 2：RecoveryCoordinator + RecoveryBackend + PowerCycleBackend，打通 UNRESPONSIVE→power cycle→board_ready。
Phase 3：Context invalidation + wifi_connect/preclean/ftp_ready 环境重新收敛。
Phase 4：Runner Recovery Policy，支持 max_attempts、retry_current_task、abort_scenario、recovery history。
Phase 5：长时间 Task Cooperative Control，引入 RuntimeControl，不允许业务模块自己实现 recovery。

## 37. 第一阶段验收标准

TC-BH-001 Monitor 关闭回归：monitor/recovery/power_switch 全关闭时行为与当前版本一致。
TC-BH-002 仅 Monitor：人为 EVB 无响应，HEALTHY→SUSPECTED→主动 probe→UNRESPONSIVE；不得出现 PowerSwitch TX。
TC-BH-003 正常静默不误判：可进入 SUSPECTED，但 probe 成功后恢复 HEALTHY，不能重启。
TC-RCV-001 PowerCycle 恢复：UNRESPONSIVE→recovery→power_switch.log 有上下电帧→EVB boot→board_ready PASS→环境收敛。
TC-RCV-002 PowerSwitch 不存在：backend=power_cycle 但能力关闭时，tasks 前明确 BackendUnavailable，不静默降级。
TC-RCV-003 RTMP 单模块故障：heartbeat timeout 但 shell health_check PASS，只判 RTMP FAIL，禁止 PowerCycle。
TC-RCV-004 连续 Hang 超上限：max_attempts=2，第三次 abort_scenario，禁止无限重启。
TC-RCV-005 Context 失效：PowerCycle 后 ftp_server_started=false、ftp_client=None、wifi_ready=false、skip_wifi=false，之后 restore 正确重建。

## 38. 最终职责定义

BoardHealthMonitor：我只负责判断板子是否健康，不负责处理板子。
RecoveryCoordinator：我只负责决定并协调“异常以后怎么办”，不负责具体硬件协议。
RecoveryBackend：我把统一恢复请求映射成某一种具体恢复能力。
PowerSwitch：我只负责按照请求上下电，不关心为什么上下电、什么时候上下电，也不关心板子是不是死机。

## 39. 建议 ADR-016 Decision 摘要

Gravity_ATS 引入 Scenario 生命周期级 BoardHealthMonitor 与 RecoveryCoordinator，并采用 Detection / Decision / Execution 三层分离。BoardHealthMonitor 只检测 EVB 健康状态并产生状态事件，不调用 PowerSwitch、不执行恢复。RecoveryCoordinator 消费健康状态，负责恢复策略、次数限制、Context 状态失效、环境重新收敛以及 Runner 流程协调。实际恢复动作通过统一 RecoveryBackend 接口提供；当前第一种 Backend 为 PowerCycleBackend，其内部复用 ADR-015 已实现的 PowerSwitch。RecoveryCoordinator 不直接依赖具体电源硬件。

power_switch.enabled 继续只表示当前环境是否存在串口上下电能力；是否进行健康监测、是否自动恢复以及采用何种恢复方式由 Scenario policy 独立控制。所有新增能力默认关闭；旧 Scenario 未声明 health_monitor/recovery 时行为与当前版本完全一致。

严禁 Monitor listener 中执行串口命令、sleep、上下电或其他阻塞操作；主动健康确认和实际恢复必须进入 Runner 安全控制流。PowerCycle 后必须失效所有与 EVB 运行实例绑定的 Context 状态，并通过现有 prepare action 重新完成环境收敛。第一阶段仅解决 Scenario 已正常启动后的运行期 EVB 无响应问题，不解决脚本启动前 EVB 已无法被 serial_init 探测的问题。

## 40. Document Agent 本轮固化范围

本轮只固化设计，不修改业务代码。建议新增 docs/02_design/decision_record/ADR-016-板卡健康监测与可插拔恢复机制.md，并更新 decision_record/README.md、system_architecture.md、data_flow.md、interface_spec.md、module_design.md、glossary.md、current_status.md、next_step.md。

所有文档必须明确标记：Design Accepted / 待 Code Agent 实施。不得描述成已经实现。ADR-015 原职责继续保留，ADR-016 是其上层补充。

## 41. 架构验收结论

本设计属于增量能力扩展，不改变 Scenario / Runner / Module / Driver 的既有职责。Application Service 用于承接跨 Module 的系统级协调，避免把死机检测、恢复策略、硬件控制、测试调度重新耦合到任何一个既有模块。

最终目标：Monitor 只监测；Coordinator 只协调；Backend 只适配恢复能力；PowerSwitch 只上下电。Monitor 不认识 PowerSwitch，Module 不认识 Recovery，PowerSwitch 不认识 Monitor，Runner 不认识具体硬件。
