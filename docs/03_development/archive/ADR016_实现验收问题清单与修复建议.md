## 2. 已正确实现的部分

- `BoardHealthMonitor` 不依赖 `PowerSwitch`，只维护 `HEALTHY / SUSPECTED / UNRESPONSIVE` 健康状态。
- `RecoveryCoordinator` 不处理 115200、二进制控制帧等具体硬件协议，只通过 `RecoveryBackend` 调用恢复能力。
- `PowerCycleBackend` 将统一 `recover()` 请求映射为 `ctx.power_switch.reboot()`，`PowerSwitch` 保持 ADR-015 的被动能力边界。
- `Context` 新增 `invalidate_board_runtime_state()`，Power Cycle 后只清理板端运行实例相关状态，不调用 `ctx.cleanup()` 全量清空。
- 恢复后的 WiFi / preclean / FTP 收敛复用已有 prepare action，没有建立第二套 Recovery WiFi / FTP 业务逻辑。
- 新增 `recovery.log`，与 `serial.log`、`power_switch.log` 职责分离。
- Reporter 已增加 `result.json.recovery_events` 参数入口，方向正确。
- 旧 Scenario 未声明 `health_monitor/recovery` 时保持默认关闭，向后兼容思路正确。

## 4. P0-01 BoardHealthMonitor 当前不是持续监测器

### 当前实现

- `BoardHealthMonitor.on_rx()` 只更新时间戳和计数，这是正确的轻量 listener 设计。
- `HEALTHY -> SUSPECTED` 的超时推进发生在 `current_state()` 中。
- `current_state()` 目前主要由 Runner 在 Module 执行结束后的 `_recovery_checkpoint()` 调用。

### 风险

如果 video / rtmp 等 Task 持续数十秒到数分钟，EVB 在 Task 中途死机时，框架可能直到 Task 返回后才首次发现 `inactivity_timeout`。

### 推荐修法

- 给 `BoardHealthMonitor` 增加轻量 watchdog timer/thread。
- watchdog 每 `check_interval` 秒只比较：

```text
time.monotonic() - last_rx
```

- 超过 `inactivity_timeout` 时，只做：

```text
state = SUSPECTED
runtime_control.request_recovery()
```

- watchdog 线程禁止执行：
  - `exec_sync`
  - `exec_async`
  - `health_check`
  - `PowerSwitch`
  - FTP
  - 网络 IO
- 主动健康 probe 仍由 Runner 在安全点执行。

### 修复后验收

在 180s video 中途人为断掉 EVB 后，应在：

```text
inactivity_timeout + check_interval
```

范围内触发 recovery request，而不是等 180s Task 完成。

## 5. P0-02 runtime_control.wait() 触发链没有闭环

### 当前实现

video 已将：

```python
time.sleep(duration)
```

改为：

```python
runtime_control.wait(duration)
```

但是 `runtime_control.wait()` 只有在：

```text
recovery_requested = true
```

时才提前返回。

而当前 `recovery_requested` 主要由：

```text
BoardHealthMonitor.current_state()
```

判断 `SUSPECTED` 后置位。

### 风险

长 Task 内部没有人调用 `current_state()` 时，`runtime_control.wait()` 等不到 recovery request。

因此 cooperative cancellation 形式上已经接入，实际触发链并未闭环。

### 推荐修法

与 P0-01 一并修复：

```text
watchdog
  ↓
SUSPECTED
  ↓
request_recovery()
  ↓
runtime_control.wait() 提前返回
  ↓
Module 尽快让出控制权
  ↓
Runner 安全点 probe
```

Module 仍然不能直接执行 recovery。

### 修复后验收

video 等待期间触发 `SUSPECTED` 后，`runtime_control.wait()` 应在约一个 wait step 内提前返回。

## 6. P0-03 confirm_failures 被拆散到后续多个 Task

### 当前实现

Runner checkpoint 发现 `SUSPECTED` 时只调用一次：

```python
monitor.probe(self.console)
```

第一次失败后：

```text
consecutive_probe_failures = 1/N
```

如果没达到阈值，就继续执行后续 Task。

### 风险

板子已经真实无响应时，系统仍会继续执行后续业务 Task，产生大量连锁 timeout / FAIL。

### 推荐修法

一旦 Runner 在安全点发现：

```text
SUSPECTED
```

就在同一次确认流程中完成：

```text
probe #1
  ↓ failure
sleep(confirm_interval)

probe #2
  ↓ failure
sleep(confirm_interval)

probe #3
  ↓ failure
UNRESPONSIVE
```

规则：

- 任一次 probe 成功：
  - 回到 `HEALTHY`
  - 清零失败计数
  - 继续测试
- 全部失败：
  - 立即进入 `UNRESPONSIVE`
  - 不再执行下一个业务 Task

### 修复后验收

`confirm_failures=3` 时，单次 SUSPECTED checkpoint 应完成 3 次健康确认，而不是跨 3 个 Task 累计。

## 7. P0-04 abort_scenario 当前只 abort 当前 cycle

### 当前实现

`Runner._run_tasks()` 收到：

```text
outcome.action == abort_scenario
```

后执行：

```python
return
```

但外层：

```python
while True:
    cycle += 1
    self._run_tasks(cycle)
```

仍然继续。

### 风险

例如 stress：

```text
cycle 10
  ↓
恢复次数耗尽
  ↓
abort_scenario
  ↓
只停止 cycle 10 剩余 Task
  ↓
cycle 11 又开始
```

违反：

```yaml
on_exhausted: abort_scenario
```

的语义。

### 推荐修法

增加框架级：

```text
ScenarioAbort
```

或等价的显式 abort flag。

推荐：

```text
_run_tasks()
  ↓
发现 abort_scenario
  ↓
raise ScenarioAbort
  ↓
TestRunner.run() 外层捕获
  ↓
退出整个 while loop
  ↓
ScenarioManager finally 正常 cleanup
```

### 修复后验收

`loop.count=200` 时任意 cycle 触发 `abort_scenario` 后，不得进入下一 cycle。

## 8. P0-05 Recovery Event 在报告前被 Context.cleanup() 清掉

### 当前实现

`RecoveryCoordinator._record()` 正确写入：

```python
ctx.recovery_history.append(entry)
```

但是：

```text
ScenarioManager.run()
  ↓
runner.run()
  ↓
cleanup actions
  ↓
ctx.cleanup()
  ↓
self._data.clear()
  ↓
return results
```

而 `main.py` 是在：

```text
manager.run()
```

返回之后才读取：

```python
manager.ctx.recovery_history
```

### 风险

真实发生 recovery 后：

```text
recovery.log
```

可能有记录，但：

```json
"recovery_events": []
```

仍可能为空。

### 推荐修法

在 `ctx.cleanup()` 前：

```python
self.recovery_history = list(getattr(ctx, "recovery_history", None) or [])
```

然后 main 改为读取：

```python
manager.recovery_history
```

更完整的未来方案可以设计：

```text
RunOutcome
  ├── results
  └── recovery_events
```

但本轮不必扩大架构改动。

### 修复后验收

制造一次 mock 或真机 recovery 后：

```text
Scenario 结束
  ↓
ctx.cleanup()
  ↓
生成 result.json
```

`recovery_events` 仍必须存在完整记录。

## 9. P0-06 PowerCycle 后 board_ready 可能命中旧串口缓冲

### 当前实现

`board_ready` 调用：

```python
console.wait_for_ready()
```

当前 `wait_for_ready()` 首先检查：

```python
self._buffer_text()
```

也就是整个历史 ring buffer。

PowerCycle 前 buffer 中大概率已经有：

```text
msh />
```

### 风险

可能出现：

```text
PowerCycle
  ↓
板子刚开始 boot
  ↓
board_ready
  ↓
历史 buffer 中找到 reboot 前的 msh />
  ↓
立即判“已就绪”
```

这是错误的 fresh-ready 判据。

### 推荐修法

复用现有 BUG-005 的 seq cursor 机制。

新增类似：

```python
cursor = console.snapshot_rx_cursor()
console.wait_for_ready_since(cursor)
```

Recovery 流程：

```text
记录 cursor_before_reboot
  ↓
PowerCycle
  ↓
只匹配 seq > cursor_before_reboot 的新 RX
  ↓
发现新 boot log / 新 msh
  ↓
READY
```

### 修复后验收

reboot 前即使 ring buffer 中已有大量 `msh />`，PowerCycle 后仍必须等待新的 RX ready 证据。

## 10. P0-07 Monitor-only 无明确 FAIL / abort 语义

### 当前实现

配置：

```yaml
health_monitor:
  enabled: true

recovery:
  enabled: false
```

时，不会创建 `RecoveryCoordinator`。

Runner 发现：

```text
UNRESPONSIVE
```

后只是：

```python
logger.error(...)
return None
```

### 风险

系统已经确认板卡不可响应，但：

- 仍可能继续后续 Task
- 没有独立 `TestResult`
- 最终退出码可能不准确反映板卡异常

### 推荐修法

定义清晰语义：

```text
UNRESPONSIVE
+
recovery disabled
```

应该：

1. 产生框架级 `board_health` FAIL / ERROR 记录。
2. 默认执行 `abort_scenario`，或由独立 policy 控制。
3. 不执行 PowerCycle。

必须明确：

> `recovery.enabled=false` 只表示“不自动恢复”，不表示“忽略已确认的板卡死机”。

### 修复后验收

`health_monitor=true + recovery=false` 时确认 `UNRESPONSIVE`：

- 必须形成可见失败记录
- 不执行 PowerSwitch
- Scenario 按策略结束

## 11. P1-01 retry_current_task 的第二次 RecoveryOutcome 被丢弃

### 当前实现

第一次：

```text
_run_module()
  ↓
retry_current_task
```

Runner 会再次：

```python
_run_module(...)
```

但第二次返回的 `RecoveryOutcome` 没再进入 action 处理逻辑。

### 风险

重跑 Task 时再次死机，即使返回：

```text
abort_scenario
```

也可能被忽略。

### 推荐修法

把：

```text
Task 执行
+
RecoveryOutcome 处理
```

统一收敛成一个循环/helper。

每次 `_run_module()` 的 Outcome 都必须处理，直到：

```text
success
continue
abort_scenario
```

并受：

```text
RecoveryCoordinator.max_attempts
```

约束。

### 修复后验收

retry Task 中再次触发 `abort_scenario` 时，必须真正终止整个 Scenario。

## 12. P1-02 RecoveryBackend 可用性检查发生得太晚

### 当前实现

配置：

```yaml
recovery:
  enabled: true
  backend: power_cycle
```

时，只有真正发生 `UNRESPONSIVE` 后，才调用：

```text
_resolve_backend()
```

检查 `ctx.power_switch`。

### 风险

如果：

```yaml
power_switch:
  enabled: false
```

或者控制器探测失败，测试可能已经跑了很久，真正死机后才发现根本无法恢复。

### 推荐修法

在：

```text
health_monitor_start
```

创建 Coordinator 后，立即执行 backend/policy validate。

如果：

```text
recovery.enabled=true
backend=power_cycle
PowerSwitch unavailable
```

应在正式 tasks 前报：

```text
RecoveryBackendUnavailable
```

禁止静默 fallback。

### 修复后验收

`power_switch.enabled=false + recovery.backend=power_cycle` 时，不进入正式 tasks。

## 13. P1-03 recovery=true + health_monitor=false 时配置静默无效

### 当前实现

Coordinator 只在：

```text
health_monitor_start
```

中创建。

如果：

```yaml
health_monitor:
  enabled: false

recovery:
  enabled: true
```

则不会创建 Coordinator，也不会显式报错。

### 风险

配置看起来开启了 recovery，但实际上完全不会工作。

### 推荐修法

增加配置约束：

```text
recovery.enabled=true
    ↓
必须要求
health_monitor.enabled=true
```

第一阶段不满足时直接：

```text
ScenarioError / ConfigError
```

### 修复后验收

`recovery=true + health_monitor=false` 必须在 tasks 前明确报配置错误。

## 14. P1-04 未知 restore action 被静默跳过

### 当前实现

`RecoveryCoordinator._restore_environment()` 中：

```text
PREPARE_ACTIONS.get(name) is None
```

时只是：

```text
log
continue
```

最后仍可能：

```text
return "ok"
```

### 风险

例如 YAML 写错：

```yaml
restore:
  - wifi_conect
```

系统会跳过 WiFi 恢复，却可能判：

```text
restore ok
```

### 推荐修法

Recovery restore 应采用 fail-closed：

```text
未知 restore action
  ↓
restore failed
```

并建议在 tasks 前预校验：

```text
recovery.restore
```

所有 action 是否注册。

### 修复后验收

restore 中出现不存在的 action 时，恢复必须失败，不得返回 ok。

## 16. P1-06 check_interval / confirm_interval 当前未真正生效

### 当前实现

`board_health.yaml` 已配置：

```yaml
check_interval: 2.0
inactivity_timeout: 60.0
confirm_failures: 3
confirm_interval: 3.0
```

但：

- `check_interval` 没有后台 watchdog 使用
- `confirm_interval` 没有用于同一次连续 probe

### 风险

用户修改 YAML 后，行为可能没有变化。

形成：

> 配置看似可调，实际不生效。

### 推荐修法

- P0-01 watchdog 使用 `check_interval`
- P0-03 连续 probe 使用 `confirm_interval`
- 增加合法性校验：
  - `check_interval > 0`
  - `inactivity_timeout > 0`
  - `confirm_failures >= 1`
  - `confirm_interval >= 0`

### 修复后验收

修改两个时间参数后，可从日志时间差验证实际节拍发生变化。

## 17. 当前能力边界：只能直接识别“串口静默型无响应”

当前 `BoardHealthMonitor` 的 SUSPECTED 入口是：

```text
超过 inactivity_timeout 没有任何 RX
```

因此它适合直接识别：

- 板子彻底安静
- UART 不再输出
- CPU hang 后不再打印
- 板子掉电

但是如果出现：

```text
业务线程已经死
msh 无法工作
但是后台错误日志持续刷串口
```

则：

```text
last_rx
```

会一直更新。

Monitor 不会进入 `SUSPECTED`。

因此当前实现更准确的能力定义是：

> **识别“串口静默型整板无响应”，而不是覆盖所有形式的板卡死机。**

本轮不建议扩大成复杂多源 watchdog，但应在 ADR / known issue 中明确。

未来可以扩展：

```text
Task 业务 timeout
   ↓
request board health probe
   ↓
shell 也不响应
   ↓
升级 UNRESPONSIVE
```

这样可以覆盖“串口仍刷日志但控制链路已经死”的故障。

## 19. 推荐修复顺序

1. **P0-01 + P0-02**  
   建立轻量 watchdog，使 SUSPECTED 能在长 Task 中真正触发 cooperative cancellation。

2. **P0-03**

## 21. 给 Code / Architect Agent 的修复约束

修复过程中必须遵守：

- 不推翻 ADR-016 架构。
- 不把 `BoardHealthMonitor` 与 `PowerSwitch` 直接耦合。
- 不让业务 Module 直接调用 `RecoveryCoordinator` / `PowerSwitch`。
- Monitor listener / watchdog 只允许轻量状态判断。
- Monitor listener / watchdog 禁止：
  - 主动串口命令
  - blocking IO
  - FTP
  - PowerSwitch
- 主动 `health_check` 必须在 Runner 安全控制流执行。
- `PowerSwitch` 保持 ADR-015 原职责。
- 恢复后的环境重新收敛继续复用 prepare actions。
- 禁止复制第二套 WiFi / FTP 恢复逻辑。
- Recovery Event 必须独立留痕，不能被 retry 后 PASS 覆盖。
- 未知 backend / restore action / 非法 recovery 配置应 fail-closed。
- 禁止静默 fallback。

## 22. 最终验收判定标准

只有在完成上述 P0 / P1 修复，并且：

```text
静态测试 PASS
+
mock 测试 PASS
+
TC-BH-001~003 真机 PASS
+
TC-RCV-001~005 真机 PASS
```

之后，才建议将 ADR-016 状态从：

```text
已实施·待真机
```

更新为：

```text
已实施并真机验证
```

然后再考虑把：

```text
health_monitor
recovery
```

正式接入：

```text
stress
aging
```

场景。

当前版本不需要重构 `PowerSwitch`，也不需要推翻原 Scenario / Runner / Module / Driver 架构。

主要修复范围应集中在：

```text
BoardHealthMonitor
RuntimeControl
Runner
ScenarioManager
Context/Reporter 留痕
RecoveryCoordinator fail-closed 语义
```

整体属于 **运行时闭环修复**，不是架构推倒重来。
