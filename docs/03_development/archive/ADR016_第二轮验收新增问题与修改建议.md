# 3. NEW-P0-01：自动恢复失败后最终退出码可能仍然错误

## 3.1 当前实现

当前恢复失败链路大致为：

```text
UNRESPONSIVE
    ↓
RecoveryCoordinator.handle_unresponsive()
    ↓
恢复失败 / restore 失败 / max_attempts 耗尽
    ↓
RecoveryOutcome(action="abort_scenario")
    ↓
Runner
    ↓
raise ScenarioAbort
    ↓
TestRunner.run() 捕获
    ↓
return results
```

当前 `main.py` 最终退出码仍然依赖：

```python
has_fail = any(r.status in ("FAIL", "ERROR") for r in results)
```

monitor-only 路径已经显式增加：

```text
board_health FAIL
```

所以没有这个问题。

但是自动恢复路径中：

```text
backend recovery failed
restore failed
max_attempts exhausted
```

目前不保证一定向 `results` 中增加 framework-level FAIL/ERROR。

---

## 3.2 风险

存在如下情况：

```text
当前业务 Task PASS
    ↓
Task 结束后确认 UNRESPONSIVE
    ↓
Recovery 执行失败
    ↓
abort_scenario
    ↓
results 中没有新的 FAIL / ERROR
    ↓
main.py has_fail == False
    ↓
进程退出码可能为 0
```

这会导致：

- 自动化报告显示成功；
- CI 认为本轮测试通过；
- 但实际上板卡已经无响应并且恢复失败。

属于严重结果一致性问题。

---

## 3.3 推荐修改

建议在 Runner 统一处理失败的 `RecoveryOutcome`。

新增 framework-level TestResult，例如：

```text
name   = board_recovery
module = board_recovery
status = ERROR
```

建议 message 包含：

```text
backend
attempts
outcome.message
```

例如：

```text
board_recovery ERROR
恢复失败：backend=power_cycle, attempts=2,
reason=restore failed at board_ready
```

推荐规则：

### 情况 A：恢复成功

```text
outcome.success == True
```

不额外生成 FAIL。

恢复历史仍记录在：

```text
recovery_events
```

### 情况 B：恢复失败

```text
outcome.success == False
```

必须：

```text
append board_recovery ERROR
```

再根据：

```text
outcome.action
```

执行：

```text
abort_scenario
```

### 情况 C：恢复次数耗尽

同样生成：

```text
board_recovery ERROR
```

然后：

```text
ScenarioAbort
```

---

## 3.4 推荐落位

修改位置建议集中在：

```text
ATS/core/runner.py
```

Runner 已经负责：

```text
RecoveryOutcome → 流程行为
```

因此在这里将失败 Outcome 转换为 framework TestResult 最合适。

不要把 TestResult 生成逻辑塞进：

```text
RecoveryCoordinator
```

否则 Coordinator 会开始感知测试报告结构，职责会变宽。

---

## 3.5 验收标准

至少增加以下测试：

### Case A：backend recover 抛异常

期望：

```text
board_recovery ERROR
Scenario 终止
main exit code = 1
```

### Case B：restore 失败

期望：

```text
board_recovery ERROR
Scenario 终止
main exit code = 1
```

### Case C：max_attempts exhausted

期望：

```text
board_recovery ERROR
Scenario 终止
main exit code = 1
```

### Case D：恢复成功

期望：

```text
不生成 board_recovery ERROR
recovery_events 有事件
按 after_recovery 执行
```

# 4. NEW-P0-02：Recovery Policy 还没有完整 fail-closed

## 4.1 当前实现

当前 `RecoveryCoordinator.validate()` 已经校验：

- backend 是否注册；
- backend 是否 available；
- restore action 是否注册。

但是以下 policy 字段还没有完整校验：

```yaml
max_attempts:
after_recovery:
on_exhausted:
```

---

## 4.2 风险

例如配置误写：

```yaml
recovery:
  enabled: true
  backend: power_cycle
  max_attempts: 2
  after_recovery: retry_current_task
  on_exhausted: abort_scenaro
```

注意：

```text
abort_scenaro
```

拼写错误。

Coordinator 仍可能返回：

```python
RecoveryOutcome(
    action="abort_scenaro",
    success=False
)
```

而 Runner 只显式处理：

```text
abort_scenario
retry_current_task
```

未知 action 当前可能落入默认分支并退出 Outcome 处理循环。

最终效果可能是：

> Recovery 已失败，但 Runner 因 action 拼写错误继续执行。

这违背 ADR-016 当前已经形成的：

```text
fail-closed
```

原则。

---

## 4.3 推荐修改

在：

```python
RecoveryCoordinator.validate()
```

增加完整 policy schema 校验。

### `max_attempts`

要求：

```text
int
>= 1
```

非法：

```text
raise ValueError
```

---

### `after_recovery`

第一阶段建议只允许：

```text
retry_current_task
continue
```

如果当前设计暂时不需要：

```text
continue
```

则更严格，只允许：

```text
retry_current_task
```

不要预留一个“代码实际没完整支持”的枚举。

---

### `on_exhausted`

第一阶段建议只允许：

```text
abort_scenario
```

---

### backend

继续保持：

```text
必须已注册
必须 available
```

---

### restore

继续保持：

```text
全部 action 必须已注册
```

---

## 4.4 Runner 再增加一道兜底

即使前置 validate 已经存在，Runner 也建议对未知 Outcome action 做 fail-closed：

```text
未知 RecoveryOutcome.action
    ↓
记录 board_recovery ERROR
    ↓
raise ScenarioAbort
```

禁止：

```text
unknown action → break → 继续测试
```

这样可以防止：

- Coordinator bug；
- 未来新增 backend 返回非法 Outcome；
- 后续代码变更绕过 validate。

---

## 4.5 验收标准

以下配置均必须在正式 tasks 前失败：

```yaml
max_attempts: 0
```

```yaml
max_attempts: -1
```

```yaml
after_recovery: retry_task
```

```yaml
on_exhausted: abort_scenaro
```

预期：

```text
ScenarioError
exit code = 2
正式 tasks 不执行
```

# 5. NEW-P1-01：Scenario 生命周期接线仍可能静默失效

## 5.1 当前实现

现在：

```yaml
health_monitor:
  enabled: true
```

并不会自动创建 Monitor。

Scenario 还必须显式包含：

```yaml
prepare:
  - health_monitor_start
```

并在 cleanup 中包含：

```yaml
cleanup:
  - health_monitor_stop
```

同理，若使用：

```yaml
recovery:
  enabled: true
  backend: power_cycle
```

则实际还依赖：

```yaml
prepare:
  - power_switch_init
```

---

## 5.2 风险

### 情况 A：Monitor enabled，但忘记 start action

```yaml
health_monitor:
  enabled: true
```

但是：

```yaml
prepare:
  - serial_init
  - wifi_connect
```

结果：

```text
配置显示 Monitor 已启用
但 BoardHealthMonitor 从未创建
脚本也不会报错
```

---

### 情况 B：有 start，没有 stop

```yaml
prepare:
  - health_monitor_start
```

但 cleanup 忘记：

```yaml
- health_monitor_stop
```

则：

- watchdog daemon thread 生命周期没有正式收口；
- listener 可能一直挂到串口 close；
- 正常 cleanup 期间存在误判风险。

---

### 情况 C：PowerCycle Recovery enabled，但没有 power_switch_init

```yaml
recovery:
  enabled: true
  backend: power_cycle
```

如果没有：

```yaml
- power_switch_init
```

则 recovery backend 在 `health_monitor_start` 的 validate 阶段会不可用。

虽然现在会 fail-closed，但属于可以更早发现的 Scenario 配置错误。

---

## 5.3 推荐修改

建议在：

```text
ScenarioManager._parse_scenario()
```

之后增加：

```text
_validate_scenario_runtime_contract()
```

或等价方法。

不要偷偷自动插 action。

原则应该是：

> Scenario 声明与生命周期 action 不一致时直接报错，让 YAML 自己保持显式和可审计。

---

## 5.4 建议校验规则

### health_monitor.enabled=true

必须：

```text
prepare 包含 health_monitor_start
cleanup 包含 health_monitor_stop
```

---

### recovery.enabled=true

必须：

```text
health_monitor.enabled=true
prepare 包含 health_monitor_start
```

---

### backend=power_cycle

必须：

```text
prepare 包含 power_switch_init
```

并建议：

```text
power_switch_init
位于
health_monitor_start
之前
```

---

### cleanup 顺序

推荐：

```text
health_monitor_stop
    ↓
stop_stream
    ↓
preview_stop
    ↓
power_switch_close
    ↓
close_serial
```

如果场景没有某一 action，则只校验存在的动作之间相对顺序。

核心要求：

```text
health_monitor_stop
```

必须早于：

```text
power_switch_close
close_serial
```

避免 cleanup 本身被 Monitor 当成异常。

---

## 5.5 验收标准

以下 YAML 应在 tasks 前明确失败：

### enabled 但无 start

```yaml
health_monitor:
  enabled: true
```

且 prepare 无 `health_monitor_start`

---

### 有 start 无 stop

cleanup 无 `health_monitor_stop`

---

### PowerCycle backend 无 power_switch_init

---

### health_monitor_stop 排在 close_serial 之后

以上都应：

```text
ScenarioError
```

# 7. NEW-P2-01：watchdog 线程退出还可以更干净

## 7.1 当前实现

watchdog：

```python
while not self._stop_watchdog.is_set():
    time.sleep(self.check_interval)
    ...
```

stop：

```python
self._stop_watchdog.set()
self._watchdog.join(timeout=2.0)
```

---

## 7.2 风险

如果未来：

```yaml
check_interval: 10
```

watchdog 正在：

```text
sleep(10)
```

cleanup 调用：

```text
stop_event.set()
join(timeout=2)
```

2 秒后 join 会超时。

daemon thread 虽然最终会醒并退出，但生命周期不够干净。

---

## 7.3 推荐修改

改成：

```python
while not self._stop_watchdog.wait(self.check_interval):
    ...
```

这样：

```python
self._stop_watchdog.set()
```

会立即唤醒 wait。

stop 中继续：

```python
join()
```

即可快速退出。

---

## 7.4 额外建议

`stop()` 可以增加：

```python
runtime_control.clear_recovery()
```

作为 Scenario 生命周期收尾兜底。

---

## 7.5 锁粒度建议

当前 watchdog 在持有：

```text
self._lock
```

时会：

```python
logger.warn(...)
```

logger 会写文件并 flush。

建议改成：

```text
锁内：
  修改 state/reason/event

锁外：
  logger.warn(...)
```

避免串口 reader callback 在更新 `last_rx` 时等待文件 IO。

# 8. HW-RISK-01：PowerCycle 后 EVB 串口是否重枚举必须真机确认

## 8.1 当前恢复假设

当前 Recovery 设计假设：

```text
原 SerialConsole 已打开
    ↓
Power OFF
    ↓
Power ON
    ↓
原 pyserial fd 仍可继续读写
    ↓
wait_for_ready_since(cursor)
```

所以当前实现没有：

```text
serial_reconnect
```

---

## 8.2 风险

如果 EVB 的 UART 转 USB 芯片随板子电源一起掉电，则可能出现：

```text
/dev/ttyUSB0 消失
    ↓
Power ON
    ↓
USB 重新枚举
    ↓
/dev/ttyUSB0 或其它节点重新出现
```

原：

```text
SerialConsole._ser
```

此时可能已经失效。

这种情况下：

```text
wait_for_ready_since()
```

逻辑本身没有问题，但旧 fd 根本收不到 reboot 后的新 RX。

---

## 8.3 必须执行的真机验证

优先执行 TC-RCV-001，并观察：

```bash
dmesg -w
```

或：

```bash
udevadm monitor
```

同时观察：

```bash
ls /dev/ttyUSB*
```

确认 PowerCycle 期间：

- EVB 串口节点是否消失；
- 是否重新枚举；
- 设备名是否变化；
- 原 SerialConsole 是否仍可继续收 RX。

---

## 8.4 两种结果

### 情况 A：串口节点不消失

说明 UART bridge 独立供电。

当前：

```text
fresh-ready cursor
```

方案可以继续使用。

---

### 情况 B：串口节点会消失 / 重枚举

则必须新增框架级恢复 action：

```text
serial_reconnect
```

建议恢复流程调整为：

```text
PowerCycle
    ↓
等待串口 USB re-enumeration
    ↓
重新 detect/open SerialConsole
    ↓
重新挂 BoardHealthMonitor listener
    ↓
board_ready
    ↓
wifi_connect
    ↓
preclean
    ↓
ftp_ready
```

注意：

`serial_reconnect` 应属于：

```text
Scenario / Application runtime restore capability
```

不要放进：

```text
PowerSwitch
```

PowerSwitch 仍只负责上下电。

# 9. QA-GAP-01：缺少专用 Recovery 真机验收 Scenario

## 9.1 当前状态

目前：

```text
normal.yaml
stress.yaml
```

仍未启用：

```text
health_monitor
recovery
```

这是正确的，因为可以保证现有稳定场景不受影响。

但当前也没有一个专用：

```text
recovery_validation.yaml
```

用于正式执行 ADR-016 真机验收。

---

## 9.2 推荐新增

建议增加：

```text
ATS/config/scenarios/recovery_validation.yaml
```

第一阶段不要修改：

```text
normal.yaml
stress.yaml
aging.yaml
```

---

## 9.3 建议场景骨架

例如：

```yaml
scenario:
  name: recovery_validation

  preview:
    enabled: false

  health_monitor:
    enabled: true

  recovery:
    enabled: true
    backend: power_cycle
    max_attempts: 2
    after_recovery: retry_current_task
    on_exhausted: abort_scenario
    restore:
      - board_ready
      - wifi_connect
      - preclean
      - ftp_ready

  prepare:
    - serial_init
    - power_switch_init
    - wifi_connect
    - preclean
    - ftp_ready
    - health_monitor_start

  tasks:
    - module: video
      duration: 180
      override:
        video_resolution: "sd1080p_0"

  cleanup:
    - health_monitor_stop
    - power_switch_close
    - close_serial
```

# 11. 修复时必须保持的架构红线

本轮修复不得破坏以下边界。

## BoardHealthMonitor

仍然：

```text
只监测
不 PowerSwitch
不 health recovery policy
```

---

## RecoveryCoordinator

仍然：

```text
只协调
不生成业务 TestResult
不处理具体 PowerSwitch 协议
```

---

## Runner

负责：

```text
RecoveryOutcome
→ retry / abort / framework TestResult
```

但：

```text
不认识具体硬件
```

---

## PowerSwitch

仍然只负责：

```text
power_on
power_off
reboot
```

禁止加入：

```text
死机判断
retry policy
Scenario logic
```

---

## Scenario

负责：

```text
显式声明生命周期
显式声明 recovery policy
```

不要由框架偷偷自动补：

```text
health_monitor_start
health_monitor_stop
power_switch_init
```

# 13. 最终结论

这一轮不需要推翻 ADR-016，也不需要再次重构 PowerSwitch。

本轮剩余问题主要集中在：

```text
恢复失败结果是否能影响最终退出码
Recovery Policy 是否彻底 fail-closed
Scenario 生命周期是否真实接线
自动测试是否固化
PowerCycle 后串口设备是否重枚举
```

属于**最后的运行闭环和真机落地问题**。

建议完成本文件中的修改后，不再继续扩展新功能，直接进入 ADR-016 真机验收。
