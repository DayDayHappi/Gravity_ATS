# 3. NEW-P0-03：`after_recovery=continue` 与 Runner 语义冲突

## 3.1 当前实现

`RecoveryCoordinator.validate()` 当前允许：

```python
after_recovery in (
    "retry_current_task",
    "continue",
)
```

因此下面配置被认为是合法的：

```yaml
recovery:
  enabled: true
  after_recovery: continue
```

恢复成功后 Coordinator 会返回：

```python
RecoveryOutcome(
    action="continue",
    success=True,
)
```

但是 Runner 当前只显式处理：

```text
abort_scenario
retry_current_task
```

其它 action 全部进入：

```text
unknown RecoveryOutcome.action
→ board_recovery ERROR
→ ScenarioAbort
```

---

## 3.2 实际错误流程

```text
UNRESPONSIVE
    ↓
PowerCycle 成功
    ↓
环境恢复成功
    ↓
RecoveryOutcome(
    action="continue",
    success=True
)
    ↓
Runner 不认识 continue
    ↓
误判 unknown action
    ↓
board_recovery ERROR
    ↓
ScenarioAbort
```

这意味着：

> **恢复已经成功，却因为合法 policy 与 Runner 处理不一致，被当成恢复失败。**

---

## 3.3 推荐修复方案

推荐直接真正支持：

```text
continue
```

在 Runner Outcome 处理逻辑中增加：

```python
if outcome.action == "continue":
    break
```

语义定义：

```text
恢复成功
    ↓
不重跑当前 Task
    ↓
继续执行 Scenario 中下一个 Task
```

完整处理顺序建议固定为：

```text
outcome is None
    → 当前 Task 正常结束

abort_scenario
    → 若失败则记录 board_recovery ERROR
    → ScenarioAbort

retry_current_task
    → 重跑当前 Task
    → 新 Outcome 继续处理

continue
    → 不重跑当前 Task
    → 继续后续 Task

其它未知值
    → board_recovery ERROR
    → ScenarioAbort
```

---

## 3.4 另一种可选方案

如果 ADR-016 第一阶段实际上不需要：

```text
continue
```

则可以更严格：

```python
after_recovery == "retry_current_task"
```

只允许一个枚举值。

但不要保留：

```text
Coordinator 校验允许 continue
Runner 实际不支持 continue
```

这种接口不一致状态。

---

## 3.5 推荐修改文件

```text
ATS/core/runner.py
```

必要时同步：

```text
ATS/application/recovery_coordinator.py
docs/02_design/decision_record/ADR-016-板卡健康监测与可插拔恢复机制.md
docs/01_architecture/interface_spec.md
```

---

## 3.6 验收标准

### Case A

配置：

```yaml
after_recovery: retry_current_task
```

恢复成功后：

```text
当前 Task 重跑
Scenario 继续
```

### Case B

配置：

```yaml
after_recovery: continue
```

恢复成功后：

```text
当前 Task 不重跑
直接进入下一个 Task
不得产生 board_recovery ERROR
不得 ScenarioAbort
```

### Case C

人为构造：

```text
RecoveryOutcome.action="invalid_action"
```

必须：

```text
board_recovery ERROR
ScenarioAbort
exit code = 1
```

# 4. NEW-P0-04：PowerCycle 没有严格验证控制器 OFF / ON 回帧

## 4.1 当前实现

恢复路径：

```text
RecoveryCoordinator
    ↓
PowerCycleBackend.recover()
    ↓
ctx.power_switch.reboot()
```

当前 `PowerSwitch.reboot()`：

```python
self.power_off()
time.sleep(delay)
self.power_on()
```

但是没有检查：

```text
power_off() 返回了什么
power_on() 返回了什么
```

而 `power_off()` / `power_on()` 当前返回：

```text
控制器响应帧 bytes
```

两次读空时也可能返回：

```python
b""
```

---

## 4.2 风险

例如：

```text
power_off()
→ b""

power_on()
→ b""
```

当前 `reboot()` 仍正常返回。

随后 Backend 继续认为：

```text
power cycle 完成
```

更危险的情况是：

```text
OFF 实际失败
    ↓
EVB 根本没有断电
    ↓
board_ready 给原板发回车
    ↓
原板返回新的 msh />
    ↓
fresh-ready PASS
    ↓
ATS 误认为“PowerCycle 恢复成功”
```

也就是说：

> **fresh-ready 只能证明 reboot 后收到了新 RX，不能证明上下电控制器真的执行了 OFF→ON。**

---

## 4.3 推荐修复原则

PowerCycle 恢复必须同时满足：

```text
电源控制链路成功
+
EVB 启动链路成功
```

不能只满足：

```text
EVB 后续还能响应
```

---

## 4.4 推荐方案

### 方案 A：新增严格接口 `reboot_checked()`

在：

```text
ATS/drivers/power_switch.py
```

增加：

```python
def reboot_checked(self, delay=None):
    ...
```

行为：

```text
power_off
    ↓
验证 OFF 回帧
    ↓
delay
    ↓
power_on
    ↓
验证 ON 回帧
    ↓
成功返回
```

失败直接：

```python
raise PowerSwitchError(...)
```

---

## 4.5 OFF 判据建议

至少要求：

```python
commands.is_valid_state_frame(off_resp)
```

是否必须：

```text
state == OFF
```

应依据 ADR-015 真机协议事实决定。

如果当前控制器下电回帧不能稳定保证：

```text
POWER_STATE_OFF
```

则不要凭猜测加强语义。

最低要求：

```text
必须收到合法 4 字节状态帧
```

---

## 4.6 ON 判据建议

ON 应严格要求：

```python
on_resp == commands.POWER_STATE_ON
```

或等价：

```python
commands.is_valid_state_frame(on_resp)
and commands.frame_state(on_resp) == 0x01
```

因为 ADR-015 当前探测控制器本身就以：

```text
POWER_STATE_ON
```

作为明确判据。

---

## 4.7 Backend 调用

`PowerCycleBackend.recover()` 改为调用严格接口：

```python
ps.reboot_checked()
```

而不是：

```python
ps.reboot()
```

原 `reboot()` 可以继续作为普通能力接口保留，避免破坏 ADR-015 已有使用方。

---

## 4.8 验收标准

### Case A：OFF 合法 + ON 合法

```text
recover PASS
继续 board_ready
```

### Case B：OFF 两次都无响应

```text
PowerSwitchError
RecoveryOutcome.success=False
board_recovery ERROR
ScenarioAbort
```

### Case C：ON 返回空

同样必须恢复失败。

### Case D：ON 返回非法帧

必须恢复失败。

### Case E：ON 返回 `POWER_STATE_ON`

才允许继续：

```text
board_ready
```

# 5. NEW-P1-03：`--dry-run` 没有执行 Scenario runtime contract 校验

## 5.1 当前实现

Scenario 生命周期静态校验现在位于：

```python
ScenarioManager.run()
```

内部：

```python
self._validate_scenario_runtime_contract(scenario)
```

但是 CLI：

```bash
python -m ATS.main --scenario xxx --dry-run
```

不会进入：

```text
manager.run()
```

而是：

```text
manager.load()
→ dependency check
→ module register check
→ return 0
```

---

## 5.2 风险

例如：

```yaml
health_monitor:
  enabled: true
```

但忘了：

```yaml
prepare:
  - health_monitor_start
```

正常运行时：

```text
ScenarioError
```

但是 dry-run 可能仍输出：

```text
配置与依赖校验通过
```

这与：

```text
--dry-run = 校验配置和依赖
```

的用户预期不一致。

---

## 5.3 推荐修改

将纯静态 Scenario contract 校验从 `run()` 中抽出来，例如：

```python
def validate_scenario(self, scenario):
    self._validate_scenario_runtime_contract(scenario)
```

然后：

### 正常运行

```text
load
→ validate_scenario
→ run
```

### dry-run

```text
load
→ validate_scenario
→ dependency check
→ module check
→ PASS
```

---

## 5.4 注意边界

dry-run 只负责静态校验：

```text
health_monitor_start/stop 是否存在
power_switch_init 是否存在
action 顺序是否正确
health_monitor/recovery 配置关系是否合法
```

不要在 dry-run 做：

```text
实际串口探测
实际 PowerSwitch 探测
实际 WiFi
实际 health_check
```

这些仍属于运行时环境验证。

---

## 5.5 验收标准

以下配置执行：

```bash
python -m ATS.main --scenario bad_case --dry-run
```

必须失败：

### Case A

```text
health_monitor.enabled=true
prepare 缺 health_monitor_start
```

### Case B

```text
cleanup 缺 health_monitor_stop
```

### Case C

```text
backend=power_cycle
prepare 缺 power_switch_init
```

### Case D

```text
power_switch_init 排在 health_monitor_start 后
```

应：

```text
exit code = 2
```

# 6. HW-RISK-01：PowerCycle 后 EVB UART 是否 USB 重枚举

## 6.1 当前假设

当前 Recovery 仍假设：

```text
PowerCycle 前的 SerialConsole
    ↓
Power OFF
    ↓
Power ON
    ↓
原 pyserial fd 继续有效
```

然后：

```text
wait_for_ready_since(cursor)
```

等待 reboot 后新 RX。

---

## 6.2 该问题无法仅靠源码判断

是否需要：

```text
serial_reconnect
```

取决于实际硬件连接方式：

### 情况 A

USB-UART 芯片由 PC/USB 独立供电：

```text
EVB Power OFF
USB serial 节点不消失
```

那么当前方案可行。

### 情况 B

USB-UART 随 EVB 电源一起掉：

```text
/dev/ttyUSBx 消失
Power ON 后重新枚举
```

那么旧：

```text
SerialConsole._ser
```

很可能失效。

---

## 6.3 真机验证要求

执行 TC-RCV-001 时同时观察：

```bash
dmesg -w
```

或：

```bash
udevadm monitor
```

以及：

```bash
watch -n 0.2 'ls -l /dev/ttyUSB* /dev/ttyACM* 2>/dev/null'
```

重点确认：

- OFF 时设备节点是否消失；
- ON 时是否重新枚举；
- 设备名是否变化；
- 原 SerialConsole 是否还能继续读取；
- reader thread 是否出现 pyserial 异常。

---

## 6.4 如果发生重枚举

需新增：

```text
serial_reconnect
```

恢复流程变为：

```text
PowerCycle
    ↓
等待 USB re-enumeration
    ↓
重新 detect/open SerialConsole
    ↓
重新绑定 BoardHealthMonitor listener
    ↓
board_ready
    ↓
wifi_connect
    ↓
preclean
    ↓
ftp_ready
```

注意：

```text
serial_reconnect
```

不能放入：

```text
PowerSwitch
```

PowerSwitch 仍只负责上下电。
