# 修复 serial.log 中同一命令 TX 时间戳晚于 RX 的假象

**日期**: 2026-08-20
**改动范围**: `core/serial_console.py`（`_write_cmd` 的 TX 日志打印位置前移）

---

## 一、问题描述

查看 `logs/<ts>/serial.log` 时，`rtmp_video_start` 这类长命令的 **TX 时间戳晚于 RX 时间戳**，
例如：

```
[22:46:56.027] RX< rtmp_video_start rtmp://192.168.1.89/live/cam   ← 板子回显
[22:46:56.027] RX< [7] [cam] ...摄像头初始化海量日志...
...
[22:46:56.087] TX> rtmp_video_start rtmp://192.168.1.89/live/cam   ← TX 反而晚 60ms
[22:46:56.087] TX> echo "__EVBTEST_END_d9f55a4b__"
```

TX 比 RX 晚约几十~几百毫秒，看起来像"先收到命令再发送"，很不合理。

## 二、根因分析

不是发送顺序真颠倒，而是 **TX 日志的打印位置在分片循环之后**，导致 TX 时间戳被标成
"最后一片写完"的时刻；而 RX 是读线程实时记录的"板子回显"时刻。

`_write_cmd()`（分片写入，见 [[20260817_0115_RTMP命令串口溢出丢字节_长命令分片写入修复]]）
里，`logger.log_serial("TX>", ...)` 原本写在 `for` 分片循环**之后**：

```python
data = (f'{cmd}\necho "{sentinel}"\n').encode("utf-8")
for i in range(0, len(data), _WRITE_CHUNK_BYTES):
    ... self._ser.write(chunk); self._ser.flush()
    time.sleep(_WRITE_CHUNK_DELAY)   # 每片后 sleep 0.1s
logger.log_serial("TX>", ...)        # ← 全部写完才记 TX
```

`rtmp_video_start <url>`（45B）+ 换行 + echo 哨兵（33B）共约 **78 字节**，按 32 字节分片
需 **3 片**、片间 `sleep(0.1)` **2 次**。因此 TX 时间戳 = "第 3 片写完"时刻，比"第 1 片真正
发出"晚了约 200ms（含调度抖动）。而板子 msh 是**逐字节 local echo**，收到第一片就开始
回显，读线程立刻记 RX。于是 RX（=发送开始）反而早于 TX（=发送完成）。

命令越长、分片越多，时差越大（实测 37ms~299ms）。这是 [[20260817_0115_RTMP命令串口溢出丢字节_长命令分片写入修复]]
分片改造时，为"日志仍记录完整命令"而把 `log_serial` 原样留在循环后（沿用旧 `_write`
"先 write 后记日志"的惯性写法），未意识到分片 sleep 会让 TX 时间戳后移到发送完成时刻。

## 三、修复内容

`core/serial_console.py` `_write_cmd()`：把 `logger.log_serial("TX>", ...)` **移到分片循环之前**，
使 TX 时间戳记为"开始发送"时刻，与 RX 的"实时接收"语义对齐。

```python
if self._ser is None:
    raise SerialError("串口未打开")
logger.log_serial("TX>", f'{cmd}\necho "{sentinel}"')   # ← 先记 TX（开始发送）
data = (f'{cmd}\necho "{sentinel}"\n').encode("utf-8")
for i in range(0, len(data), _WRITE_CHUNK_BYTES):
    chunk = data[i:i + _WRITE_CHUNK_BYTES]
    with self._lock:
        self._ser.write(chunk)
        self._ser.flush()
    time.sleep(_WRITE_CHUNK_DELAY)
```

## 四、验证结果

- `python3 -m py_compile ATS/core/serial_console.py` 语法检查通过。
- **待真机验证**：跑一次含 rtmp 的测试，看 serial.log 里 `rtmp_video_start` 的 TX 时间戳应
  早于（或等于）RX，不再倒挂。

## 五、还会再有吗

- 仅改日志打印时机，不改变分片发送行为本身（片数、片间延时、溢出防护均不变）。
- TX 与 RX 时间戳今后反映的是"发送开始 vs 板子回显"两个真实时间点，TX 仍可能略早于 RX
  （正常，发送在前、回显在后），不会再出现"发送完成"假象。

## 六、经验沉淀

- **日志时间戳的语义要和事件本身对齐**：记录"发送"应记"开始发送"而非"发送完成"，
  否则分片/重试等把动作拉长的场景会让日志时序失真，误导排查。
- 改"先 write 后记日志"这类惯性写法时，要检查它在新增的分片/延时路径下是否还成立。
