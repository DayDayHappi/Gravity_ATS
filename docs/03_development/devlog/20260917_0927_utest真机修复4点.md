# 20260917_0927_utest真机修复4点

## 问题描述

utest 场景真机跑出 4 个问题：

1. `pvt_auto_test` 哨兵超时（脚本超时 10s 偏紧，实际跑约 10.2s）。
2. `utest.py` 哨兵超时后，即使 result 行已出现且状态为白名单 PASSED，也被误报「未知状态」。
3. 场景应去掉 `qspi_test`（9 项 → 8 项）。
4. 日志打印冗余「脚本超时 {timeout}s」，干扰判读。

## 根因分析

1. `pvt_auto_test` 固件 `[run timeout]` 标 1s，但真机实测约 10.2s，脚本 10s 超时卡线，提为 20s（与 i2c 组对齐）。
2. 原判据逻辑：`exec_sync` 哨兵超时（`r.success=False`）后**直接**进「ANY_RE 宽松重判」，但白名单 `UTEST_RESULT_RE` 才匹配 PASSED 等合法状态；哨兵超时只是命令跑得慢，result 行已出现即业务已完成，应先白名单重判。
3. `qspi_test` 本期不测，场景移除 task（`UTEST_TESTCASES` 映射保留，方便未来加回）。
4. 日志打印删减。

## 修复内容

- `ATS/drivers/utest_commands.py`：`UTEST_TESTCASES["pvt_auto_test"]` 10.0 → 20.0（保留 qspi_test 映射）。
- `ATS/modules/utest.py`：
  - L46 `logger.step` 去掉「（脚本超时 {timeout:g}s）」，只留 `utest: {testcase}`。
  - 判据重排：`exec_sync` 成功 → 走状态映射；失败（哨兵超时/无 result 行）→ **先用白名单 `UTEST_RESULT_RE` 对 r.clean 重判**，命中则按 status 出 PASS/FAIL/ERROR/SKIP；命中不了才走「ANY_RE 未知状态 → ERROR / 无 result 行 → FAIL」。
  - 抽 `_mk_from_status()` 复用状态映射（成功路径与白名单重判路径共用）。
  - docstring「9 个」→「多个」。
- `ATS/config/scenarios/utest.yaml`：删除 qspi_test task（9 → 8 项）；头注释「9 项」→「8 项」。

## 验证结果

- `py_compile` 通过；`--scenario utest --dry-run` 通过；场景解析 8 项（qspi_test 已移除）。
- 判据修正单测（模拟哨兵超时 `success=False` 的 4 分支 + 正常路径）：
  - 哨兵超时 + PASSED result 行 → **PASS**（原误报「未知」，已修复）。
  - 哨兵超时 + FAILED result 行 → FAIL。
  - 哨兵超时 + PANIC（非白名单）→ ERROR。
  - 哨兵超时 + 无 result 行 → FAIL。
  - 正常 PASSED → PASS。
- 超时映射：pvt_auto_test=20.0、pvt_test=10.0、qspi_test 保留=20.0。

## 还会再有吗

- 待真机重跑 utest 场景验证 8 项全 PASS。
- 若未来固件其他 testcase 标称 run timeout 与实际偏差，同样需在 `UTEST_TESTCASES` 单独调脚本超时。

## 经验沉淀

- 同步阻塞命令「哨兵超时」≠「业务失败」：result 行是业务完成标志，哨兵只定界；result 行已出现时即使哨兵超时也应先按白名单状态出结果，不要直接落入未知/失败兜底。
- 标称 run timeout（固件自述）与脚本等待值解耦：脚本超时 = 固件 run timeout + 实测余量，以真机为准单独调。
