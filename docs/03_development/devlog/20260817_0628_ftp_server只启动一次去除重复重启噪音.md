# ftp_server 全程只启动一次，去除重复重启噪音；wifi join 后加 5s 稳定等待

**日期**: 2026-08-17
**改动范围**: `main.py`（预清理去掉 ftp_server 恢复 + wifi 连接成功后加 sleep(5)）、`modules/wifi.py`（wifi_join 连接成功后加 sleep(5)）、`modules/ftp.py`（`ensure_ftp` 不再重发 ftp_server，只重连 PC 端客户端）

---

## 一、问题描述

当前全部测试用例都能 PASS，但运行日志中打印了大量 `service go wrong, now wait restarting...`，干扰问题定位（排查其他问题时很难在刷屏里找到有效信息）。

## 二、根因分析

排查发现全流程中 `ftp_server` 命令被发送了不止一次：

1. `main.py` 预清理阶段（wifi 连接**之前**）主动发一次 `ftp_server`，试图"恢复"可能残留的崩溃循环——但此时板子可能还没联网，这次发送对本轮测试无意义。
2. `ftp` 模块 `FtpModule.run()` 在 wifi 连接后正式发一次 `ftp_server`（这次是必要的，唯一应该保留的）。
3. `photo`/`video` 模块每次拍照/录像后都调用 `ensure_ftp(ctx, console, force=True)`，而 `ensure_ftp` 内部在 `force=True` 时会**再重发一次 `ftp_server`** 来"恢复"服务。

三处叠加，一次完整测试跑下来 `ftp_server` 可能被发送 5～10 次以上。而根据此前 [[20260817_0309_rtmp移除ftp_server前置压制]] 的经验沉淀：固件的 "service go wrong" 本身就是崩溃循环重启的表现，脚本每多发一次 `ftp_server`，就是往循环里再喂一次重启触发，新建线程、旧线程 suspend 不回收，刷屏日志随之成倍增加。

即便当前测试仍能全部 PASS（因为 photo/video 用 FTP 下载有重试兜底、rtmp 已不依赖 FTP），重复发送本身没有必要，且是刷屏噪音的直接来源。

## 三、修复内容

1. **`main.py`**：预清理阶段删除 `console.exec_sync("ftp_server", ...)` + `time.sleep(1.0)`，替换为注释说明。
2. **`modules/ftp.py`** `ensure_ftp()`：去掉重发 `ftp_server` 的分支，force/非 force 都只做「测试现有 PC 端连接是否存活 → 不存活则关闭旧连接、重新 `FtpClient().connect()`」，不再触碰 EVB 端服务。文档字符串同步更新。
3. **`main.py` `interactive_wifi()`** 和 **`modules/wifi.py` `WifiJoinModule.run()`**：wifi join 成功获取 IP 后各加 `time.sleep(5.0)`，等板子网络/服务状态稳定后再发下一条命令（`wifi.py` 相应补上 `import time`）。

修改后全仓库搜索 `ftp_server`，唯一实际发送点只剩 `modules/ftp.py` 的 `FtpModule.run()`。

## 四、验证结果

- `ast.parse` 语法检查三个改动文件均 OK。
- **待真机验证**：跑一次完整流程（含 photo/video 多次调用 `ensure_ftp(force=True)`），确认日志中 `service go wrong` 只在必要时出现（甚至不出现，因为不再主动触发），且 photo/video/ftp 用例仍 PASS。

## 五、还会再有吗（残留风险）

1. 固件 FTP 服务在重负载后仍可能**自发**崩溃重启（这是固件 bug，非脚本触发），届时日志里仍可能看到一次 `service go wrong`，但不会再被脚本人为放大成多次。
2. 若后续某模块又新增了 `ensure_ftp(force=True)` 之类"重连恢复"的调用点，只要不在 `ensure_ftp` 内部重新加回 `ftp_server` 发送，就不会引入新的重复触发点——这是本次修复的关键约束，未来改动需留意别破坏它。

## 六、经验沉淀

1. **"确保可用"和"重启服务"要分开**：`ensure_ftp` 原意是"确保 FTP 客户端可用"，却顺手把"重启 EVB 端服务"也绑在了里面，导致每次调用方只是想"重连一下"，却意外触发了服务重启。接口设计上，PC 端客户端重连和 EVB 端服务重启应该是两个独立操作，只应在真正需要时才做后者。
2. **重复触发点要一次性全仓库搜索排查**：单独修一个模块（如之前修 rtmp）不够，同一命令可能在预清理、正式模块、辅助函数三处都有发送，需要 `grep -rn` 全局确认只剩一个必要发送点。
3. 与 [[20260817_0309_rtmp移除ftp_server前置压制]] 的经验一致：固件崩溃循环下，任何"再发一次"的恢复动作都可能是火上浇油，脚本侧应尽量减少不必要的主动触发。
