# 板卡健康监测与可插拔恢复机制实施（ADR-016）

## 问题描述

ADR-016（Document Agent 定稿）要求新增 Scenario 生命周期级 EVB 健康监测与恢复机制：
在 stress/aging 长时间场景识别 EVB 运行期失去响应，按策略执行恢复（power cycle），
恢复后环境重新收敛、测试流程恢复或终止。完整链路：检测 → 确认 → 恢复决策 → 恢复执行 →
环境重新收敛 → 流程恢复/终止。全部能力默认关闭，向后兼容。

## 实施内容（Phase 1~5 全部落地，Level 3 系统边界变更但 ADR 已定稿）

### 新增 ATS/application/ 包（跨模块系统级协调）

- `__init__.py`：应用服务层定位说明 + 职责分离红线。
- `board_health_monitor.py`（Phase 1）：`BoardHealthMonitor` + `HealthEvent`；
  状态机 `HEALTHY → SUSPECTED → UNRESPONSIVE`；listener `on_rx` 只更新时间戳（禁止阻塞）；
  主动 probe 复用 `console.health_check()` 由 Runner 在安全点调用；证据留痕 `pop_events`。
  **不认识 PowerSwitch**。
- `recovery_coordinator.py`（Phase 2~4）：`RecoveryCoordinator` 状态机
  `IDLE→REQUESTED→RECOVERING→RECONCILING→HEALTHY/FAILED`；`recovery_in_progress` 互斥；
  max_attempts 上限 → on_exhausted；复用 prepare action 恢复环境；恢复历史写
  `ctx.recovery_history` + `recovery.log`（不被 PASS 覆盖）。**不认识具体硬件**。
- `recovery_backends/`（Phase 2）：`base.py`（`RecoveryBackend` 抽象 + `register_backend` +
  `RecoveryBackendUnavailable`）+ `power_cycle.py`（映射 `ctx.power_switch.reboot()`）。
- `runtime_control.py`（Phase 5）：全局恢复请求标志 + `wait()` 分段 sleep
  （cooperative cancellation）。

### 修改

- `core/logger.py`：新增 `log_recovery()` + `_RECOVERY_FP`（recovery.log 懒加载），close 补关闭。
- `core/context.py`：新增 `invalidate_board_runtime_state()`（只清板端状态，保留
  system_config/console/power_switch 等）+ `recovery_history` 约定。
- `core/scenario.py`：`Scenario` 增 `health_monitor`/`recovery` 字段。
- `core/scenario_manager.py`：parse 透传策略；新增 `board_ready`（复用 wait_for_ready +
  health_check）、`health_monitor_start`/`health_monitor_stop` 动作；ctx 透传策略。
- `core/runner.py`：`_recovery_checkpoint`（Task 后检查健康，SUSPECTED 安全点 probe，
  UNRESPONSIVE 交 Coordinator）；retry_current_task / abort_scenario 策略接线。
- `core/reporter.py`：`recovery_events` 增量输出（result.json）。
- `main.py`：reporter 传 recovery_events。
- `modules/video.py`：两处长录像 `time.sleep(duration)` 改 `runtime_control.wait()`
  （Phase 5 cooperative cancellation）。
- 新增 `config/modules/board_health.yaml`（Monitor 参数）。

### 红线遵守

- Monitor 不认识 PowerSwitch；Module 不认识 Recovery；Runner 不认识具体硬件；PowerSwitch 不认识 Monitor。
- listener 内禁止 sleep/exec_sync/exec_async/PowerSwitch/FTP/网络 IO（`on_rx` 只更新时间戳）。
- backend 不可用报 `RecoveryBackendUnavailable`，禁止静默 fallback。
- PowerCycle 后失效板端 ctx 状态；恢复事件不被 PASS 覆盖；全部能力默认关闭。

## 验证结果（离线）

- `py_compile` / `compileall ATS/` 通过；全包 import + 模块注册正常（含 video runtime_control 接线）。
- Monitor 状态机（mock）：HEALTHY→SUSPECTED（超时）→probe 成功回 HEALTHY（不误判）→
  probe 连续失败 2 次→UNRESPONSIVE；mark_healthy 回 HEALTHY；SUSPECTED/UNRESPONSIVE 置位恢复请求。
- Coordinator：backend 不可用 → 明确报 backend_unavailable（不静默降级）；backend 可用 +
  restore 成功 → retry_current_task；超 max_attempts → abort_scenario（禁止无限重启）；
  PowerCycle 后 ctx 板端状态失效（ftp_client/evb_ip/wifi_ready/skip_wifi 清空，保留 system_config/console/power_switch）。
- 向后兼容：旧场景默认 health_monitor/recovery 为空；enabled=false 时 health_monitor_start/stop
  零副作用；monitor 关闭时 recovery 不启用。
- runtime_control.wait：无中断正常等待返回 False；收到恢复请求提前返回 True。

**待真机**：TC-BH-001~003 + TC-RCV-001~005（见 ADR-016 Acceptance Criteria）。
`inactivity_timeout` 默认值（60s）需真实 stress 日志校准。

## 还会再有吗

- 第一阶段 Scope 只处理「Scenario 已启动后运行期故障」，不解决「ATS 启动时 EVB 已死」
  （ADR-016 明确：需单独后续 ADR）。
- `board_ready` 复用 wait_for_ready + health_check，不重新 serial_init；若真机发现 Power Cycle
  导致 USB 串口重新枚举，需独立扩展 `serial_reconnect`（不提前假设）。
- `inactivity_timeout`/`confirm_failures` 默认值需真机校准；RTMP 业务故障（heartbeat timeout 但
  shell health_check PASS）只判 RTMP FAIL、禁止 PowerCycle（逻辑已隔离，待真机 TC-RCV-003 验证）。

## 经验沉淀

- Detection/Decision/Execution 三层分离（Monitor 监测 / Coordinator 协调 / Backend 适配 /
  PowerSwitch 执行），替换电源机制无需改动 Monitor/Runner/业务模块。
- Monitor listener 必须极轻量（读线程同步回调，禁止阻塞），主动 probe 移到 Runner 安全点，
  避免「检测逻辑本身放大无响应」。
- 恢复事件独立留痕（recovery_history + recovery.log），不能被 retry 后的 PASS 覆盖——问题
  可审计性是自动化可靠性底线。
- 协作式取消（runtime_control）让长等待 Task 在恢复请求时提前让位，无需业务模块认识 recovery。
