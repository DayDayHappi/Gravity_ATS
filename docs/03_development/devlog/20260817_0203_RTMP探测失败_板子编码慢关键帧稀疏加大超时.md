# RTMP 探测失败：板子编码慢导致关键帧稀疏，加大 ffprobe 超时

**日期**: 2026-08-17
**改动范围**: `drivers/rtmp_receiver.py`（probe 探测参数与默认超时）+ `modules/rtmp.py`（重试次数/间隔）

---

## 一、问题描述

连续两次真机测试 rtmp FAIL：`ffprobe 退出码 1: Input/output error`（或 `探测超时`）。但板子其实**成功推流了**——serial.log 明确有 `[RTMP] publish ready ... Push Start`。

## 二、根因分析

### 2.1 板子推流成功，但编码极慢、关键帧(IDR)稀疏

serial.log 关键证据：

```
[RTMP] slow send frame 601 len=91766 dt=3030ms (IDR)   ← 第 601 帧才是关键帧
[RTMP] dropped 540 p-frames (backlog 96%)              ← 540 个 P 帧全丢
[ringbuf] no space ... RINGBUF: write fail              ← VPU 编码输出缓冲溢出
```

板子推的是 **1080p = 1296×2304**（`cam_set video 1080p` 实测确认），大分辨率编码本就吃力；photo/video 之后固件 FTP 陷入 `service go wrong` 崩溃循环刷屏，疯狂抢 CPU；结果编码速度骤降，**关键帧从正常「30 帧一个」退化到「600 帧一个、隔 57 秒才来一个」**。

### 2.2 为什么 ffprobe 失败

ffprobe 连上 nginx 后必须等到一个 IDR 才能解码出流信息。但原探测参数 `-rw_timeout 3s` 太短，等不到 IDR → `Input/output error`。ffplay 同理，`nan fd=0` 一帧没解出来。

### 2.3 为什么之前成功过

对比 01:30 成功那次：IDR 间隔才 30 帧、板子编码流畅，ffprobe 几秒就探测到。失败是板子负载重（FTP 刷屏 + 大分辨率编码慢），脚本探测超时对「慢流」不够鲁棒。

### 2.4 实验验证

- `cam_set` 支持 `[gop:0-1000]` 参数，但实测设 `gop=30` 后，板子在 FTP 刷屏状态下 8 秒仍只出 1 个 IDR（单帧 2.7 秒发完）——编码慢是主因，gop 救不了。
- 板子分辨率只支持 `4k`/`1080p` 两档，1080p 已是最低，无法再降。

## 三、修复内容

`drivers/rtmp_receiver.py` 的 `probe()`：

| 参数 | 原值 | 新值 | 说明 |
|------|------|------|------|
| `-rw_timeout` | 3s | 15s | 放宽读超时，等稀疏的 IDR |
| `-analyzeduration` | 2s | 10s | 放宽分析窗口 |
| `-probesize` | 1MB | 3MB | 容忍大 IDR（可达 100KB） |
| 外层 `timeout` | 15s | 45s | subprocess 双保险 |

`modules/rtmp.py` 的 `probe()` 调用：`attempts=4, interval=2.0` → `attempts=5, interval=3.0`。

代价：无流/拥塞时单次探测最多等 45s、重试 5 次，rtmp 项最坏约 3 分钟。但正常（板子不拥塞）时首次探测几秒即成功，几乎不受影响。

## 四、验证结果

- `ast.parse` 语法 OK。
- **待真机验证**：跑 `python3 -m ATS.main --no-interactive-wifi`，rtmp 项应 PASS（板子拥塞时可能耗时较长）。

## 五、还会再有吗（残留风险）

1. **治标未治本**：加大超时只是让 ffprobe 耐心等，未解决「板子编码慢」的根因。若板子严重拥塞（FTP 刷屏最猛时 IDR 间隔 57s），45s 单次超时仍可能不够。
2. **FTP 崩溃刷屏是主因之一，未排查**：photo/video 后固件 FTP 持续 `service go wrong` 抢 CPU，是编码慢的重要诱因。后续应单独排查（为何崩溃、如何彻底压制），可大幅缩短 IDR 间隔。
3. **测试时长波动**：rtmp 项耗时会随板子负载在 10s~3min 间波动，无人值守时需容忍。

## 六、经验沉淀

1. **「推流成功」≠「探测能成功」**：RTMP 推流拓扑里，服务端收到 publish 只代表连接建立，真正影响拉流端能否解码的是关键帧(IDR)是否及时到达。排查探测失败要先看推流端的帧发送日志（slow send/dropped/IDR 间隔），而不是只盯着拉流端报错。
2. **大分辨率 + 弱编码器的关键帧稀疏是 RTMP 固有陷阱**：1080p 竖屏（1296×2304）在板端编码吃力，IDR 间隔被拉长到几十秒，任何依赖「首帧/关键帧到达」的探测都要给足超时。不要用 640×480 的经验值（几秒）去套大分辨率。
3. **探测超时的设置要区分「无流」和「慢流」**：`-rw_timeout` 短（3s）适合快速判定「无流」，但会误杀「有流但 IDR 稀疏」；拉长后无流场景变慢，需外层 subprocess timeout + 重试双保险。两难权衡，用「无流场景由 check_ready/推流命令成功性保证 + 慢流场景拉长超时」折中。
4. **板端负载（FTP 刷屏）会显著影响编码速度**：同一分辨率同一命令，板子空闲时 IDR 30 帧一个、拥塞时 600 帧一个。排查编码/推流问题时先看板端有无异常刷屏抢 CPU。见 [[rtmp-ffmpeg-bundled]]、[[ats-changelog-rule]]。
