## 第一部分：实现的模块与实现方式

### 1. 项目整体架构

采用**分层 + 注册**的解耦架构，确保测试项可随时增删改而不牵动核心：

```
ATS/
├── main.py                # 入口：CLI、串口探测、WiFi 交互、板子预清理、调度
├── config/test_config.yaml # 数据驱动配置
├── core/                  # 框架核心（稳定，加用例不改这里）
│   ├── ansi.py            # ANSI 转义剥离
│   ├── logger.py          # 常驻读线程全量日志
│   ├── context.py         # 跨模块共享上下文
│   ├── config.py          # YAML 加载 + ${ENV} 替换 + schema 校验
│   ├── result.py          # Response/TestResult 数据结构
│   ├── serial_console.py  # 串口：哨兵机制 + 自动探测 + 波特率回退
│   ├── runner.py          # 拓扑排序 + 执行 + 重试 + fail-fast
│   └── reporter.py        # JSON + JUnit + HTML 报告
├── modules/               # 功能模块（每模块一文件，@register 注册）
│   ├── base.py            # TestModule 基类 + 注册装饰器
│   ├── wifi.py emmc.py ftp.py photo.py video.py rtmp.py
└── drivers/               # PC 端辅助
    ├── ftp_client.py      # ftplib 封装
    └── rtmp_receiver.py   # ffmpeg 拉流 + ffprobe 验证
```

**使用的 Python 库**：

| 库 | 用途 | 来源 |
|----|------|------|
| `pyserial` | 串口通信 | pip install |
| `pyyaml` | 配置文件解析 | 系统自带 |
| `jinja2` | HTML 报告模板 | 系统自带 |
| `ftplib` | FTP 客户端 | Python 标准库 |
| `subprocess` | 启停 ffmpeg | Python 标准库 |
| `argparse` | CLI 解析 | Python 标准库 |
| `ffmpeg`/`ffprobe` | RTMP 拉流验证（待测） | 需 apt install |

### 2. 测试流程顺序与各模块实现

最终测试链路（顺序固定）：

```
WiFi(scan+join) → eMMC → FTP服务器 → 拍照 → 录像 → RTMP推流
```

按这个顺序，各模块的实现方式如下。

#### 2.1 串口通信层（core/serial_console.py）—— 最关键的基础

这是整个项目的地基，也是耗时最多的部分。

**实现方式**：

1. **自动探测串口**：枚举 `/dev/ttyUSB*` 和 `/dev/ttyACM*`，对每个端口 × 候选波特率 `[2000000, 250000, 115200, 921600]` 组合，发送 `\n` 后读取 2 秒输出，用 EVB 指纹正则（`JX009`、`msh />`、`Some IC design company.cn Build`）匹配，命中即为 EVB。多个匹配则交互让用户选。

2. **常驻读线程**：打开串口后启动一个后台线程，持续把串口字节写入 `logs/<时间戳>/serial.log`（带毫秒时间戳、保留 ANSI 原始字节），同时喂进一个 `deque` 环形缓冲。这样异步后台日志（如 WiFi 连接中的 `[I/WLAN...]`）不会丢失，命令匹配从缓冲截取。

3. **哨兵机制定界命令结束**：msh 的提示符 `msh />` 会被后台日志打碎粘连（实测 `msh />[32m...`、`msh />wifi scan`），不能靠等提示符判断命令结束。方案是发命令时附加 `echo "TOKEN"`，等 TOKEN 出现即定界。

4. **命令分类执行**：
   - `exec_sync`：同步命令（wifi scan、cd、ftp_server），哨兵定界 + 正则判定
   - `exec_async`：异步命令（wifi join、拍照、录像），发命令后直接等期望正则（不依赖哨兵，因这些命令输出海量日志会打乱哨兵）

5. **ANSI 剥离**：EVB 输出带大量颜色码 `\x1b[32m...\x1b[0m`，正则匹配前用 `re.sub(r"\x1b\[[0-9;]*[A-Za-z]", "", text)` 剥离。

6. **就绪检测**：打开后主动发 `\n` 唤醒 shell，匹配 `FW start ok` 或 `msh />` / `msh /xxx>` 提示符。

#### 2.2 WiFi 模块（modules/wifi.py）

**实现方式**：
- `wifi_scan`：`exec_sync("wifi scan")`，正则匹配表头 `SSID\s+MAC\s+security\s+rssi\s+chn\s+Mbps` + 数据行解析 AP 列表，RSSI < -70 警告
- `wifi_join`：`exec_async("wifi join <ssid> <pwd>", expect=r"Got IP address\s*:\s*([0-9.]+)")`，异步等待拿到 IP（实测约 9 秒），提取 IP 存入 `ctx.evb_ip` 供后续模块用
- **交互式连接**：启动时提示是否连默认 WiFi（G-Demo/Gdemo@123），否则扫描列 AP 让用户选并输密码。连上后 wifi 用例 SKIP

**关键正则**（对齐实测字节）：`Got IP address\s*:\s*([0-9.]+)`，注意"address"和":"之间有空格，冒号后也有空格。

#### 2.3 eMMC 模块（modules/emmc.py）

**实现方式**：实测板子上电已自动挂载 `/emmc`（启动日志 `sd mount to /emmc/ is successful`），故默认只执行 `cd emmc` 验证可进入目录，不做 mkfs/mount（避免冲突）。`--format` 参数才触发格式化。

#### 2.4 FTP 模块（modules/ftp.py + drivers/ftp_client.py）

这是第二个耗时大头，固件 FTP 服务有严重限制。

**实现方式**：
1. 串口发 `ftp_server`，等 `Ftp server init success`
2. PC 端用 `ftplib.FTP` 连接 `evb_ip:21`（loogg/loogg），带重试
3. 验证列 `/emmc` 目录
4. 把已连接的 `ftp_client` 存入 `ctx`，供 photo/video 复用
5. **`ensure_ftp(force=True)`**：拍照/录像后 FTP 会崩，强制重发 `ftp_server` + 重连

**FtpClient 关键设计**：
- 主动模式（`pasv=False`），该 FTP 不支持 PASV
- `list_files` 用 `LIST` 命令解析（不支持 NLST），且必须先 `CWD` 再无参 `LIST`（`LIST <path>` 会忽略路径）
- `size` 用 LIST 父目录解析（不支持 SIZE 命令）
- `download` 用 `retrbinary` 二进制下载，保证照片/视频字节完整

#### 2.5 拍照模块（modules/photo.py）

**实现方式**：
1. `cam_set photo <mode>` 切模式 + 稳定延时
2. `dfs_capture_start`，用 `exec_async` 等串口成功标志 `Save Photo Successful:\s*(\S+)`，直接解析保存路径（如 `/emmc/PIC/20260812_111522_6722/`）
3. **FTP 下载验证（辅助）**：`ensure_ftp(force=True)` 强制重连，列新目录里的 jpg 文件，下载第一个到 `logs/<时间戳>/photos/`，验证 JPEG 头 `FF D8 FF` + 大小 > 10KB
4. 拍照失败只标记该模式 FAIL，继续下一个模式，不影响后续录像/推流

**实测文件结构**（与手册不同）：`/emmc/PIC/<时间戳目录>/Image_<时间戳>_<序号>.jpg`，auto 模式生成多个 jpg。

#### 2.6 录像模块（modules/video.py）

**实现方式**：
1. `cam_set video 1080p`
2. `dfs_video_start`（`exec_async` 等 `Record Start`）
3. `sleep(录像时长)`
4. `dfs_video_stop`（`exec_async` 等 `Save Video Successful:\s*(\S+)`），解析视频路径
5. **FTP 大小校验（辅助）**：`ensure_ftp(force=True)` 后用 `ftp.size(video_path)` 校验 > 100KB

**实测文件结构**：`/emmc/VIDEO/<时间戳目录>/Video_<序号>_0.h265` + `Imu_<序号>.bin`

#### 2.7 RTMP 模块（modules/rtmp.py）—— 待测

**实现方式**（已编码，未真机验证）：
- `setup`：自动检测 PC IP（取与 EVB 同网段的本机接口），启动 `RtmpReceiver`
- `run`：`rtmp_video_start rtmp://<pc_ip>/live/cam1` → 等推流时长 → `RtmpReceiver.verify()`（ffprobe 验证流可解码）→ `rtmp_video_stop`
- ffmpeg 拉流带 `-reconnect` 重连参数，容忍 EVB 推流稍晚启动
- 无 ffprobe 时降级为 `ffmpeg -i` 解析或仅校验文件大小

**未测原因**：PC 未装 ffmpeg 二进制（网络认证问题，apt/pip 都连不上）。

### 3. 报告与日志

每次运行生成时间戳子目录：
- `reports/<时间戳>/`：`result.json`（机器可读）、`junit.xml`（CI 集成）、`report.html`（人可读，jinja2 渲染）
- `logs/<时间戳>/`：`serial.log`（全量串口字节）、`run.log`（框架日志）、`photos/`（下载的照片）、`videos/`

退出码：0 全过 / 1 有失败 / 2 环境配置错。

## 第二部分：开发过程中遇到的问题与解决

### 问题 1：哨兵机制失效——msh 不支持 `;` 分隔命令（耗时最多）

**这是整个开发中耗时最多的一个问题**，从发现到彻底解决，反复调试了约 1.5 小时。

**设计阶段假设**：用 `cmd; echo <TOKEN>` 作为命令定界，等 TOKEN 出现即认为命令结束。这是标准 shell 的做法。

**真机实测打脸**：
1. 第一次 `health_check` 发 `echo EVBTEST_HELLO`，返回 `Usage: echo "string" [filename]`——echo 不带引号会报用法错误
2. 改成 `echo "EVBTEST_HELLO"` 后，单独 echo 正常
3. 但 `cmd; echo "TOKEN"` 里的 `;` 不工作——这个 msh **不支持 `;` 分隔命令**，`echo "A"; echo "B"` 被 echo 当成单个参数，报 Usage

**解决过程**：
- 先发现是 `;` 的问题（测试 `echo "A"; echo "B"` vs `echo "A"\necho "B"`）
- 改用**换行分隔**：发 `cmd\necho "TOKEN"`，两条命令分两行，msh 顺序执行
- 这又引出第二个问题：哨兵 TOKEN 会出现在两处——命令回显行 `cmd\necho "TOKEN"` 和 echo 的真正输出 `TOKEN`。最初用 `find(TOKEN)` 会命中回显行，导致响应被截断成空
- 最终改成**行首哨兵匹配**：正则 `(?:^|\n)TOKEN`，只匹配行首的 TOKEN（跳过回显行里的），正确截取响应

**还会再有吗**：不会。换行分隔 + 行首哨兵 + echo 带引号已固化到 `serial_console.py`，对所有同步命令稳定工作。后续加新命令直接用 `exec_sync` 即可。

### 问题 2：拍照/录像命令打乱哨兵——改用 exec_async（耗时第二多）

约 1 小时。

**现象**：拍照 `dfs_capture_start` 命令发出后，哨兵 TOKEN 的回显出现**引号丢失、行错位**（如 `echo __EVBTEST_END_xxx__"`，开头引号丢了），哨兵匹配失败，命令判超时。

**根因**：拍照/录像命令会输出**海量摄像头初始化日志**（sensor probe、AE/AWB 初始化、`mem_laySolv` 场景求解等，几十 KB），这些日志和命令回显、哨兵输出交织在一起，把哨兵的引号和行结构打乱了。

**解决**：拍照/录像改用 `exec_async`——它发命令后**不依赖哨兵**，直接在缓冲里等期望正则（如 `Save Photo Successful`）。`exec_async` 的 `_wait_regex` 从命令发出后的缓冲快照开始持续正则匹配，30 秒超时内匹配到即成功。

**还会再有吗**：不会。所有"重输出命令"统一用 `exec_async` + 正向成功标志判据，已固化到 photo/video 模块。

### 问题 3：成功判据误判——初始化日志含 "invalid" 触发 error 关键字

约 30 分钟。

**现象**：录像 `dfs_video_start` 明明成功了（日志有 `Record Start`），却判 FAIL。detail 里是摄像头初始化日志。

**根因**：`exec_sync` 无 `expect` 时，默认靠"无 error 关键字"判定（正则匹配 `error|failed|fail|cannot|invalid|...`）。但摄像头初始化日志里有 `[fallback]preset capCfg 0 0 0 invalid` 这类内容，`invalid` 触发了误判。

**解决**：拍照/录像命令全部用**正向 expect**（`Record Start`、`Save Photo Successful`），不靠"无 error 关键字"。

**还会再有吗**：不会。新命令只要找到明确的成功标志正则，就不会被海量日志误判。

### 问题 4：FTP 服务只支持主动模式（耗时第三多）

约 1 小时。

**现象**：ftplib 连 FTP 成功登录，但一执行 `LIST`/`NLST`/`RETR` 就 `502 Not Implemented`。而用户用 Windows FileZilla 能正常下载。

**排查过程**：
1. 开 ftplib debug 模式，看到发的是 `PASV` 命令，服务器回 `502 Not Implemented`——**这个 RT-Thread FTP 服务不支持被动模式**
2. ftplib 默认 `pasv=True`，所以一发 PASV 就 502，根本到不了 LIST
3. FileZilla 能用是因为它检测到 PASV 失败会自动回退主动模式
4. 改 `set_pasv(False)` 用主动模式，但 `LIST` 超时——主动模式需要 EVB 主动回连 PC 的数据端口，被 PC 防火墙挡
5. 验证 EVB→PC 网络通（ping 成功），确认是 PC 防火墙问题
6. 用户执行 `sudo ufw disable` 关防火墙后，主动模式 LIST/RETR 全通

**还发现 FTP 服务的其他限制**：
- `LIST <path>` 会**忽略路径参数**，列的是当前目录——必须先 `CWD` 再无参 `LIST`
- 不支持 `NLST`/`STOR`/`SIZE`——`list_files` 改用 LIST 解析，`size` 用 LIST 父目录解析，上传不可用

**还会再有吗**：不会。`FtpClient` 已全部适配（`pasv=False` + CWD+LIST + 解析 LIST）。但**使用前提是 PC 防火墙放行**，这需要在目标 PC 上执行 `sudo ufw disable` 或 `sudo ufw allow 1024:65535/tcp`，已写进 README。

### 问题 5：FTP 服务在拍照/录像后崩溃（固件 bug）

约 1 小时。

**现象**：拍照/录像后，串口输出 `[W/ftp] service go wrong, now wait restarting...` 反复，FTP 服务崩溃，无法 list/download。导致 photo/video 的 FTP 辅助验证跳过（显示"未列出 jpg 辅助验证"）。

**排查过程**：
1. 确认 FTP 不会自恢复（等 10 秒还在错误循环）
2. 发现**重发 `ftp_server` 能恢复**（`Ftp server init success` 后又能正常连接）
3. 写了 `ensure_ftp()`：检查连接，失效则重发 `ftp_server` + 重连
4. 但 `ensure_ftp` 的健康检查（list `/emmc`）太宽松——服务半崩时 list 根目录能成，list 子目录失败，导致 photo 的辅助验证还是跳过
5. 最终给 `ensure_ftp` 加 `force=True` 参数：**拍照/录像后强制重发 `ftp_server` + 重连**，不管现有连接看着是否活着

**解决后**：photo 报告 `JPEG OK 680KB`（下载到本地 + 校验通过），video 报告 `9989KB`（大小校验通过）。

**还会再有吗**：会，这是固件 bug，拍照/录像后 FTP 大概率崩。但 `ensure_ftp(force=True)` 已能可靠恢复，每次使用前强制重连，对上层透明。**测试前需重启板子保证干净状态**（已写入 README 的稳定性注意）。

### 问题 6：板子状态不干净导致 WiFi 连不上

约 30 分钟。

**现象**：完整流程跑 `wifi_join` 时 0ms 失败，串口只收到 `wifi is connect`（不是 `connect success`），之后被 `[W/ftp] service go wrong` 刷屏，拿不到 IP。

**根因**：上一次测试残留导致板子启动后 FTP 就在崩溃循环，干扰了 WiFi 连接。而且 `wifi_scan` 后立即 `wifi_join` 可能也有状态问题。

**解决**：
1. main.py 加**板子预清理**步骤：测试前发 `dfs_video_stop`（停录像）+ `wifi disc`（断 WiFi）+ `ftp_server`（恢复 FTP 服务）
2. 建议每轮完整测试前重启板子

**还会再有吗**：预清理能处理大部分情况，但固件状态异常时仍需重启板子。已写入 README。

### 问题 7：网络环境导致依赖装不上

约 40 分钟（主要在排查）。

**现象**：`pip install pyserial` 报 `Network is unreachable`，`sudo apt install ffmpeg` 也连不上。`wget` 下载任何外网文件都返回 190 字节的 HTML 认证跳转页。

**根因**：PC 所在网络有**网页认证网关**（`http://10.10.246.250/`），所有外网请求被劫持到认证页，`forbid=1` 表示未认证或会话过期。

**解决**：
- pyserial 后来在网络通的窗口期用 pip 装上了
- ffmpeg 始终装不上（apt/pip/wget 全失败，pypi 不在白名单）
- RTMP 模块因此未真机验证；代码里加了 `imageio-ffmpeg`/多路径探测的兼容，等环境就绪即可测

**还会再有吗**：会。这台 PC 的网络认证是常态问题，每次会话过期都要重新认证。RTMP 测试需先解决 ffmpeg 安装（认证后 `sudo apt install ffmpeg`）。

### 问题 8：串口权限不足

约 15 分钟。

**现象**：`pyserial` 打开 `/dev/ttyUSB0` 报 `Permission denied`。

**根因**：串口设备属于 `dialout` 组，当前用户不在该组。

**解决**：`sudo chmod 666 /dev/ttyUSB*` 临时放权（或 `sudo usermod -aG dialout $USER` 永久加组后重新登录）。

**还会再有吗**：临时 chmod 重启/重插失效；永久加组后不会再有。

### 问题 9：msh 提示符有两种形态

约 20 分钟。

**现象**：`wait_for_ready` 有时检测不到就绪，但板子明明有 `msh /emmc>`（cd 进 emmc 后提示符变了）。

**根因**：原就绪正则 `msh\s*/?>` 只匹配 `msh />`，不匹配 `msh /emmc>`。

**解决**：改正则为 `msh\s+/[^>]*>|msh\s*/>`，同时匹配根目录和子目录提示符。

**还会再有吗**：不会。

### 问题 10：波特率与手册不符

约 10 分钟。

**现象**：手册和 `res/start.txt` 旧日志是 250000，但自动探测命中 2000000。

**根因**：当前固件 UART0 已改为 2000000 bps，手册是旧版。

**解决**：默认 2000000 + 自动探测回退候选 `[2000000, 250000, 115200, 921600]`，探测结果会打印，实测命中 2000000。

**还会再有吗**：不会，已固化。

## 第三部分：时间分布与总结

### 时间分布（单日开发，约 8 小时）

| 阶段 | 耗时 | 占比 |
|------|------|------|
| 需求/设计文档 + 用户确认 | 1.5h | 19% |
| 编码（架构 + 全部模块） | 2h | 25% |

### 耗时最多的三个点

1. **串口哨兵机制**（1.5h）：msh 不支持 `;`、echo 要引号、行首哨兵匹配。这是地基，必须搞对，否则后面全废。
2. **拍照/录像的异步处理**（1.5h）：海量日志打乱哨兵，改 exec_async + 正向判据 + FTP 崩溃恢复，多个问题交织。
3. **FTP 服务限制适配**（1h）：不支持 PASV、LIST 忽略路径、不支持 NLST/STOR/SIZE，逐个命令试错适配。
