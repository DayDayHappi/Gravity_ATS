# 串口同步/异步命令执行机制改造：exec_async 不再发送哨兵

**日期**: 2026-08-20
**改动范围**: `core/serial_console.py`（重构 `_write_safe` + `exec_async` 去哨兵）、`modules/rtmp.py`（expect 改业务状态字符串）

---

## 一、问题描述

此前 `exec_sync()` 和 `exec_async()` 都会发送「业务命令 + `echo "SENTINEL"`」，但哨兵只能表示
「Shell 已执行到 echo」，不能表示异步业务真正完成。例如 `wifi join` 的时序是：

```
wifi join → wifi join success → SENTINEL → 数秒后 Got IP address
```

哨兵先于业务完成出现，语义模糊；而且 `exec_async` 实际从不等待哨兵（只等 expect），
白白多发送了一段哨兵字节（对 rtmp 这类长命令还会多占串口接收缓冲，加剧溢出风险）。

## 二、根因分析

同步/异步两种命令的「完成」语义本质不同：

- **同步命令**（ifconfig / cd / cam_set）：命令执行完才返回 shell，哨兵恰好表示「命令已返回」。
- **异步命令**（wifi join / ftp_server / dfs_capture_start / rtmp_video_start）：Shell 返回后业务仍在
  后台跑，真正完成要靠业务字符串（Got IP / service launched / Save Photo Successful / publish ready）。

旧实现把两者混为「命令+哨兵」，导致 exec_async 的哨兵既无意义又多占串口缓冲。历史遗留：
`exec_async` 的 expect 本就不依赖哨兵（[[20260817_0115_RTMP命令串口溢出丢字节_长命令分片写入修复]] 引入
分片后，rtmp 用 exec_async 正是为了绕开哨兵被 FTP 刷屏打乱的问题），哨兵发送只是沿用了 exec_sync 的写法。

## 三、修复内容

### 3.1 `core/serial_console.py`

1. **抽离统一安全发送 `_write_safe(text)`**：只负责「给定文本（含换行）分片 + 片间延时 + 记 TX」，
   不关心同步/异步/哨兵。合并删除了旧 `_write`（死代码）和 `_write_cmd`（职责混杂）。
2. **`exec_sync`**：保留哨兵。发 `cmd\necho "哨兵"\n`，等哨兵定界。哨兵语义明确为「前一条同步命令已返回」。
3. **`exec_async`**：**不再生成、不再发送哨兵**，只发 `cmd\n`，直接等 expect（业务完成字符串）。

### 3.2 `modules/rtmp.py`

`rtmp_video_start/stop` 的 expect 从「命令回显/宽松正则」改为 DUT 侧真实业务状态：

- `rtmp_video_start`：`expect=r"publish ready|Push Start"`（旧 `rtmp_video_start|RTMP|push|start` 会命中命令回显）
- `rtmp_video_stop`：`expect=r"Push Stop|Stop requested"`（旧 `rtmp_video_stop|stop|RTMP` 会命中命令回显）

这两串均从 serial.log 实测确认（`[RTMP] publish ready on rtmp://...`、`[RTMP] Push Start -> ...`、
`[RTMP] Push Stop: total frames = N`、`[RTMP] Stop requested`）。

> RTMP 最终 PASS 判据**不变**：仍是 PC 端 ffprobe 探测到实时流；exec_async 的匹配结果不作为最终判据。

### 3.3 未改动（原则性不涉及）

`core/runner.py`、`core/context.py`、`modules/base.py`、`core/reporter.py`、`drivers/ftp_client.py`，
以及 wifi/ftp/photo/video 模块（它们已用业务 expect，本次无改动）。

## 四、验证结果

- `python3 -m py_compile` 语法检查通过（`serial_console.py`、`rtmp.py`）。
- `grep` 确认无残留 `_write_cmd` / `._write(` 调用；`_gen_sentinel` 仅剩 `exec_sync` 一处使用（正确）。
- **待真机验证**：按验收标准逐项确认——
  - 同步命令（ifconfig / wifi scan / cd / cam_set）输出完整、哨兵后返回；
  - 异步命令（wifi join / ftp_server / photo / video / rtmp）不再发送哨兵、等到业务字符串才返回；
  - serial.log 中 TX 时间不得晚于该命令产生的 RX；
  - 异步命令不得因命令回显提前成功；
  - 长串口命令不再出现截断 / command not found。

## 五、还会再有吗

- **异步 expect 语义依赖模块自律**：`exec_async` 无法在串口层强制「expect 不是命令回显」，
  需要模块传入真正的业务字符串。rtmp 已修，其余模块本就合规。新增模块时需遵循「命令回显 ≠ 业务成功」。
- **rtmp 启动 expect 等待时间**：`result_timeout=8.0` 未变。`publish ready / Push Start` 是 RTMP 握手阶段
  输出（早于首帧），通常很快；但若板子 CPU 被 FTP 刷屏占满、连握手都慢，exec_async 可能超时——
  此时仍由 ffprobe 兜底判据，不影响最终 PASS/FAIL，只是多等 8s。
- **分片与哨兵已解耦**：`_write_safe` 统一处理分片，未来更长的命令（如带鉴权的推流 URL）自动安全，
  不会再因「是否带哨兵」影响分片逻辑。

## 六、经验沉淀

- **哨兵和业务完成是两件事**：哨兵只表示「命令已返回」，异步业务的完成必须靠业务字符串。
  把两者混为一谈，会让 `exec_async` 的哨兵既无意义又徒增串口字节。
- **"物理发送"与"完成判定"应解耦**：`_write_safe` 只管可靠发送，`exec_sync`/`exec_async` 各自决定
  「等什么」——低耦合、易扩展，新增命令类型不动发送层。
- **命令回显 ≠ 业务成功**：expect 若写成命令名本身，RX 里的回显会立即匹配导致提前成功。
  应从 serial.log 实测确认真正的业务完成字符串（如 `publish ready` / `Push Stop`）。
