# ffplay 画面确认增强：stderr 落日志 + 展示窗口延长

**日期**: 2026-08-17
**改动范围**: `modules/rtmp.py`（ffplay stderr 落日志、展示延长）+ `config/test_config.yaml`（新增 `ffplay_show_duration`）

---

## 一、问题描述

真机测试 rtmp 已 PASS（`h264 1296x2304`），脚本日志显示 `ffplay 画面确认已启动 (pid=...)`，但用户**没看到画面窗口**。

## 二、根因分析（三层叠加）

### 1. ffplay 的 stderr 被吞进 /dev/null

原代码 `subprocess.Popen(..., stdout=DEVNULL, stderr=DEVNULL)`，ffplay 连流失败、等不到关键帧、SDL 初始化报错等一律不显示，只留一句「已启动」，无法得知它到底发生了什么。

### 2. 展示窗口存活时间太短（约 8s）

脚本时序：发 `rtmp_video_start` → `sleep 3` → 起 ffplay → 立即 ffprobe 探测（本次约 8s）→ 探测成功即进入 `rtmp_video_stop` → `teardown` 里 `killpg` 杀掉 ffplay。ffplay 从启动到被关只有约 8s，用户来不及看到窗口。

### 3. 大分辨率首帧解码慢

本次流分辨率 1296×2304（竖屏大图），ffplay 连流→握手→等 H264 关键帧→解码首帧需数秒，8s 内可能刚出画面就被杀。

## 三、修复内容

### A. `modules/rtmp.py`

1. `__init__` 新增 `self._ffplay_log = None`。
2. ffplay 启动时：`stderr` 从 `DEVNULL` 改为写入 `logs/<run_ts>/ffplay.log`（用 `logger.log_dir()` 定位，句柄存 `_ffplay_log`）；stdout 仍 DEVNULL。
3. ffprobe 探测成功后、`rtmp_video_stop` 之前，新增「展示窗口保持」：仅当 `info.ok` 且 ffplay 仍运行时 `sleep(ffplay_show_duration)`，默认 5s，给人眼确认画面时间。失败则跳过、尽快 stop 清理。
4. `teardown` 关闭 `_ffplay_log` 句柄。

### B. `config/test_config.yaml`

`rtmp` 段新增 `ffplay_show_duration: 5`（秒），可调。

## 四、验证结果

- `ast.parse` 语法 OK；`yaml.safe_load` 配置 OK。
- **待真机验证**：跑 `python3 -m ATS.main --no-interactive-wifi`，确认 ①rtmp 仍 PASS；②`logs/<run_ts>/ffplay.log` 有内容（无报错或可定位报错）；③能短暂看到 ffplay 窗口。

## 五、还会再有吗（残留风险）

1. **DISPLAY 为空的场景不受影响**：ffplay 不启动，`show` 停留分支因 `_ffplay_proc is None` 跳过，SSH/无人值守不增加耗时。
2. **ffplay 连流时机仍可能早于板子 push ready**：`sleep 3` 后起 ffplay，若板子 sensor 初始化超过 3s（大分辨率更慢），ffplay 连不上会因 `-rw_timeout 3s` 退出，窗口仍看不到。本次未改启动时机，靠 `ffplay.log` 先暴露真相，视真机结果再决定是否给 ffplay 加重试。
3. **展示延长增加测试耗时**：每次 rtmp 多约 5s（仅探测成功且有 ffplay 时），可接受。

## 六、经验沉淀

1. **子进程 stderr 别无条件 DEVNULL**：调试类/确认类子进程（ffplay 画面确认）应把 stderr 落到日志文件，否则「启动了但没画面」这类问题无从下手。`subprocess.DEVNULL` 只该用于确无诊断价值的纯输出（如 ffmpeg 存盘的进度条）。
2. **"确认类"动作要留足够展示时间**：ffplay 是给人眼看的「可选确认」，判据靠 ffprobe（机器可读），但既然启动了就要让人看得见——探测成功后、清理前多停几秒，用配置项控制，兼顾「无人值守不加耗时」（无 DISPLAY 自动跳过）和「桌面调试能看到窗口」。
3. **大分辨率推流的首帧慢是 RTMP 推拉模型固有特性**：1296×2304 这种大图关键帧间隔与解码耗时都更长，任何依赖「首帧到达」的动作（ffprobe 探测、ffplay 出画面）都要给足时间，别用 640×480 的经验值去套。见 [[rtmp-ffmpeg-bundled]]。
