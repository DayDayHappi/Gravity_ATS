# 引入测试场景层（Scenario Layer）：配置彻底拆分 + 场景驱动

**日期**: 2026-08-20
**改动范围**: 新增 `core/scenario.py`、`core/scenario_manager.py`、`config/{system,modules,scenarios}/`；
修改 `core/config.py`、`core/runner.py`、`core/result.py`、`core/reporter.py`、`modules/base.py`、
各业务模块、`main.py`；删除 `config/test_config.yaml`

---

## 一、问题描述

原架构「Module + 单一 `test_config.yaml` + `TestRunner(按 enabled_modules 调度)」缺「测试场景」抽象，
导致压力测试（拍照 50 次、推流 10min 循环）等「测试策略」只能写进模块代码，违反模块只负责「怎么测」的边界。

## 二、根因分析

「执行多少次 / 和谁组合 / 循环多久」属**测试策略**，与「模块能力」本质不同职责，混在一起导致：
- 加压测要改 photo/video/rtmp 核心代码（污染模块）
- 无法复用模块到不同测试组合
- 无法优雅支持老化/兼容性等新测试模式

## 三、修复内容

### 3.1 职责边界（架构约定，写入代码注释）

```
Scenario: 怎么组合测试   Runner: 什么时候执行   Module: 怎么测   Config: 参数是什么
```

### 3.2 配置体系彻底拆分（`test_config.yaml` 废弃删除）

```
config/system.yaml            系统/环境级：serial、wifi(网络环境)、pc.ip、runner、report
config/modules/<name>.yaml    模块能力参数（wifi/emmc/ftp/photo/video/rtmp）
config/scenarios/<name>.yaml  测试策略（normal/stress/aging）
```

### 3.3 新增 `core/scenario.py`

`Scenario`/`Task`/`LoopConfig` dataclass + prepare/cleanup 动作注册表 + `@prepare_action`/`@cleanup_action` 装饰器。

### 3.4 新增 `core/scenario_manager.py`

`ScenarioManager`：加载场景、编排 prepare→tasks(loop)→cleanup；内置 6 个框架级动作
（serial_init/wifi_connect/preclean/ftp_ready/stop_stream/close_serial），串口初始化与 WiFi 交互从 main.py 迁入。

### 3.5 修改 `core/config.py`

拆为 `load_system`/`load_module_config`/`load_scenario`/`list_scenarios`，保留 `_expand_env`/`apply_overrides`。

### 3.6 修改 `core/runner.py`

从「按 enabled_modules 拓扑排序」改为「按 scenario.tasks 声明顺序执行」；新增 `repeat`（模块循环）、
`loop`（整轮循环 count/duration/无限）；参数合并 module 默认 + task.override + task.duration(经 duration_key)。

### 3.7 修改 `modules/base.py` + 各业务模块

`run(ctx, console, params=None)` + `_merge(params)` + `duration_key`；photo/video/rtmp 核心逻辑**零改动**，
只加参数入口。wifi 的 ssid/password 改从 `ctx.system_config`（system.wifi）读。

### 3.8 修改 `main.py`

`--scenario`/`--list-scenarios` 主入口，移除 `--modules`/`--skip`；串口/WiFi 迁移为 prepare 动作。

### 3.9 修改 `core/result.py` + `core/reporter.py`

`TestResult` 增 `scenario`/`cycle` 字段；reporter 汇总增加场景维度统计（每场景 cycle 数 + 每模块 pass/fail/skip/error）。

## 四、验证结果

- `python3 -m py_compile` 全部通过。
- `--list-scenarios` 列出 normal/stress/aging；`--list-modules` 正常。
- `--dry-run` 三个场景依赖校验通过。
- 场景解析正确：stress 的 loop.count=3、photo repeat=50、video duration=180、rtmp duration=600。
- duration_key 映射（video→video_duration、rtmp→stream_duration）、`_merge` 覆盖优先级正确。
- `--format` → emmc override 合并正确。
- `--port /dev/ttyUSB999`（不存在）正确返回退出码 2，且 CLI 覆盖穿透到 prepare 动作（修复了
  ScenarioManager.run 重新 load_system 丢弃 CLI 覆盖的 bug）。
- **待真机验证**：`--scenario normal --no-interactive-wifi` 完整 8 模块链路，及 stress 压测循环。

## 五、还会再有吗

- **破坏性 CLI**：`--modules`/`--skip` 已移除，旧命令需改用 `--scenario`（handoff/使用手册需同步）。
- **wifi 参数归属**：ssid/password 属 system.wifi（网络环境），wifi 模块本身无独立参数文件。
- **loop 无限循环**（count/duration 都缺省）需 Ctrl+C 优雅退出，产测慎用。
- **product 配置层**预留接口未实现（当前仅 VX100 单产品）。

## 六、经验沉淀

- **「测多少次」是策略不是能力**：重复/循环/持续时间必须由 Scenario+Runner 驱动，模块只实现一次动作 +
  参数接口，才能在正常/压测/老化间复用同一模块（photo/video/rtmp 一行核心代码没改）。
- **配置分层按「生命周期/归属」拆**：system(环境，跨模块) / module(能力参数) / scenario(策略)，
  各自独立演进互不污染。
- **编排器不要重新加载已覆盖的配置**：main 里 apply_overrides 后的 system_cfg 必须原样传给
  ScenarioManager，否则 CLI 覆盖被静默丢弃（本次踩坑并修复）。
