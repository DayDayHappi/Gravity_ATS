# 修复 exec_sync 环形缓冲滚满后快照定位失效致 cam_set 误判（方案 A 序号游标）

## 问题描述

真机 stress 压测（`logs/stress/20260918/20260918_163736`）跑到约第 26 轮起，photo/video 的
`cam_set photo|video <mode>` 全部判 `[FAIL] 设置模式/设置录像组合 失败`，此后持续 FAIL 不可自愈；
photo 因第一步 cam_set 失败提前 return，不再发 `dfs_capture_start`。

矛盾点：固件回显成功（`I/App Dfs: auto mode` 等）+ 哨兵 1.6s 内完整出现（非超时），但脚本判 FAIL。

## 根因分析

两层叠加，缺一不可：

1. **快照定位失效**：`exec_sync`/`_wait_pattern` 用「字符串前缀切片」定位命令后新输出：
   `new = full[len(snapshot):] if full.startswith(snapshot) else full`。环形缓冲
   `deque(maxlen=65536)` 长时间压测滚满后，命令执行期间任何新数据都会顶掉头部，
   `full.startswith(snapshot)` 恒为 False → `new = full`（整个历史缓冲当成本次响应）。
2. **`_ERROR_RE` 过宽**：无 expect 时 `_judge` 用 `_ERROR_RE`（含 `invalid`）扫响应，第 1 层把
   历史缓冲喂进来，命中 RTMP 阶段固件正常 fallback 日志 `preset capCfg 200 0 0 invalid, use default`
   （全 log 780 条）→ 误判 `success=False`。

## 修复内容

文件：`ATS/core/serial_console.py`（对外 API 签名不变，纯内部实现级改动）。

方案 A：快照定位从「字符串前缀」改为「单调递增序号游标」。

1. `__init__`：`deque(str)` → `deque(tuple[int, str])`，新增全局自增序号 `self._buffer_seq = 0`。
2. `_reader_loop`：每次 append 时 `self._buffer_seq += 1`，append `(seq, text)`。
3. 新增 `_snapshot_seq()`：发命令前记序号游标（替代原 `_buffer_text()` 文本快照）。
4. 新增 `_buffer_text_since(start_seq)`：拼接 `seq > start_seq` 的 chunk；deque FIFO 淘汰的
   必然是 `seq <= start_seq` 的旧 chunk，不影响增量定位（不依赖 startswith）。
5. `_wait_pattern` / `_wait_regex`：参数 `start_snapshot: str` → `start_seq: int`，用
   `_buffer_text_since(start_seq)` 取增量。
6. `exec_sync` / `exec_async` / `wait_for_ready`：快照改为 `start_seq = self._snapshot_seq()`。
7. `_buffer_text()`：保留「返回全部文本」语义（供 `wait_for_ready` 等全缓冲检查），实现改
   `"".join(text for _, text in self._buffer)`。

同时收窄 `_ERROR_RE`（第二项独立评估，一并处理避免治标不治本）：

- `invalid` 加负向前瞻 `(?![\s,]*use\s+default)`，排除相机正常 fallback 日志
  `invalid, use default`；其余 `invalid`（如 `invalid argument`）仍判失败。
- video 的 cam_set 另有 `VIDEO_SET_ERROR` 二次判定兜底，photo 的 cam_set 失败由后续
  capture 超时兜底，不因收窄而漏报真失败。

## 验证结果

- `py_compile` 通过。
- 离线模拟（`SerialConsole.__new__` 手动驱动缓冲）：先喂 65536 条旧数据 + 780 条 invalid 残留
  把 deque 滚满，再记游标、追加命令响应；`_buffer_text_since(start_seq)` 精确取到命令后增量，
  不含 OLD/invalid 残留；`_wait_pattern` 在条件变量等待下正确匹配哨兵；`_judge` 无 expect 判 PASS
  （修复前该场景误判 FAIL）。
- 所有消费方 import 正常（photo/video/rtmp/wifi/emmc/ftp/scenario_manager/utest）。

**待真机**：`python3 -m ATS.main --scenario stress --no-interactive-wifi` 跑至 26 轮以上（越过
RTMP 10min），确认 photo/video 不再出现「设置模式/设置录像组合失败」。

## 还会再有吗

根治：增量定位不再依赖「字符串前缀相等」这一缓冲滚满后失效的假设。遗留边界（不处理）：若单命令
执行期间（快照→哨兵）产生的 chunk 数超过 65536（约 16MB），`seq > start_seq` 的新 chunk 也会被
FIFO 淘汰造成丢失——实测单命令 1.6s 内数据量远达不到；如需彻底可改按字节预算 maxlen，本次不建议
扩大改动面。

## 经验沉淀

- 环形缓冲 + 字符串前缀快照是脆弱组合：缓冲滚满会让前缀假设失效。增量定位应使用单调递增序号游标，
  淘汰与定位解耦（FIFO 只淘汰旧序号，不影响游标增量）。
- `_ERROR_RE` 反判（无 expect 时靠"无错误关键字"判成功）易被正常日志误伤；新增检测项应优先显式
  传业务 expect（红线「哨兵 ≠ 业务完成」的延伸），反判关键字需对正常日志做排除（负向前瞻）。
