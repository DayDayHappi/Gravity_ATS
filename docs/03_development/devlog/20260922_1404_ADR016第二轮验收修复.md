# ADR-016 第二轮验收修复（2 NEW-P0 + 2 NEW-P1 + 1 NEW-P2 + QA-GAP）

## 问题描述

第二轮验收（`docs/03_development/archive/ADR016_第二轮验收新增问题与修改建议.md`）发现
上一轮 13 项已关闭，但仍有 2 个 NEW-P0、2 个 NEW-P1、1 个 NEW-P2、1 个 QA-GAP、
1 个真机门槛（HW-RISK-01，非代码）。本轮按 Stage 1~6 修复代码级问题，HW-RISK-01 留真机确认。

## 修复内容（按 Stage 顺序）

### Stage 1（NEW-P0-01 结果一致性）
- `core/runner.py`：`abort_scenario` 且 `outcome.success=False`（恢复失败/耗尽）时，
  生成 framework 级 `board_recovery ERROR` TestResult，保证最终退出码非 0。
  落位在 Runner（Coordinator 不感知报告结构，职责不变宽）。

### Stage 2（NEW-P0-02 Policy fail-closed + Runner 兜底）
- `recovery_coordinator.validate()` 补全 policy schema 校验：`max_attempts >= 1`、
  `after_recovery ∈ {retry_current_task, continue}`、`on_exhausted ∈ {abort_scenario}`。
- `core/runner.py`：未知 `RecoveryOutcome.action` fail-closed（记 board_recovery ERROR +
  抛 ScenarioAbort），禁止未知 action → break → 继续。

### Stage 3（NEW-P1-01 Scenario 生命周期接线前置校验）
- `scenario_manager._validate_scenario_runtime_contract()`：health_monitor.enabled 要求
  prepare 含 health_monitor_start + cleanup 含 health_monitor_stop；recovery.enabled 要求
  monitor + health_monitor_start；backend=power_cycle 要求 power_switch_init 且在
  health_monitor_start 之前；health_monitor_stop 必须在 power_switch_close/close_serial 之前。
  不自动补 action（YAML 保持显式可审计），违规抛 ScenarioError。

### Stage 4（NEW-P1-02 mock 测试固化）
- 新建 `tests/` 包（unittest 风格，工程无 pytest/无网络）：`test_board_health_monitor.py`
  （7 用例）、`test_recovery_coordinator.py`（9 用例）、`test_recovery_runner.py`（4 用例）、
  `test_recovery_reporter.py`（3 用例），共 23 用例，`python3 -m unittest discover -s tests` 全过。

### Stage 5（NEW-P2-01 线程收尾）
- `board_health_monitor.py`：watchdog 循环改 `_stop_watchdog.wait(check_interval)`
  （stop 的 set() 立即唤醒，避免长 check_interval 下 join 超时残留）；锁内只改
  state/reason/event，`logger.warn` 移出锁外（避免 reader 回调等文件 IO）；
  `stop()` 补 `runtime_control.clear_recovery()` 收尾兜底。

### Stage 6（QA-GAP-01 专用验收场景）
- 新建 `config/scenarios/recovery_validation.yaml`：health_monitor+recovery 启用、
  power_cycle 后端、restore=[board_ready,wifi_connect,preclean,ftp_ready]、
  prepare 顺序合规、单次 180s 录像 task、cleanup 顺序合规。不修改 normal/stress/aging。

## 还会再有吗

- HW-RISK-01 若确认串口重枚举，需新增框架级 `serial_reconnect` 恢复 action（属 Scenario/

- `after_recovery` 目前仅 `retry_current_task` 被 Runner 显式处理；`continue` 已过 validate

## 经验沉淀

- 恢复失败的「结果一致性」必须闭环到退出码：框架级 FAIL/ERROR（board_recovery）是自动化
  可靠性的底线，不能让「恢复失败但退出码 0」静默发生。
- 配置 fail-closed 要覆盖到枚举值拼写（after_recovery/on_exhausted），并在 Runner 再加一道
  兜底（未知 action → abort），双保险防「Coordinator bug / 未来 backend 返回非法值」绕过。
- Scenario 生命周期「enabled=真实接线」是常见静默失效源：框架不自动补 action，声明与接线
  不一致直接报错，保证可审计。
- mock 测试固化进 `tests/`（unittest 无外部依赖），让线程/状态机/异常传播类逻辑在后续重构
  时有回归网。
