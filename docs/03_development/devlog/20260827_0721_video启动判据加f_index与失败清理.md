## 根因（实测日志证实）
连续压测第 10 轮，`dfs_video_start` 后固件漏打 `Record Start`（摄像头资源退化），但编码实际在跑
（`f_index` 持续增长：0 → 90 → 180...）。当前 `video.py` 只等 `Record Start`（`result_timeout=25s`），
误判「开始录像失败」FAIL；且失败分支直接 return、未发 `dfs_video_stop` 清理，把 stream_on 半初始化态
泄漏给下一个 rtmp task → ffprobe `Input/output error`（run.log cycle 10~12 连锁 FAIL/SKIP）。

f_index 实测格式（video 录像，无 `[RTMP]` 前缀，区别于 rtmp_monitor 的 `[RTMP] f_index`）：
```
I/NO_TAG: Gravity_XR Record Start
I/NO_TAG: f_index = 0, f_len = 83618, cur_total_len = 83709     ← Record Start 后约 2s
I/NO_TAG: f_index = 90, f_len = 159743, ...                     ← 再约 3s
```

## 做了什么
1. 启动成功判据：`expect=r"Record Start"` → `expect=r"Record Start|f_index\s*="`。
   有 `Record Start` **或** `f_index` 出现即判启动成功（f_index=0 出现即证明编码在跑 = 启动成功，
   不额外等 ≥90 徒增等待——启动成功本应在「启动」时点确定，中途崩由 stop 判据兜底）。
2. 失败清理：`if not r.success:` 分支补发一次 `dfs_video_stop`（best-effort，不判结果），
   避免 stream_on 半初始化态泄漏给下一 task。expect 用宽松判据
   `Save Video|Please start|recording completed`（与 prepare.preclean 同款，兼容「已启动/未启动/半启动」），
   短超时 8s。

## 改了哪些文件
- `ATS/modules/video.py`（仅此一个源文件，L64-66 判据 + 失败清理；exec_async/Response 接口不动）

## 如何验证
1. `python3 -m py_compile ATS/modules/video.py` → PASS。
2. 判据正则：
   - `Gravity_XR Record Start` → 匹配（正常路径）→ PASS；
   - `f_index = 0` / `f_index = 90`（漏打 Record Start，编码在跑）→ 匹配 → PASS；
   - 无 `Record Start`/`f_index` 的普通日志（如 camera init）→ 不匹配（正确判失败）→ PASS。
3. 清理正则 `Save Video|Please start|recording completed`：
   - `Video recording completed successfully.`（已启动）→ 匹配；
   - `Please start ...`（未启动）→ 匹配；
   - `Save Video Successful: ...`（半启动）→ 匹配 → PASS。
