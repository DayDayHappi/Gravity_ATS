# ADR-016 运行时闭环修复（7 P0 + 6 P1，验收报告驱动）

## 问题描述

2026-09-22 验收发现 ADR-016 主体代码虽已实施，但运行时闭环存在 7 个 P0 + 6 个 P1 问题，
当前版本不建议作为 stress/aging 自动恢复正式版。权威修复依据：
`docs/03_development/archive/ADR016_实现验收问题清单与修复建议.md`。

## 修复内容（按验收报告 §19 推荐顺序，全部落地）

### P0 修复

- **P0-01+P0-02（watchdog 持续监测 + runtime_control 触发链闭环）**：`BoardHealthMonitor`
  新增 daemon watchdog 线程，每 `check_interval` 秒比较 `last_rx` 距今，超 `inactivity_timeout`
  置 SUSPECTED + `runtime_control.request_recovery()`（仅 HEALTHY→SUSPECTED 推进一次，不重复刷）。
  watchdog 禁止 exec_sync/exec_async/health_check/PowerSwitch/FTP/网络 IO。
  至此 video `runtime_control.wait()` 在长 Task 中途死机能约一个 step 内提前返回。
- **P0-03（confirm_failures 同一次确认流程）**：新增 `Monitor.confirm_health()`，在同一安全点
  一次性完成 `confirm_failures` 次主动 probe（间 sleep `confirm_interval`）；任一次成功回 HEALTHY，
  全失败进 UNRESPONSIVE。Runner checkpoint 改调 `confirm_health()`，不再跨 Task 累计。
- **P0-04（Scenario 级 abort）**：新增 `runner.ScenarioAbort` 异常；`_run_tasks` 收到
  `abort_scenario` 抛 `ScenarioAbort`，`run()` 外层捕获退出整个 while loop（不再进下一 cycle）。
- **P0-05（recovery_history 报告前不丢）**：`ScenarioManager.run()` finally 里在 `ctx.cleanup()`
  前保存 `self.recovery_history`；`main.py` 改读 `manager.recovery_history`。
- **P0-06（fresh-ready）**：`serial_console` 新增 `snapshot_rx_cursor()` + `wait_for_ready_since(cursor)`
  （只匹配 seq>cursor 的新 RX）；Coordinator PowerCycle 前记录游标到 `ctx.recovery_cursor`，
  `board_ready` 用 `wait_for_ready_since` 判定新板真正 boot，消费后清游标。
- **P0-07（monitor-only FAIL/abort 语义）**：recovery 未启用但确认 UNRESPONSIVE 时，Runner
  记录框架级 `board_health` FAIL + 抛 `ScenarioAbort`（不 PowerCycle）。

### P1 修复

- **P1-01（retry 二次 Outcome）**：Runner 的 Outcome 处理改为 while 循环，每次 `_run_module`
  的 Outcome 都处理，直到 continue/abort；retry 后二次 Outcome 不再丢弃。
- **P1-02（backend 前置校验）**：`RecoveryCoordinator.validate()`；`health_monitor_start`
  创建 Coordinator 后立即 validate，backend 不可用抛 `RecoveryBackendUnavailable`（tasks 前报错）。
- **P1-03（recovery 要求 monitor）**：`health_monitor_start` 开头 fail-closed：recovery=true
  且 monitor=false 抛 `ScenarioError`。
- **P1-04（restore fail-closed）**：`_restore_environment` 未知 action 直接 restore failed；
  `validate()` 亦前置校验 restore action 全部注册。
- **P1-05（HTML Recovery Events）**：`write_html` 模板增独立 Recovery Events 区域（含无 jinja2
  退化分支）；`generate`/`write_html` 传 recovery_events。
- **P1-06（时间参数真正接线）**：watchdog 用 `check_interval`、confirm_health 用
  `confirm_interval`；`BoardHealthMonitor.__init__` 新增参数合法性校验 fail-closed。

## 验证结果（离线 mock）

- `py_compile` / `compileall ATS/` 通过；全包 import 正常。
- watchdog：长 Task 中无外部调用下，超 inactivity_timeout 自动 SUSPECTED + request_recovery。
- 参数非法（check_interval<=0 / confirm_failures<1 等）抛 ValueError。
- confirm_health：一次性完成 confirm_failures 次，全失败 → UNRESPONSIVE。
- fail-closed：recovery+monitor 配置约束、backend 前置校验、restore 未知 action 均在 tasks 前报错。
- fresh-ready：snapshot→ready_since(cursor)→消费清空 链路完整。
- recovery_history 在 ctx.cleanup 前保存。
- ScenarioAbort：monitor-only UNRESPONSIVE 记录 board_health FAIL 并中止整个 Scenario；
  retry 二次 Outcome(abort) 被正确处理。
- HTML/JSON 均展示 Recovery Events。

**待真机**：TC-BH-001~003 + TC-RCV-001~005（验收报告 §20）。

## 还会再有吗

- 能力边界不变（验收报告 §17）：当前只识别「串口静默型整板无响应」，不覆盖「串口仍刷日志但
  控制链路已死」，未来扩展 Task 业务 timeout → probe → shell 不响应 → 升级 UNRESPONSIVE（需 ADR）。
- `inactivity_timeout` 等默认值仍需真实 stress 日志校准。
- 现有 normal/stress 未声明 health_monitor/recovery（保持向后兼容）；建议先建独立验证场景
  `stress_recovery_validation` 跑 TC-BH/TC-RCV，全过再决定接入正式 stress/aging。

## 经验沉淀

- watchdog 与 active probe 分离：watchdog 只做「轻量超时推进 + 置位请求」（禁止 IO），主动
  确认放 Runner 安全点，既及时又避免后台线程并发串口命令。
- 运行时闭环的「触发链」必须端到端验证：watchdog→request→wait 提前返回→安全点 probe→决策，
  任何一环断开会造成「形式上接入、实际失效」。
- 恢复事件留痕必须在 ctx.cleanup 前物化到独立载体（manager.recovery_history），否则被清空后
  报告静默丢失。
- fail-closed 优先：backend 不可用、restore 未注册、recovery 配置矛盾都要在 tasks 前显式报错，
  禁止静默降级/静默无效。
