# 修复 download 下载完整性与逐文件日志

## 日期
2026-08-31

## 变更来源
Document Agent Request：`docs/03_development/archive/修复需求_download下载完整性与逐文件日志.md`
（download 场景首轮真机运行暴露的缺陷，Level 1：模块内部 bug 修复 + 日志增强）。

## 问题描述
download 场景首轮真机运行后暴露两处缺陷：

1. **无逐文件成功日志**：`download.py` 下载循环成功分支零打印，只能看到「下载 X -> Y」，
   无法逐文件确认，失败才打 warn。
2. **残缺文件静默入库（核心）**：`ftp_client.py::download()` 里
   `if total <= 0 or local_sz >= total: return True` —— 远端大小未知（`size()` 解析不到返回 -1）
   时，第一次 `retrbinary` 结束即静默 `return True`，中途断流/截断的残缺文件被当成成功，
   且不打印任何告警（与现场「run.log 无告警」吻合）。
3. **汇总缺目录明细**：`latest_n=20` 只下 19 个，从日志无法判断是目录数不够还是某目录无匹配文件。

现场证据（已固化在需求文档 §2）：18 个完整视频 ≈46s，1 个 `20260824_094316_2663/Video_2663_0.h265`
仅 6.6MB/89 帧 ≈3.5s；RTC 未校时目录名多为 `20260101_*`（字典序=时间序假设复现为不可靠）。

## 根因分析
- `size()` 对 LIST 解析不到目标文件名时返回 -1，`_parse_list_line` 对「仅名称」行返回 size=0。
- `download()` 对 `total<=0` 无兜底，直接放行；`download.py` 无条件信任 bool 返回值。

## 修复内容

1. **`ATS/drivers/ftp_client.py::download()`**
   - 新增可选参数 `out`（dict），回传 `remote_size`（-1=未知）/`local_size`/`resumed`/`verified`。
   - 完整性校验修复：`total <= 0` 时**不静默 return True**——下载结束后重查一次 `size()` 兜底比对；
     仍拿不到则打印 `warn`「远端大小未知，无法校验完整性，按可疑处理」并按失败/可疑返回。
   - `total > 0` 的正常路径（比对 + 续传）不变。
2. **`ATS/modules/download.py::_download_source`**
   - 逐文件成功日志：`成功 <fname>: 远端 XKB / 本地 XKB（续传）`，带两端大小 + 续传标记。
   - 失败日志带远端/本地大小，便于判断是否截断。
   - 目录明细：`label: <dir> 目录总数 N，实际取最新 M 个`；汇总 message 改
     `目录 M/N 个，下载 X 个文件 / 共 XKB / 失败 Y 个`。

## 如何验证
1. `python3 -m py_compile ATS/drivers/ftp_client.py ATS/modules/download.py` → PASS。
2. `inspect.getsource` 确认 `download()` 含 `out` 参数 +「无法校验完整性」兜底；
   `_download_source` 含目录明细 + 逐文件成功/失败日志 → PASS。
3. 待真机复跑 `--scenario download`：
   - 每个文件下载后打印 `成功 ... 远端/本地大小`，本地与板端一致。
   - 重点核实 `20260824_094316_2663/Video_2663_0.h265` 是否本身即短录像
     （板端文件仍在，直接列 `/emmc/VIDEO/20260824_094316_2663/` 比大小定性）。
   - 汇总行可见「目录总数 / 实际取数 / 成功 / 失败 / 总大小」。

## 还会再有吗
- 若 `20260824_*` 短文件是板端本身短录像（而非 FTP 截断），则本修复只解决「未知大小不静默成功」，
  该文件会转为 `失败/可疑` 告警而非静默入库，正确定性需真机列板端大小确认。
- `size()` 解析不到 -1 的根因若属固件 LIST 格式限制，兜底已覆盖；若可修可后续提升 `_parse_list_line` 健壮性。

## 经验沉淀
「无法校验完整性」绝不静默判成功——宁可降级为失败/可疑并打 warn，也不让残缺文件无痕入库；
下载类函数的返回值要么带足够信息（`out` 回传大小），要么调用方独立比对两端大小，不能只信一个 bool。

## 附带影响（记录备查）
`ftp_client.download()` 的 `total<=0` 兜底对**所有调用方**生效：`photo.py`、`video.py` 的辅助
下载验证（不传 `out`）在远端大小未知时也会从「静默 True」变为「warn + False」，属更严格正确的
行为变化——photo 会因此多报「下载验证失败（PASS 态）」，video 会多报「大小校验跳过」，
不影响主判据（拍照/录像成功判定基于串口完成标志，不依赖 FTP 下载）。
