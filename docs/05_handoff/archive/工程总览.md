## 1. 项目定位（一段话）

为 **VX100 EVB 板**（双核异构 RISC-V，RT-Thread msh shell）开发的**上位机自动化测试脚本**，
替代人工，用于功能验证/产测。PC 通过串口发命令控制 EVB，通过 WiFi/FTP/RTMP 验证功能产物，生成报告。

```
PC (Python)  ──串口 2000000bps──>  EVB (msh shell)
     │                                  │ 摄像头
     │  WiFi/FTP/RTMP                    │
     ◄──────────────────────────────────┘
```

- **串口**：UART0（FT2232），波特率 **2000000**（手册写 250000 是旧固件，以 2000000 为准）
- **WiFi**：连局域网，SSID/密码见 `config/system.yaml` 的 `wifi` 段
- **FTP**：EVB 侧 RT-Thread 自带（端口 21，loogg/loogg，只支持主动模式）
- **RTMP**：EVB 推流 → PC 端 nginx-rtmp（1935）中转 → ffprobe 探测 / ffplay 看画面

**测试链路**：`wifi_check → wifi_scan → wifi_join → emmc → ftp → photo → video → rtmp`（8 项）。

**入口**：`python3 -m ATS.main --scenario <name>`（默认 `normal`）。

## 2. 最新架构（第五次交接后）

```
config/                     配置三层（数据驱动）
  system.yaml               系统/环境级：串口、WiFi 网络环境、pc.ip、runner、report
  modules/<name>.yaml       模块能力参数（wifi/emmc/ftp/photo/video/rtmp）
  scenarios/<name>.yaml     测试策略（normal/stress/aging）
core/                       框架核心（稳定，加用例不改这里）
  scenario.py               Scenario/Task/LoopConfig 数据结构 + prepare/cleanup 动作注册表
  scenario_manager.py       加载场景 + 编排 prepare → tasks(loop) → cleanup（含 6 个框架级动作）
  runner.py                 按 Task 列表调度 + repeat/loop + 重试 + fail-fast
  serial_console.py         串口：哨兵机制 + 常驻读线程 + 自动探测 + 波特率回退（核心）
  config.py / context.py / result.py / reporter.py / logger.py / ansi.py
modules/                    功能模块（每模块一文件，@register 注册）
  base.py                   TestModule 基类 + @register 装饰器 + run(ctx,console,params)
  wifi.py / emmc.py / ftp.py / photo.py / video.py / rtmp.py / rtmp_monitor.py
drivers/                    PC 端辅助
  ftp_client.py             ftplib 封装（主动模式 + 断点续传）
  rtmp_receiver.py          ffprobe 实时探测 RTMP 流（主判据）
  rtmp_server.py            nginx-rtmp 就绪检查（只查 1935 监听，不启停 nginx）
tools/                      内置 ffmpeg/ffprobe/ffplay（静态构建，离线可用）
ATS/tools/serial_terminal.py  --terminal 交互式串口终端（类 Xcom）
```

**职责边界（架构约定，写进代码注释，勿破坏）**：

```
Scenario = 怎么组合测试（流程/循环/持续时间）
Runner   = 什么时候执行（调度）
Module   = 怎么测（一次测试动作 + 参数接口）
Config   = 参数是什么
```

## 3. 配置三层体系（别放错）

| 层 | 文件 | 放什么 |
|----|------|--------|
| system | `config/system.yaml` | 串口、WiFi 网络环境（ssid/password 属这里，不是 wifi 模块参数）、pc.ip、runner、report |
| modules | `config/modules/*.yaml` | 模块业务参数（photo_modes、video_duration、stream_duration、heartbeat_timeout…） |
| scenarios | `config/scenarios/*.yaml` | 流程/组合/循环（prepare/tasks/loop/cleanup） |

**场景结构示例**（stress）：
```yaml
scenario:
  name: stress
  prepare: [serial_init, wifi_connect, preclean, ftp_ready]
  loop: {enable: true, count: 3}
  tasks:
    - {module: photo, repeat: 50}
    - {module: video, duration: 180}
    - {module: rtmp,  duration: 600}
  cleanup: [stop_stream, close_serial]
```

- `task.repeat`：单任务重复 N 次（Runner 循环，模块内不写 for）
- `task.duration`：经模块类属性 `duration_key` 覆盖持续参数（video→`video_duration`、rtmp→`stream_duration`）
- `loop`：整轮循环（count 次数 / duration 时长 / 都缺省=无限循环）
- 三个场景：`normal`（8 模块完整）、`stress`（photo×50 + video 180s + rtmp 600s，loop×3）、`aging`（photo×10 + rtmp 600s，loop 7200s）

**prepare/cleanup 内置动作**（`scenario_manager.py`）：`serial_init`（探测+打开+就绪+自检）、`wifi_connect`（交互连 WiFi）、`preclean`（cd / + 停录像）、`ftp_ready`（幂等启动 ftp_server）、`stop_stream`（兜底停推流）、`close_serial`。

## 4. 核心机制（浓缩结论，不含排查过程）

### 4.1 串口哨兵机制（`serial_console.py`）
- msh 提示符 `msh />` 会被后台日志/回显打碎粘连，不能靠等提示符。
- **`exec_sync`（同步命令）**：发 `cmd\necho "TOKEN"\n`，等**行首**哨兵定界。适合 ifconfig / wifi scan / cd / cam_set。
- **`exec_async`（异步命令）**：**只发 `cmd\n`、不发哨兵**，直接等业务正则。适合 wifi join / dfs_capture_start / rtmp_video_start（这些命令后台业务未完成时 Shell 已返回，哨兵无意义）。
- **哨兵 ≠ 业务完成**：同步命令的哨兵表示「命令已返回」；异步命令的成败必须靠业务字符串（`Got IP address` / `Save Photo Successful` / `publish ready` / `service launched success`）。
- **命令回显 ≠ 业务成功**：expect 不能写命令名本身，否则回显立即匹配导致假成功。
- 解析前一律 `ansi.strip()` 剥离 ANSI。
- **echo 必须带引号**（`echo "string"`），msh 不支持 `;` 分隔命令（用换行分隔）。

### 4.2 分片写入（防串口溢出）
- 板子串口接收缓冲 `RT_SERIAL_RB_BUFSZ` 默认约 64B；长命令（如 `rtmp_video_start <url>`）一次性写入会溢出丢字节 → `command not found`。
- 统一 `_write_safe()`：按 **32 字节/片 + 片间 0.1s** 延时写入（`_WRITE_CHUNK_BYTES=32`、`_WRITE_CHUNK_DELAY=0.1`）。对短命令只有 1 片，几乎无影响。

### 4.3 自动探测 + 波特率回退
- 未指定 `--port` 时扫描 `/dev/ttyUSB*` + `/dev/ttyACM*` × 候选波特率 `[2000000, 250000, 115200, 921600]`，用指纹（`JX009` / `msh />` / `GravityXR.cn Build`）匹配；多个匹配交互选择。

### 4.4 FTP 会话三原则（`ftp.py` + `ftp_client.py`，排查 FTP 必看）
1. **`ftp_server` 全程只发一次**（`ctx.ftp_server_started` 标志幂等）。重发会触发固件 `service go wrong` 崩溃循环刷屏。
2. **冷启动分两阶段**：`Ftp server init success` ≠ 已 listen；要到 `service launched success`（约 3~4s 后）才能 connect。启动用 `exec_async` 等 launched。
3. **会话 3s 空闲即断**：不缓存/复用连接；`ensure_ftp` 每次下载前都重建独立连接（新 socket → 登录 → cwd 根目录）。
- **FTP 只支持主动模式（PORT）**：不支持 PASV/NLST/STOR/SIZE；`LIST <path>` 忽略路径（先 `CWD` 再无参 `LIST`）；`size` 用 LIST 父目录解析；上传不可用。
- **需 PC 防火墙放行入站高位端口**（主动模式 EVB 回连 PC）。

### 4.5 RTMP 流程（`rtmp.py` + `rtmp_receiver.py` + `rtmp_monitor.py`）
时序（★关键）：`check_ready(1935)` → `rtmp_video_start <url>`(exec_async) → sleep 3s 等上线 → 可选 ffplay → **ffprobe 实时探测**（主判据）→ 保持推流 + heartbeat 检测 → `rtmp_video_stop`。
- **★ ffprobe 探测必须在 `rtmp_video_stop` 之前**（探测的是实时流，stop 后必失败）。
- **主判据**：ffprobe 实时探测 `rtmp://<pc_ip>/live/cam` 得到 h264 + 分辨率 → PASS。
- **持续检测**：`RTMPMonitor` 订阅串口原始数据（`add_listener`），用板端 `[RTMP] f_index` 日志作 heartbeat（正常约 2~4s 一条）；超 `heartbeat_timeout`（配置 **60s**）无 f_index 判推流异常停止，提前 FAIL。串口层只转发原始数据、不加业务逻辑。
- ffplay 仅**可选**画面确认（有 DISPLAY + 终端模拟器时开独立终端窗口；无 DISPLAY 自动跳过），不影响判据。
- `pc_ip` 解析顺序：`system.pc.ip` → auto 探测（UDP connect 取本端 IP）。多网卡易探错，建议写死。

## 5. 模块一览

| 模块 | depends | 成功判据 | 要点 |
|------|---------|---------|------|
| wifi_check | - | ifconfig 有非 0.0.0.0 IP | 已联网则 `ctx.skip_wifi=True` + 存 `evb_ip`，scan/join 跳过 |
| wifi_scan | wifi_check | 表头 `SSID MAC security rssi chn Mbps` + ≥1 行 | RSSI<-70 只警告不判失败 |
| wifi_join | wifi_scan | `Got IP address : <IP>`（异步，约 9s） | 成功后 `sleep(5)` 等稳定；IP 存 `ctx.evb_ip` |
| emmc | - | `cd /emmc` 无 error | 默认不格式化；`--format` 才 mkfs/mount |
| ftp | wifi_join | 列 /emmc 成功 | 幂等启动 ftp_server + 连接验证 |
| photo | ftp | 串口 `Save Photo Successful: <dir>` | 主判据=串口；FTP 下载 JPEG 头(FFD8FF)+大小>10KB 为辅助，失败降级不判 FAIL；遍历 photo_modes |
| video | ftp | 串口 `Save Video Successful: <path>` | duration 经 `video_duration`；FTP 下载校验大小>100KB 为辅助 |
| rtmp | wifi_join | ffprobe 探到 h264+分辨率 **且** heartbeat 无超时 | 不依赖 ftp；见 4.5 |

**依赖关系与执行**：runner 按 `scenario.tasks` **声明顺序**执行（不再拓扑排序）；`depends` 只用于 fail-fast——依赖模块 FAIL/ERROR 才 SKIP 本模块，**SKIP 不阻断**依赖（主动跳过不算失败）。

## 8. 遗留待办（按优先级）

### 🔴 P0-1 — stress/aging 场景 WiFi 前置缺失（上次会话末尾用户提出，未解决）
`--no-interactive-wifi + stress` 时：`wifi_connect` 动作跳过 → `ctx.evb_ip` 拿不到 → `ftp_ready` 的 `start_ftp` 因无 evb_ip 返回 None → photo/video 无 ftp_client 全 SKIP → rtmp FAIL。

**用户当时问**：「yaml 语法能不能把 wifi_join 写在 loop 外面？」—— 当前 loop 只循环整轮 tasks，没有「循环外一次性前置任务」概念。两个方向：
- **方向 A（推荐）**：给 prepare 加一个「非交互连接 WiFi」动作（用 system.wifi 默认 ssid/pwd 连，不弹交互），stress/aging 的 prepare 用它替代 wifi_connect。
- **方向 B**：给 scenario 加 `pre_tasks`（循环外任务）结构，`pre_tasks` 执行一次、`tasks` 被 loop 循环。改动更大但更通用。

### 🔴 P0-2 — 全部改动待真机验证
```bash
python3 -m ATS.main --scenario normal --no-interactive-wifi   # 先通正常链路
python3 -m ATS.main --scenario stress --no-interactive-wifi   # 再通压测循环（受 P0-1 影响）
```

### 🟡 P1 — loop 语义局限
当前 loop 只能循环「整轮 tasks」，不支持「A 任务循环 N 次 + B 只跑 1 次」的混合编排（目前靠 task.repeat + scenario.loop 两层凑合够用）。

### 🟡 P2 — 破坏性 CLI 变更
`--modules` / `--skip` 已移除，`--scenario` 成为主入口；`test_config.yaml` 已删除。旧文档（前三份交接、使用手册）里的命令全部失效，需同步文档。

### 🟢 P3 — RTMP 类型2 网络异常未覆盖
heartbeat 只能证明「板端编码线程活着」，证明不了「网络断但板端仍在编码」（此时 f_index 持续但 ffprobe 收不到）。如需覆盖需补周期 ffprobe 复探。

## 10. 开发红线与注意事项

1. **模块红线（不可违反）**：photo/video/rtmp 等模块**只实现一次测试动作 + 参数接口**，循环/重复/持续时间一律由 Scenario + Runner 驱动。模块内不得出现 for 循环重复、不得感知场景类型。
2. **ftp_server 全程只发一次**：由 `start_ftp` 的 `ctx.ftp_server_started` 保证幂等。重发触发固件崩溃循环。
3. **ftp 每次下载前重建连接**：不缓存/复用（服务端 3s 空闲断会话），沿用老规则勿改。
4. **改代码必留痕**：改 ATS 代码必须在 `doc/devBugLog/` 新建 `YYYYMMDD_HHMM_描述.md`（问题→根因→修复→验证→残留→经验），并更新 `doc/devBugLog/README.md` 索引。**注意：doc/ 已被 .gitignore 忽略，改动不进 git，仅本地保留。**
5. **配置三层别放错**：串口/WiFi 网络环境/pc.ip → system.yaml；模块业务参数 → modules/*.yaml；流程/循环/组合 → scenarios/*.yaml。
6. **哨兵与业务完成是两件事**：exec_async 的 expect 必须是真实业务字符串，不能是命令回显。
7. **长等待必须带进度心跳**：>10s 的 sleep 改成分段 sleep + 周期打印（防误判卡住）。
8. **仓库只跟踪 `ATS/` + `tools/`**：logs/reports/doc/handoff/res/.claude 均已 `git rm --cached`，本地保留但不进 git。
