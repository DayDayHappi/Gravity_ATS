## 三、关键改动详解

### 1. FTP 会话三原则（本会话最重要的一组修复）

板子 FTP 有三个非显而易见的固件行为，脚本已按此定型：

1. **`ftp_server` 全程只发一次**（wifi 连接后由 ftp 模块发）。重发会触发固件
   `service go wrong, now wait restarting` 崩溃循环刷屏，干扰日志定位。
2. **冷启动分两阶段**：`Ftp server init success` 只表示初始化完成，到真正
   `service launched success`（listen 21 端口）还有约 **3~4s 延迟**。只等 init
   success 就 connect 会 `Connection refused`。启动用 `exec_async` 等 launched。
3. **会话有约 3s 空闲超时**：闲置即断。因此**不缓存/复用连接**，`ensure_ftp` 每次
   下载前都重建独立连接（新 socket → USER/PASS 重新登录 → cwd 根目录），数据连接走
   主动模式（PORT），ftplib 每次传输自动换新端口（规避 TIME_WAIT）。

> 这三条是排查 FTP 失败的核心——必须结合 serial.log 时序才能发现，代码层面看不出来。

### 2. RTMP 长推流 + ffplay 低延迟

- **推流时长**：`stream_duration: 600`（10 分钟）统一控制推流持续；ffplay 跟随流
  播放，无需单独计时。ffplay 在独立终端窗口启动（`start_new_session`），用户可手动
  关闭窗口，不影响判据（判据仍是 ffprobe 实时探测）。
- **ffplay 低延迟参数**（2026-08-18 定稿）：
  ```
  ffplay -rtmp_live live -rtmp_buffer 0 -fflags nobuffer \
         -flags low_delay -framedrop -sync ext <url>
  ```
  URL 复用脚本运行时 `url`（`rtmp://{pc_ip}/live/cam`），pc_ip 在 setup 动态确定，不写死。
- **关键时序不变**：ffprobe 探测在 `rtmp_video_stop` 之前（探测实时流）。

### 3. 日志可观测性（防误判卡住）

- **runner 层模块计时**：每个模块开始打印 `>>> 模块 [name] 开始执行`，结束（无论
  成败/异常）在 `finally` 里打印 `<<< 模块 [name] 结束，耗时 X.Xs（结果 PASS/FAIL）`，
  覆盖 setup/run/teardown 全过程。
- **rtmp 长推流进度心跳**：600s 静默期每 30s 打印一次 `推流已保持 X/600s ...`。
- **录像模块**：拍摄开始/结束、FTP 开始下载/下载完成，各带耗时。

## 四、已知问题（固件侧，脚本无法根治）

### 1. ⚠️ ImuThread 崩溃导致 ffplay 画面卡住（最重要，需转固件工程师）

- **现象**：推流约 3 分钟后 ffplay 画面卡住。
- **根因**：`ImuThread`（相机电子防抖 EIS 链路）崩溃，连锁导致
  `discontinuous frame` + `interp not finish in sof`，RTMP 发送间隔从 ~70ms 突增到
  1.7s，画面卡死。
- **崩溃证据**（`logs/20260819_031823/serial.log`）：
  ```
  ---- RV_Backtrace Call Frame Start: ----
  Thread: ImuThread backtrace
  [0] ra 0x8825c798  [1] ra 0x8825c622  [2] ra 0x8825c638
  [3] ra 0x3738     [4] ra 0x882595c4  [5] ra 0x88255dd4
  riscv32-unknown-elf-addr2line -e out/jx009-evb-rv-nds-a45/a45_scenario_jx_evb.elf \
    -a -f 8825c798 8825c61e 8825c638 3738 882595c4 88255dd4
  ```
- **触发条件**：连续录制 180s 视频 + 立即 RTMP 推流约 3 分钟后。
- 脚本最终仍 PASS，是因为判据 ffprobe 在推流开始 10s 已探测到流（早于崩溃）。

### 2. RTMP 发送线程启动调度延迟（首帧/首 IDR 高延时）

- **现象**：前一个重负载（180s 录像 + FTP 下载）结束到 RTMP 开始的冷却间隔越短，
  发送线程越容易在启动阶段被残留线程抢占 CPU，前几十帧积压 → ffprobe 首次探测超时。
- **表现**：serial.log 里 `slow send frame` 的 dt 从首帧就 >500ms（正常 ~70ms）。
- 冷却间隔长（如 FTP 下载慢）反而延时低。这是固件线程调度/资源释放问题。

### 3. 遗留：pc_ip 自动探测选错网卡（沿用上份交接）

PC 多网卡时 `_detect_pc_ip` 可能探到 EVB 不可达的 IP。当前测试环境已能自动探测
正确（192.168.1.89），但换机器后仍需确认 `rtmp.pc_ip` 是否写死更稳。

> 两类固件问题 + 本次日志分析的完整记录见 `doc/RTMP推流延时与画面卡住_日志分析.md`。

## 六、给下一位接手者的建议

1. **当前全链路已跑通**，接手后先按第五节命令跑一遍完整测试确认环境，再动代码。
2. **RTMP 画面卡住 = 固件 ImuThread 崩溃**：先 grep serial.log 的 `RV_Backtrace` /
   `ImuThread` / `discontinuous frame`，有则转固件工程师（线索见第四节），别再当脚本 bug 改。
3. **FTP 失败先看 serial.log 时序**：`ftp_server` 到 `service launched success` 的时间差
   （冷启动延迟 3~4s），以及是否重复发了 ftp_server。
4. **改代码必须记录**：改 ATS 代码后在 `doc/devBugLog/` 新建 `YYYYMMDD_HHMM_描述.md`，
   更新 README 索引（规则见 README.md）。
5. **遇到长 IO 操作要加进度日志**：任何 >10s 的 sleep 都改成分段 sleep + 周期打印，避免误判卡住。
