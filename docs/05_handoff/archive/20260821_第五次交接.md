## 二、现在的架构

### 2.1 分层与职责边界

```
                 config
          +-------------------+
          | system.yaml       系统/环境级：串口、WiFi网络环境、pc.ip、runner、report
          | modules/*.yaml    模块能力参数（photo/video/rtmp/...）
          | scenarios/*.yaml  测试策略（normal/stress/aging）
          +-------------------+
                   |
                   v
              ScenarioManager     加载场景 + 编排 prepare→tasks(loop)→cleanup
                   |
                   v
              TestRunner          按 Task 调度 + repeat/loop + 重试 + fail-fast
                   |
                   v
              Module Layer        wifi/emmc/ftp/photo/video/rtmp（只实现一次测试动作）
```

**职责边界**（已写入代码注释）：**Scenario=怎么组合测试，Runner=什么时候执行，Module=怎么测，Config=参数是什么。**

### 2.3 场景示例

```yaml
# stress.yaml —— photo 50 次 + video 3min + rtmp 10min，整轮循环 3 次
scenario:
  name: stress
  prepare: [serial_init, wifi_connect, preclean, ftp_ready]
  loop: {enable: true, count: 3}
  tasks:
    - {module: photo, repeat: 50}
    - {module: video, duration: 180}
    - {module: rtmp,  duration: 600}
  cleanup: [stop_stream, close_serial]
```

## 三、现在具备什么能力

1. **普通测试**：`normal` 场景等价原有 8 模块完整链路，向后兼容。
2. **压测/老化**：`stress`（photo×50 + video 3min + rtmp 10min 循环 3 轮）、`aging`（限时 2h 循环），**无需改任何模块核心逻辑**，加新场景只新增一个 yaml。
3. **repeat / loop / duration 覆盖**：重复次数、整轮循环（count 次数 / duration 时长 / 无限）、持续类参数覆盖（经 `duration_key` 映射：video→video_duration、rtmp→stream_duration）。
4. **场景隔离**：非 normal 场景日志/报告自动隔离到 `logs/<场景>/logs/` 与 `logs/<场景>/report/`。
5. **ftp_server 幂等**：`start_ftp` 保证全程只发一次 `ftp_server`（重发会触发固件崩溃循环），脚本侧始终无状态 client、每次下载前重建连接。
6. **报告场景维度**：`result.json` 增加 `scenario_stats`（每场景 cycle 数 + 每模块 pass/fail/skip/error）。

## 四、遗留问题（按优先级）

### 🔴 P0 — 全部改动未真机验证

本次 4 个提交 + 第四次交接的 4 项改动（TX/RX 时间戳、exec_async 去哨兵、RTMP heartbeat、测试结束询问）**都未跑真机**。验证顺序建议：

```bash
python3 -m ATS.main --scenario normal --no-interactive-wifi   # 先通正常链路
python3 -m ATS.main --scenario stress --no-interactive-wifi   # 再通压测循环
```

### 🔴 P0 — stress/aging 场景的 WiFi 前置缺失（本次会话末尾用户提出，未解决）

**问题**：`wifi_connect` 动作在 `--no-interactive-wifi` 时是「跳过，交给 wifi_join 模块」；但 stress/aging 的 tasks 里**没有 wifi_join 模块**（也没有 wifi_check），导致：

```
--no-interactive-wifi + stress
  wifi_connect 跳过 → ctx.evb_ip 拿不到
  → ftp_ready 的 start_ftp 因无 evb_ip 返回 None（FTP 起不来）
  → photo/video 无 ftp_client → SKIP
  → rtmp 无 evb_ip → FAIL
```

**用户最后一个问题**：「yaml 语法可不可以把 wifi_join 写在 loop 外面？」—— 这正是关键。当前 loop 语义是「循环整个 tasks」，**没有「循环外的一次性前置任务」概念**。下一个接手者要解决这个，两个方向：

- **方向 A（推荐）**：给 prepare 加一个「非交互连接 WiFi」动作（用 system.wifi 默认 SSID/密码连，不弹交互），stress/aging 的 prepare 里用它替代 wifi_connect。
- **方向 B**：给 scenario 增加 `pre_tasks`（循环外任务）结构，`pre_tasks` 执行一次、`tasks` 被 loop 循环。改动更大但更通用。

### 🟡 P1 — loop 语义的通用性局限

当前 `loop` 只能循环「整轮 tasks」。若未来要「A 任务循环 N 次 + B 任务只跑 1 次」这种混合，需要更灵活的编排（如 task 级 loop）。当前 stress 通过 `task.repeat` 实现单任务多次，通过 `scenario.loop` 实现整轮循环，够用但不够灵活。

### 🟡 P2 — 破坏性 CLI 变更

`--modules` / `--skip` 已移除，`--scenario` 成为主入口。旧命令（handoff 前三份、`使用手册.md` 里的）全部失效，需同步更新文档。`test_config.yaml` 已删除。

### 🟢 P3 — 第四次交接遗留

- RTMP 类型2 网络异常未覆盖（heartbeat 只能证明板端编码线程活着，证明不了数据到达 PC，需周期 ffprobe 复探）。

## 六、要注意哪些

1. **模块红线（不可违反）**：photo/video/rtmp 等模块**只实现一次测试动作 + 参数接口**，循环/重复/持续时间一律由 Scenario + Runner 驱动。模块代码里不得出现 for 循环重复、不得感知场景类型。
2. **ftp_server 全程只发一次**：重发触发固件 `service go wrong, now wait restarting` 崩溃循环。现在由 `start_ftp` 的 `ctx.ftp_server_started` 标志保证幂等。
3. **ftp server 3s 空闲断会话但一直 listen**：脚本侧始终无状态 client，`ensure_ftp` 每次下载前重建连接，不缓存复用（沿用老规则，勿改）。
4. **固件已知 bug（脚本无法根治，勿当脚本 bug 改）**：ImuThread 崩溃（→ffplay 画面卡住）、FTP 崩溃循环、RTMP 命令卡死板子、RTMP 发送线程启动调度延迟。排查先 grep serial.log 的 `RV_Backtrace` / `ImuThread` / `discontinuous frame`。
5. **改代码必留痕**：改 ATS 代码必须在 `doc/devBugLog/` 新建 `YYYYMMDD_HHMM_描述.md` 并更新 README 索引（注意：doc/ 现已被 .gitignore 忽略，改动不进 git，仅本地保留）。
6. **配置三层别放错**：串口/WiFi 网络环境/pc.ip → system.yaml；模块业务参数 → modules/*.yaml；流程/循环/组合 → scenarios/*.yaml。WiFi 的 ssid/password 属 system.wifi（网络环境），wifi 模块本身无独立参数。
