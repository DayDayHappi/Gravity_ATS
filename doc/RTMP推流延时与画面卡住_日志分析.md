# RTMP 推流延时与画面卡住 日志分析报告

**日期**: 2026-08-19
**分析对象**: `logs/20260819_023552`、`logs/20260819_014935`、`logs/20260819_031823` 三次测试的 `run.log` 与 `serial.log`
**结论性质**: 固件侧问题定位线索，非脚本 bug

---

## 一、延时对比：023552（低延时） vs 014935（高延时）

### 现象

两次测试流程完全一致（wifi → emmc → ftp → photo → video 180s → rtmp 600s），
但 rtmp 推流的**首帧/首 IDR 到达 PC 端（ffprobe 探测到流）的延时差异巨大**：

| | 023552（低延时）| 014935（高延时）|
|---|---|---|
| ffprobe 探测 | 一次成功 | **第一次超时**（`探测超时(1/5)`），第二次才成功 |
| 首 IDR 到达 | 推流后约 26s（frame 751, dt=69ms）| 推流后约 7s 起 dt 已飙到 498ms，frame 61 IDR dt=2843ms |

### 串口日志对比

**023552（低延时）——发送线程从启动就跟上编码：**
```
Push Start  @ 02:46:51.911
帧 0~315     正常速度发送（未触发 slow send）
首帧 slow   @ 02:47:02.899（frame 316, dt=117ms）
首个 IDR    @ 02:47:17.934（frame 751, dt=69ms）
```

**014935（高延时）——发送线程一启动就落后：**
```
Push Start  @ 01:56:49.546
帧 45        slow send dt=498ms   ← 0.5s 前就开始积压
帧 60        dt=1170ms            ← 落后 1.2s
帧 61        dt=2843ms (IDR)      ← 落后 2.8s 才发出第一个关键帧
帧 85        dt=4766ms            ← 落后近 5s
```

### 差异根因：前一个重负载结束到 RTMP 开始的冷却间隔不同

| | 023552（低延时）| 014935（高延时）|
|---|---|---|
| 录像结束 | 02:39:41 | 01:53:36 |
| FTP 下载耗时 | **429s**（慢）| **193s**（快）|
| 录像结束 → RTMP 间隔 | **430s** | **193s** |

- 023552 的 FTP 下载慢（399MB 传了 7 分钟），意外给了板子**更长的冷却时间**，
  前一录像会话的编码器/内存/线程完全释放，RTMP 启动时 CPU 干净，发送线程立即拿到时间片。
- 014935 的 FTP 下载快，录像结束仅 3 分钟就开始推流，板子 RTOS 的线程调度/内存碎片/
  缓存状态未恢复到冷启动水平，RTMP 发送线程最初几秒抢不到足够 CPU，帧立即积压。

### 结论

延时差异来自**板子 RTMP 发送线程的启动调度延迟**——前一个重负载（180s 录像 + FTP 传输）
结束后，间隔越短，发送线程越容易在启动阶段被残留线程抢占 CPU，导致前几十帧积压。
积压一旦形成，发送端需花更长时间消化队列，表现为首帧/首 IDR 到 PC 端的延迟大幅增加。

## 二、画面卡住分析：031823（ImuThread 崩溃）

### 现象

ffplay 一开始延时很低，但**推流约 3 分钟后画面卡住**。脚本最终仍 PASS
（判据 ffprobe 在推流开始 10s 时已探测到流，早于崩溃）。

### 时间线（推流 03:25:08 开始）

| 时刻 | 推流后 | 事件 |
|------|--------|------|
| 03:26:44~27:48 | 96s~160s | 正常，`slow send` dt 稳定 53~77ms |
| 03:26:58 | 110s | 开始**零星**出现 `discontinuous frame`（相机帧号跳变）|
| 03:27:48.705 | 160s | frame 4771 dt=77ms，**最后一个正常帧** |
| 03:27:50.708 | 162s | frame 4784 **dt=1745ms**，发送线程突然落后 1.7s |
| 03:27:55 | 167s | `interp not finish in sof` **密集爆发**（3A/ISP 插值在帧同步信号前未完成）|
| **03:28:13.058** | **185s** | **`ImuThread` 崩溃，打印 RV_Backtrace** |

### 崩溃证据（serial.log 末尾）

```

Current Thread Name:  ImuThread
[0]Stack interval :[...]  ra 0x000000008825c79c pc 0x000000008825c798
[1]Stack interval :[...]  ra 0x000000008825c622 pc 0x000000008825c61e
[2]Stack interval :[...]  ra 0x000000008825c63c pc 0x000000008825c638
[3]Stack interval :[...]  ra 0x000000000000373c pc 0x0000000000003738

  -a -f 8825c798 8825c61e 8825c638 3738 882595c4 88255dd4
---- RV_Backtrace Call Frame End:----
```

### 根因分析

**IMU 线程（惯性测量单元，用于相机电子防抖 EIS）在推流约 3 分钟后崩溃**，引发连锁反应：

1. IMU 是相机 ISP 链路的一环（录像初始化日志里有 `imu detector sucessed` / `imu init errcode:0`）。
2. ImuThread 崩溃 → 相机帧生成链路过载 → `discontinuous frame`（帧不连续）+
   `interp not finish in sof`（插值在 SOF 前没做完）。
3. 编码器拿不到连续帧 → RTMP 发送线程等不到新帧 → 发送间隔从 77ms 突增到 1745ms。
4. ffplay 端长时间收不到新帧 → **画面卡住**。

### 结论

- 这是**固件 bug，不是脚本问题**。脚本推流流程、ffplay 参数、判据均正常。
- 崩溃日志已给出 `addr2line` 命令，把 6 个地址喂进去即可定位 ImuThread 崩溃的具体函数/行号。

## 三、给固件工程师的线索汇总

**崩溃现场（031823）**
- 崩溃线程：`ImuThread`
- 崩溃地址：`8825c798 8825c61e 8825c638 3738 882595c4 88255dd4`
- 定位命令（固件已打印）：
  ```
  riscv32-unknown-elf-addr2line -e out/jx009-evb-rv-nds-a45/a45_scenario_jx_evb.elf \
    -a -f 8825c798 8825c61e 8825c638 3738 882595c4 88255dd4
  ```
- 触发条件：连续录制 180s 视频 + 立即 RTMP 推流约 3 分钟后

**两类固件稳定性问题的共同特征**
1. 长时间运行后编码/推流退化（IDR 稀疏、发送积压）。
2. 前一个重负载结束后冷却不足，RTMP 启动阶段发送线程调度延迟。

均指向板子 RTOS 在长时间/连续重负载下的线程调度、内存回收、资源释放问题，属固件侧
稳定性缺陷，脚本侧无法根治，仅能通过冷却间隔、超时重试等手段规避。
