## 1. 引言

### 1.1 目的

本文档定义 VX100 EVB 上位机自动化测试脚本的软件需求。该脚本运行于 Ubuntu PC，通过串口与 EVB 板交互，自动执行功能测试、收集结果并生成测试报告。

### 1.2 范围

覆盖 VX100 EVB Software User Manual v1p2 中定义的**运行时软件功能**的自动化测试。不包括工厂烧录工序（Flash 烧写、eFuse 烧写），这些属于产测工具范畴，不在本脚本范围内。

### 1.3 核心原则

1. **配置驱动**：测试用例通过配置文件声明，新增/删减功能无需改代码。
2. **模块化**：每个功能模块独立封装，模块间通过明确接口耦合。
3. **可扩展**：新功能模块按约定接口开发即可接入，不修改框架核心。
4. **量产友好**：支持批量执行、结果汇总、CI/CD 集成。

## 2. 被测系统概述

### 2.1 硬件连接拓扑

```
┌──────────────┐   UART0 (250000bps)    ┌──────────┐
│   测试 PC     │◄──────────────────────►│  VX100   │
│  (Ubuntu)    │   UART2 (烧录用，不测)  │   EVB    │
│              │                        │          │
│  FTP Client  │◄─── Wi-Fi / 局域网 ───►│  FTP     │
│  RTMP Server │◄─── Wi-Fi / 局域网 ───►│  RTMP    │
└──────────────┘                        └──────────┘
```

### 2.2 软件栈

- **EVB 端**：RT-Thread OS，msh shell 通过 UART0 提供命令交互
- **测试 PC 端**：Python 3.x + pyserial，通过串口发送命令、解析响应
- **辅助工具**：FTP 客户端库、RTMP 服务器（nginx-rtmp）

### 2.3 命令响应模式

EVB 通过 msh 串口接收文本命令，执行后输出结果。测试脚本的核心交互模型为：

```
发送命令 → 等待响应 → 解析输出 → 判定通过/失败
```

## 3. 功能模块测试需求分析

### 3.1 模块分类

根据文档内容，将功能模块分为三类：

| 类别 | 说明 | 包含模块 |
|------|------|----------|
| **A 类 — 可自动化** | 纯串口命令交互，可完全自动化 | WiFi 扫描/连接、eMMC 挂载、拍照、录像、FTP 服务启停、RTMP 推流 |
| **B 类 — 需辅助验证** | 串口命令 + 外部协议验证 | FTP 文件传输验证、RTMP 流验证、拍照/录像文件完整性验证 |
| **C 类 — 不纳入自动化** | 产线烧录工序，一次性/破坏性操作 | Flash 烧写、eFuse 烧写 |

> **决策理由**：Flash 烧写和 eFuse 烧写属于产测工具范畴，需要专门的烧录治具和拨码开关操作，且 eFuse 为 OTP 不可逆，不适合纳入常规功能回归测试。这些由单独的产测工具负责。

### 3.2 模块测试需求详情

#### 模块 1：WiFi 扫描 (wifi scan)

| 属性 | 内容 |
|------|------|
| **测试接口** | 串口命令 `wifi scan` |
| **成功判据** | 输出包含 SSID 列表，且能解析出至少一个 AP 的 SSID 和 RSSI 值 |
| **失败判据** | 超时无响应、返回错误信息、扫描结果为空 |
| **超时** | 15 秒 |
| **前置条件** | EVB 已启动，WiFi 天线已连接 |
| **备注** | RSSI 值仅做记录，不强制判定；但 RSSI < -70 时应输出警告 |

#### 模块 2：WiFi 连接 (wifi join)

| 属性 | 内容 |
|------|------|
| **测试接口** | 串口命令 `wifi join <ssid> <password>` |
| **成功判据** | 输出包含 `Got IP address` 及有效 IP 地址 |
| **失败判据** | 超时、输出认证失败、未获取 IP |
| **超时** | 30 秒 |
| **前置条件** | WiFi 扫描功能正常 |
| **配置项** | `wifi_ssid`, `wifi_password`（敏感信息，支持环境变量覆盖） |
| **备注** | 连接成功后应缓存 IP 地址，供后续 FTP/RTMP 测试使用 |

#### 模块 3：eMMC 格式化与挂载

| 属性 | 内容 |
|------|------|
| **测试接口** | `mkfs -t elm sd` → `mount sd /emmc elm` → `cd emmc` |
| **成功判据** | 每条命令无错误输出，挂载后可进入 `/emmc` 目录 |
| **失败判据** | 格式化失败、挂载失败、目录不存在 |
| **超时** | 格式化 60 秒，挂载 10 秒 |
| **前置条件** | EVB 已启动，eMMC 硬件正常 |
| **备注** | 格式化会清空 eMMC 数据，测试前需确认；支持跳过格式化（`--skip-format`），仅执行挂载 |

#### 模块 4：FTP 服务器

| 属性 | 内容 |
|------|------|
| **测试接口** | 串口命令 `ftp_server`，验证侧通过 FTP 协议连接 |
| **成功判据** | 串口输出 `FTP server init success`，且 PC 可通过 FTP 客户端成功连接 |
| **失败判据** | 启动失败、FTP 连接被拒绝、登录认证失败 |
| **超时** | 启动 10 秒，FTP 连接 10 秒 |
| **前置条件** | WiFi 已连接，eMMC 已挂载 |
| **配置项** | `ftp_user`, `ftp_password`（默认 loogg/loogg），`ftp_port`（默认 21） |
| **验证内容** | (1) 连接成功 (2) 可列出 `/emmc` 目录 (3) 可上传/下载文件 |

#### 模块 5：拍照

| 属性 | 内容 |
|------|------|
| **测试接口** | `cam_set photo <mode>` → `dfs_capture_start` |
| **成功判据** | 命令无错误输出，且 `/emmc/pic` 目录下生成了新的 .jpg 文件 |
| **失败判据** | 设置模式失败、拍照命令返回错误、无文件生成 |
| **超时** | 拍照 10 秒 |
| **前置条件** | eMMC 已挂载，FTP 服务已启动（用于验证文件） |
| **测试维度** | 遍历 4 种拍照模式：auto, single, mfnr, hdr（0/1/2/3） |
| **验证内容** | 通过 FTP 列出 `/emmc/pic` 目录，确认文件存在且大小 > 0 |

#### 模块 6：录像

| 属性 | 内容 |
|------|------|
| **测试接口** | `cam_set video 1080p` → `dfs_video_start` → （等待 N 秒）→ `dfs_video_stop` |
| **成功判据** | 开始/停止命令无错误，且 `/emmc/video` 目录下生成了视频文件 |
| **失败判据** | 命令返回错误、无文件生成、文件大小为 0 |
| **超时** | 录像时长 + 10 秒（可配置录像时长，默认 5 秒） |
| **前置条件** | eMMC 已挂载，FTP 服务已启动 |
| **配置项** | `video_duration`（默认 5 秒），`video_resolution`（默认 1080p） |
| **备注** | v1p2 已删除 4K 分辨率，仅测试 1080p |

#### 模块 7：RTMP 推流

| 属性 | 内容 |
|------|------|
| **测试接口** | `rtmp_video_start <url>` → （等待 N 秒）→ `rtmp_video_stop` |
| **成功判据** | 推流命令无错误，且 RTMP 服务器端收到视频流 |
| **失败判据** | 推流启动失败、服务器未收到流、推流过程中断 |
| **超时** | 推流持续时间 + 15 秒 |
| **前置条件** | WiFi 已连接，RTMP 服务器（nginx-rtmp）已在 PC 端启动 |
| **配置项** | `rtmp_url`（默认 `rtmp://<pc_ip>/live/cam1`），`stream_duration`（默认 10 秒） |
| **验证内容** | (1) 推流命令成功返回 (2) nginx-rtmp 统计接口确认有活跃连接 (3) 流断开后确认连接关闭 |

#### 模块 8：文件完整性验证（通过 FTP）

| 属性 | 内容 |
|------|------|
| **测试接口** | FTP 协议（使用 Python ftplib） |
| **成功判据** | 成功下载指定文件，文件大小 > 0，对于图片可进一步验证 JPEG 头 |
| **失败判据** | 下载失败、文件大小为 0、文件损坏 |
| **超时** | 单个文件下载 30 秒 |
| **前置条件** | FTP 服务已启动 |
| **备注** | 此模块为辅助验证模块，可被拍照/录像测试用例调用 |

### 4.2 核心设计模式

#### 4.2.1 命令-响应模式（Command-Response）

所有串口交互抽象为统一的命令-响应模型：

```
Command.send(command_string) → Response(output, elapsed_ms, success)
```

由通信层处理超时、重试、响应解析，上层模块只关心业务逻辑。

#### 4.2.2 模块注册机制

每个功能模块实现统一接口，通过装饰器或配置文件注册到测试框架：

```python
# 概念示意（非代码）
class WiFiModule(TestModule):
    name = "wifi"
    commands = {
        "scan":  {"cmd": "wifi scan",  "timeout": 15, "expect": r"SSID|RSSI"},
        "join":  {"cmd": "wifi join {ssid} {password}", "timeout": 30, "expect": r"Got IP address"},
    }
```

#### 4.2.3 测试用例 = 功能模块 + 验证逻辑

测试用例组合功能模块的 command 和验证侧的 assertion：

```
TestCase("wifi_scan") = WiFiModule.scan() + AssertOutputContains("SSID")
TestCase("wifi_join") = WiFiModule.join(ssid, pwd)  + AssertOutputRegex(r"Got IP address")
```

### 4.3 配置管理

#### 4.3.1 配置文件结构（YAML）

```yaml
# test_config.yaml
serial:
  port: "/dev/ttyUSB0"     # UART0 端口 (Linux 设备路径)
  baudrate: 250000
  timeout: 2.0

wifi:
  ssid: "TestWiFi"
  password: "${WIFI_PASSWORD}"  # 支持环境变量替换

ftp:
  user: "loogg"
  password: "loogg"
  port: 21

rtmp:
  server_url: "rtmp://{pc_ip}/live/cam1"
  nginx_stats_url: "http://{pc_ip}:8080/stats"  # nginx-rtmp 统计接口

camera:
  photo_modes: ["auto", "single", "mfnr", "hdr_0", "hdr_1", "hdr_2", "hdr_3"]
  video_duration: 5       # 录像时长（秒）
  stream_duration: 10     # 推流时长（秒）

test:
  enabled_modules:        # 通过此列表控制执行哪些模块
    - wifi_scan
    - wifi_join
    - emmc_mount
    - ftp_server
    - photo_capture
    - video_record
    - rtmp_stream
  skip_format: false      # 是否跳过 eMMC 格式化
  retry_on_fail: 1        # 失败重试次数
```

#### 4.3.2 敏感信息处理

- WiFi 密码等敏感字段支持 `${ENV_VAR}` 语法，从环境变量读取
- 配置文件中的敏感字段可被命令行参数覆盖

### 4.4 测试执行流程

```
1. 加载配置 → 2. 检查环境 → 3. 建立串口连接 → 4. 执行前置条件
    → 5. 按序执行测试用例 → 6. 收集结果 → 7. 清理/恢复 → 8. 生成报告
```

## 5. 详细需求

### 5.1 通信层需求

| 编号 | 需求描述 |
|------|----------|
| COM-001 | 支持通过配置文件指定串口号和波特率，默认波特率 250000 |
| COM-002 | 命令发送后，等待指定超时时间，收集所有输出 |
| COM-003 | 支持正则表达式匹配响应内容，判定成功/失败 |
| COM-004 | 支持多行响应收集，直到遇到提示符（如 `msh />`）或超时 |
| COM-005 | 所有串口通信记录完整日志（含时间戳），便于问题回溯 |
| COM-006 | 串口异常（断连、超时、乱码）应有明确的错误信息和恢复策略 |

### 5.2 模块层需求

| 编号 | 需求描述 |
|------|----------|
| MOD-001 | 每个功能模块实现为独立类，继承自 `TestModule` 基类 |
| MOD-002 | 模块必须声明：模块名称、依赖项（前置模块）、提供的命令列表 |
| MOD-003 | 模块命令支持参数化（如 `wifi join {ssid} {password}`） |
| MOD-004 | 模块支持 `setup()` / `teardown()` 生命周期方法 |
| MOD-005 | 模块之间通过共享上下文传递数据（如 WiFi 连接后的 IP 地址） |

### 5.3 测试用例需求

| 编号 | 需求描述 |
|------|----------|
| TC-001 | 测试用例通过 YAML 配置声明，无需编码即可新增/禁用 |
| TC-002 | 每个测试用例包含：用例 ID、名称、依赖关系、超时时间、判定条件 |
| TC-003 | 支持用例间的依赖声明（如 `ftp_server` 依赖 `wifi_join` 和 `emmc_mount`） |
| TC-004 | 某个用例失败时，依赖它的后续用例自动跳过（fail-fast 模式，可配置） |
| TC-005 | 支持用例级别的重试（可配置重试次数和间隔） |
| TC-006 | 每条用例独立计时，记录执行耗时 |

### 5.4 测试报告需求

| 编号 | 需求描述 |
|------|----------|
| RPT-001 | 输出文本格式的实时测试进度（控制台） |
| RPT-002 | 生成 JSON 格式的详细测试结果，包含每个用例的输入/输出/耗时/判定 |
| RPT-003 | 生成 HTML 格式的可视化测试报告 |
| RPT-004 | 报告包含：总用例数、通过数、失败数、跳过数、通过率、总耗时 |
| RPT-005 | 失败用例包含：失败原因、期望输出、实际输出、完整串口日志上下文 |
| RPT-006 | 支持 JUnit XML 格式输出，便于 CI/CD 集成（如 Jenkins） |

### 5.5 命令行接口需求

| 编号 | 需求描述 |
|------|----------|
| CLI-001 | `--config <path>` 指定配置文件路径 |
| CLI-002 | `--modules <list>` 指定本次执行的模块（逗号分隔），覆盖配置文件 |
| CLI-003 | `--skip <list>` 跳过指定模块 |
| CLI-004 | `--port <device>` 覆盖串口配置（Linux 设备路径，如 `/dev/ttyUSB0`） |
| CLI-005 | `--wifi-ssid <ssid>` / `--wifi-password <pwd>` 覆盖 WiFi 配置 |
| CLI-006 | `--output-dir <path>` 指定报告输出目录 |
| CLI-007 | `--junit` 额外输出 JUnit XML 格式 |
| CLI-008 | `--verbose` / `-v` 详细日志模式 |
| CLI-009 | `--list-modules` 列出所有可用模块及其描述 |
| CLI-010 | `--dry-run` 仅验证配置和依赖关系，不实际执行 |

## 6. 非功能性需求

### 6.1 性能

| 编号 | 需求描述 |
|------|----------|
| PERF-001 | 串口命令响应延迟 < 200ms（不含命令本身执行时间） |
| PERF-002 | 完整一轮测试套件（不含录像/推流）执行时间 < 3 分钟 |
| PERF-003 | 测试报告生成时间 < 5 秒 |

### 6.2 可靠性

| 编号 | 需求描述 |
|------|----------|
| REL-001 | 串口通信异常时自动重连（最多 3 次），重连成功后从中断点继续 |
| REL-002 | 每个命令支持独立超时配置，防止单点阻塞整个测试流程 |
| REL-003 | 测试结束后执行清理（关闭 FTP 连接、停止推流等），确保 EVB 可恢复初始状态 |

### 6.3 可维护性

| 编号 | 需求描述 |
|------|----------|
| MAI-001 | 代码遵循 PEP 8 规范 |
| MAI-002 | 所有公共接口有 docstring 文档 |
| MAI-003 | 模块与框架解耦，新增模块仅需新增一个文件 + 注册 |
| MAI-004 | 配置文件有 schema 校验，错误配置在启动阶段即被发现 |

### 6.4 兼容性

## 7. 扩展性设计

### 7.1 新增功能模块

当文档新增功能（如新增 `cam_set photo night` 模式）时，只需：

1. 在对应模块的 YAML 声明中新增命令定义
2. 或在配置文件的 `test.enabled_modules` 中添加新用例
3. **无需修改框架代码**

### 7.2 删减功能模块

当文档删除功能（如 v1p2 删除了 4K 录像）时，只需：

1. 从配置文件的 `test.enabled_modules` 中移除对应项
2. **无需修改框架代码**

### 7.3 自定义验证逻辑

对于需要复杂验证的场景（如验证图片内容不是纯黑、视频编码格式正确），框架提供：

- **钩子机制**：在命令执行后注入自定义验证函数
- **插件目录**：`validators/` 目录下放置自定义验证脚本，自动发现和加载

### 7.4 多 EVB 并行测试

架构预留多串口支持，未来可扩展为：

```yaml
serial:
  devices:
    - port: "/dev/ttyUSB0"
      label: "EVB-01"
    - port: "/dev/ttyUSB1"
      label: "EVB-02"
```

测试用例可指定 `target` 参数，选择在特定 EVB 上执行。并行执行时，每个 EVB 的测试上下文隔离。

### 7.5 CI/CD 集成

- JUnit XML 输出可直接接入 Jenkins/GitLab CI
- 命令行退出码：0 = 全部通过，1 = 有失败用例，2 = 环境/配置错误
- 支持通过环境变量注入所有配置项，便于 CI 流水线参数化
