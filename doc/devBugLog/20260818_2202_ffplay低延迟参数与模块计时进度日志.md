# ffplay 改低延迟直播参数 + 各模块计时/关键节点进度日志

**日期**: 2026-08-18
**改动范围**: `modules/rtmp.py`（ffplay 命令参数、推流阶段进度日志）、`core/runner.py`（模块开始/结束计时打印）

---

## 一、问题描述

两项需求：
1. ffplay 播放参数换成低延迟直播参数，拉流 URL 的 IP 用工程运行时确定的 PC IP（不能写死）。
2. 在关键节点加日志 + 各模块开始时计时、结束（不论成败）打印运行时长，避免长流程下误以为脚本卡住。

## 二、改动内容

### 1. ffplay 低延迟直播参数

将 `_launch_ffplay_terminal` 和 `_launch_ffplay_direct` 两处 ffplay 命令统一替换为：

```
ffplay -rtmp_live live -rtmp_buffer 0 -fflags nobuffer \
       -flags low_delay -framedrop -sync ext <url>
```

- 新增 `-rtmp_live live -rtmp_buffer 0`（直播低延迟 + 关缓冲）。
- 去掉原 `-x 480 -y 360`（窗口尺寸，用户新命令不含；ffplay 按源分辨率开窗口）。
- `<url>` 用运行时 `url` 变量（`rtmp://{pc_ip}/live/cam`），`pc_ip` 在 `setup()` 里
  已动态确定（自动检测或配置写死），不写死 IP。

### 2. 模块级计时（runner）

`TestRunner._run_module()` 用 `time.monotonic()` + `try/finally` 包裹整个执行流程：
- 模块开始时打印 `>>> 模块 [name] 开始执行`。
- 结束时（无论成功/失败/setup 异常/执行异常）在 `finally` 里打印
  `<<< 模块 [name] 结束，耗时 X.Xs（结果 PASS/FAIL/SKIP/ERROR）`。
- 覆盖 setup/run(带重试)/teardown 全过程，比模块自身 `elapsed_ms` 更完整。

### 3. 关键节点进度日志

- rtmp 推流命令下发后加 `推流命令已下发，等待 EVB 建连上线...`（原 exec_async 后
  sleep 3s 静默）。
- rtmp 长推流保持阶段（`stream_duration`，默认 600s）从一次 `time.sleep(duration)`
  改为每 30s 打印一次 `推流已保持 X/600s ...` 进度，600s 静默期不再让人误判卡住。

## 三、验证结果

- `ast.parse` 语法检查 `rtmp.py`、`runner.py` 均 OK。
- **待真机验证**：跑 rtmp 用例，确认 ffplay 窗口以低延迟参数出画面、URL IP 为 PC 实际 IP，
  推流期间每 30s 有进度日志，各模块开始/结束都有耗时打印。

## 四、还会再有吗（残留风险）

1. `-sync ext` 依赖流携带外部时间戳，若固件推流时间戳异常，ffplay 可能跳帧/卡帧，
   属 ffplay 播放侧表现，不影响 ffprobe 判据（判据仍是 ffprobe 探测到视频流）。
2. 去掉 `-x 480 -y 360` 后窗口按源分辨率（1296x2304）打开可能偏大，如需要可再补回
   尺寸参数（放在 `-sync ext` 之后、`<url>` 之前即可）。

## 五、经验沉淀

1. **长等待必须带进度心跳**：任何超过约 10s 的 `time.sleep` 都应改成"分段 sleep + 周期
   打印"，否则长时间静默会被误判为卡死。这次 600s 推流是最典型的场景。
2. **计时放编排层而非模块内**：模块自己用 `Timer` 算 `elapsed_ms` 只覆盖 run() 内部，
   不含 setup/teardown，且失败/异常路径可能没算。在 runner 统一用 `time.monotonic()` +
   `try/finally` 计时，天然覆盖所有路径、所有出口，一处实现全局生效。
3. ffplay 命令的 URL 必须复用脚本里已解析好的 `url`（含动态 pc_ip），不要另写一份带
   字面 IP 的命令，避免 IP 变更时漏改。
