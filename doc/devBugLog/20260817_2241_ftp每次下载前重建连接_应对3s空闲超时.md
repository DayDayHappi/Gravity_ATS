# FTP 客户端改为每次下载前重建连接（服务端 3s 空闲超时）

**日期**: 2026-08-17
**改动范围**: `modules/ftp.py`（`ensure_ftp` 不再探测旧连接，直接重建）、`drivers/ftp_client.py`（`connect()` 恢复工作目录 + 关闭旧 socket；`download()` 每次下载前先重建连接）

---

## 一、问题描述

板子端 `ftp_server` 与 PC 端建立控制连接后，服务端有一个约 3s 的空闲超时：3s 内没有操作就会断开会话。旧实现把 FTP 连接当作"长连接"缓存复用——`ensure_ftp(force=False)` 会先探测旧连接（`list_dir`）活着就直接复用，`download()` 也只在 `self._ftp is None` 时才重连。结果拍照/录像中间隔了数秒后再去下载时，旧连接其实已被服务端断开，导致下载失败/卡死。

## 二、根因分析

1. **3s 空闲超时 vs 长连接假设**：固件 FTP 会话空闲即断，脚本却在跨模块（photo/video）之间缓存并复用同一个 `FtpClient` 连接，中间穿插拍照/录像等耗时操作（远大于 3s），复用时刻连接早已失效。
2. **"先探测再重连"是伪优化**：探测（`list_dir`）本身也要一次往返，且大概率发现连接已死，多此一举还引入额外失败路径。
3. **断点续传复用死连接**：`download()` 的续传重试逻辑只在 `_ftp is None` 时重连，若连接处于"半死"（socket 未释放但服务端已断开）状态，`retrbinary` 会直接报错而不重连。

## 三、修复内容

用户明确服务器端一直 listen，只需每次下载前重新 connect。按此改造：

1. **`drivers/ftp_client.py` `connect()`**：
   - 开始前 `_safe_close()` 关闭可能残留的旧 socket，避免同对象复用泄漏。
   - 每次都是全新独立连接：新 `FTP()` -> `connect()`（读欢迎信息，`ftplib.getresp()` 已读净不留缓冲）-> `login()` USER/PASS loogg/loogg -> `set_pasv(False)` 主动模式 -> `cwd("/")` 恢复工作目录到已知基线。

2. **`drivers/ftp_client.py` `download()`**：
   - 入口无条件先 `self.connect()` 建一条全新连接用于本次下载（查大小、发起传输都基于这条新连接），不再假设调用前的旧连接可用。
   - 续传重试仍走 `self.connect()` 重建（全新会话），不复用可能已死的旧连接。

3. **`modules/ftp.py` `ensure_ftp()`**：
   - 删除"先 `list_dir` 探测旧连接，活着就复用"的分支；每次调用都关闭旧客户端、新建 `FtpClient` 并 `connect()`。
   - `force` 参数保留（语义区分"拍照/录像刚结束" vs "开始前基线"），行为统一为"重建连接"。

4. **主动模式数据连接（PORT）**：无需额外代码。`ftplib` 在每次实际传输时通过 `ntransfercmd -> makeport()` 用 `socket.create_server(("", 0))` 起一个全新的临时数据端口并发 `PORT h1,h2,h3,h4,h5,h6`，让服务器主动连回，天然满足"每次传输换新端口、避免旧端口 TIME_WAIT 复用失败"的要求。

5. **`ftp_server` 全局仍只发一次**：确认全仓库唯一发送点仍是 `modules/ftp.py` `FtpModule.run()`。

## 四、验证结果

- `ast.parse` 语法检查 `ftp_client.py`、`ftp.py` 均 OK。
- **待真机验证**：完整跑一遍（含 photo 多模式 + video 录像下载），确认拍照/录像之间的空闲不会导致下载失败，大文件下载能靠重建连接 + 断点续传完整下完。

## 五、还会再有吗（残留风险）

1. 若单个大文件传输过程中出现超过 3s 的数据停滞（编码落盘慢），控制连接仍可能被服务端断开，需靠 `download()` 的续传重试重建连接恢复——已覆盖，但极端慢速流下仍可能反复重试，属固件限制。
2. 主动模式要求 PC 防火墙放行入站高端口（已配置 ufw 放行 1024-65535，见 [[pc-firewall-allows-highports]]），换机器部署时需确认。

## 六、经验沉淀

1. **"短命连接"就不要当长连接缓存**：服务端有空闲超时（如 3s）时，跨步骤缓存连接是错误设计，正确做法是"用前即连、用完即弃"，让服务端一直 listen 承担会话管理。
2. **"先探测再决定"对短命连接是伪优化**：探测的往返成本和发现连接已死的高概率，决定了不如直接重建。见 [[20260817_0628_ftp_server只启动一次去除重复重启噪音]]——那边是"别重发 ftp_server"，这边是"别缓存控制连接"，两者合起来才是完整的 FTP 会话策略。
