# RTMP 推流命令串口溢出丢字节：长命令分片写入修复

**日期**: 2026-08-17
**改动范围**: `core/serial_console.py`（`_write_cmd` 新增 + `exec_sync`/`exec_async` 改用分片写入）

---

## 一、问题描述

真机测试 `rtmp` 模块持续 FAIL（`ffprobe 退出码 1: Input/output error`），但手动在 msh 输 `rtmp_video_start <url>` 后，PC 端 ffplay 能正常拉到画面。手动 OK、脚本 FAIL，且 ffplay 要等约 15s 才有画面。

## 二、根因分析

**不是推流命令不存在、也不是时序问题，是串口发送长命令时字节溢出、命令被截断。**

### 2.1 直接证据（serial.log）

```
TX> rtmp_video_start rtmp://10.1.90.128/live/cam
TX> echo "__EVBTEST_END_ce9fda2b__"
RX< rtmp_vid...[W/U
RX< ART] Warning: There is no enough buffer for saving data, please increase the RT_SERIAL_RB_BUFSZ option.
RX< rtmp_vide__": command not found.          ← 命令被截成 rtmp_vide
```

`RT_SERIAL_RB_BUFSZ` 是 RT-Thread 串口接收环形缓冲，默认约 64 字节。`rtmp_video_start <url>`（45B）+ 换行 + `echo "哨兵"`（33B）共约 **77 字节**，一次性写入时超过缓冲，溢出丢字节 → 板子只收到 `rtmp_vide` → `command not found`。

### 2.2 为什么手动 OK、脚本 FAIL

手动是「发一行、等响应」的节奏，板子有时间搬移缓冲，不溢出。脚本 `exec_async` 把「命令 + 换行 + echo 哨兵 + 换行」**一次性 `ser.write` 写入**，77 字节瞬间灌入。

### 2.3 为什么 rtmp 才中招、其他命令没事

1. **命令长度**：`rtmp_video_start rtmp://<ip>/live/cam` 是本项目最长的命令（45B），叠加哨兵后 77B，是唯一超过 64B 缓冲的命令。`rtmp_video_stop`（14B）、`wifi join`、`ftp_server` 等都短，不溢出。
2. **板子 CPU 忙**：rtmp 在 photo/video 之后执行，此时固件 FTP 正陷入 `service go wrong` 崩溃循环刷屏，板子 CPU 忙于刷屏，来不及把接收字节搬进环形缓冲，溢出概率进一步放大。

### 2.4 复现实验

手动用脚本完全相同的方式一次性写入 77 字节，板子回显复现：`rtmp_vide__": command not found.`；而分开发（先发命令、等 0.5s、再发哨兵）时板子正常推流（`[RTMP] publish ready ... Push Start`）。

## 三、修复内容

`core/serial_console.py`：

1. 新增常量 `_WRITE_CHUNK_BYTES = 32`（每片 ≤32B，远小于 64B 缓冲）、`_WRITE_CHUNK_DELAY = 0.1`（片间延时）。
2. 新增 `_write_cmd(cmd, sentinel)`：把「命令 + 哨兵」按 32 字节分片写入，每片后 `time.sleep(0.1)`，给板子搬移时间。日志仍记录完整命令（与原 `_write` 一致）。
3. `exec_sync` / `exec_async` 的发送从 `_write(full_cmd)` 改为 `_write_cmd(cmd, sentinel)`。

分片后 77B 命令被切成 3 片（32+32+13），每片独立到达、片间 0.1s 喘息，不再溢出。该修复对所有命令生效（短命令只有 1 片 + 1 次 0.1s 延时，影响可忽略），未来更长的命令也天然安全。

## 四、验证结果

- `ast.parse` 语法 OK；`_write_cmd` 三处调用点正确（定义 + exec_sync + exec_async）。
- **待真机验证**（需板子重新上电）：`python3 -m ATS.main --no-interactive-wifi`，rtmp 项应 PASS。

## 五、还会再有吗（残留风险）

1. **缓冲上限仍未从根上解决**：分片是绕过 `RT_SERIAL_RB_BUFSZ` 偏小，未改板子固件的缓冲大小。若未来出现 >100B 的命令，仍可能单片 32B 都嫌大（不，32B < 64B 永远安全）。真正根治需改板子固件 `RT_SERIAL_RB_BUFSZ`，属固件侧，脚本不可控。
2. **FTP 崩溃刷屏未根治**：这是 photo/video 后固件侧问题，脚本只能 `ensure_ftp` 压制 + 分片容忍。若刷屏更猛烈（CPU 更忙），0.1s 延时可能不够，需视真机结果再调 `_WRITE_CHUNK_DELAY`。
3. **延时对整体耗时的影响**：每命令多 1 片约 0.1s，完整测试几十条命令多几秒，可接受。

## 六、经验沉淀

1. **串口长命令要防接收缓冲溢出**：嵌入式串口环形缓冲（RT-Thread `RT_SERIAL_RB_BUFSZ` 默认 64B）远小于 PC 端直觉。往串口写「命令 + 哨兵」这种几十字节的组合时，必须分片 + 片间延时，不能一次性 `write`。命令越长越危险，叠加对端 CPU 忙（刷屏/中断风暴）时更是雪上加霜。
2. **"手动 OK 脚本 FAIL" 优先怀疑发送节奏差异**：手动发命令天然带「发→等→回」节奏，脚本往往是「一口气灌入」。同样的命令、不同的发送方式，结果可能完全不同。遇到这类问题，先比对两者的发送字节序列与时序。
3. **serial.log 里的板子警告是金矿**：`Warning: ... RT_SERIAL_RB_BUFSZ` 这类固件侧告警直接指向根因，比 `command not found` 更靠前、更本质。排查串口问题时先看告警，再看表层报错。
4. **命令长度要做防御性设计**：本项目最长命令是 rtmp 推流地址，未来若 URL 变长（带鉴权参数等）会再次触发。分片写入这类「按固定字节切 + 延时」的模式应作为串口发送层的通用策略，而非临时补丁。见 [[rtmp-ffmpeg-bundled]]（同为串口/依赖链路的防御性处理）。
