# 内置 ffmpeg/ffprobe 到项目，打通 RTMP 验证依赖

**日期**: 2026-08-13
**改动范围**: 新增 `tools/ffmpeg/` 目录（预编译二进制）+ `ATS/config/test_config.yaml` 配置

## 1. 问题描述

RTMP 推流模块（`modules/rtmp.py`）代码早已完成，但一直是 6/7 模块中**唯一未真机验证**的项。

阻塞点：PC 上没有 ffmpeg/ffprobe。该机器网络有网页认证网关，会话过期后 `apt install ffmpeg` 与 `pip install` 都连不上源，无法在线安装。

`rtmp_receiver.py` 的拉流验证强依赖 `ffmpeg`（拉流存盘）和 `ffprobe`（解析流信息），二者缺失则 RTMP 模块无法运行。

## 2. 根因分析

- `check_dependencies()`（main.py）对启用了 rtmp 的配置会调用 `RtmpReceiver.check_tools()`，找不到 ffmpeg 时直接返回退出码 2（环境错），测试根本起不来。
- 机器网络受限，apt/pip 在线安装这条路走不通，必须**离线引入预编译二进制**。

关键认知（避免重复踩坑）：ffmpeg 分发包有三种，**只有第三种能直接用**：

| 包类型 | 文件名特征 | 内容 | 能否直接用 |
|--------|-----------|------|-----------|
| 源码包 | `ffmpeg-x.x.x.tar.xz`、`ffmpeg_x.x.orig.tar.xz` | `Makefile`+`configure`+`.c/.h` | 否，需 `./configure && make` 编译，还要 gcc/nasm/yasm 工具链 |
| deb 包 | `ffmpeg_x.x-x_amd64.deb` | 二进制 | 解压可用，但依赖一堆系统 `.so`（libavcodec 等），缺库跑不起来 |
| **静态构建包** | 文件名含 `static` 或 `-gpl`，体积 ~100MB+ | `bin/ffmpeg`+`bin/ffprobe` 现成可执行 | **能，零系统依赖** |

判别诀窍：`tar -tJf 包名 | grep -E '/(ffmpeg|ffprobe)$'`，能在 `bin/` 下看到现成可执行文件的就是预编译包；只看到 `configure`/`Makefile`/`.c` 的是源码。

本次下载过程先后试了 3 个包才找到对的：
1. `ffmpeg_8.1.orig.tar.xz`（12MB）→ 源码包，放弃
2. `ffmpeg_8.0.1-3ubuntu2_amd64.deb`（299 字节）→ 实为 503 错误页被存成 .deb，下载失败
3. `ffmpeg-master-latest-linux64-gpl.tar.xz`（123MB，BtbN GPL 静态构建）→ 正解

## 3. 修复内容

### 3.1 引入预编译静态 ffmpeg/ffprobe

从 `ffmpeg-master-latest-linux64-gpl.tar.xz`（BtbN 构建，gcc 15.2 编译，版本 N-126086-20260812）解压出 `bin/ffmpeg` 和 `bin/ffprobe`，放到项目内：

```
tools/ffmpeg/ffmpeg      (140MB, 含全部编解码器, --static 静态构建)
tools/ffmpeg/ffprobe     (140MB)
```

只取这两个需要的二进制，不搬整个包。加可执行权限。

选静态构建包的两个关键原因：
- `--pkg-config-flags=--static`：静态链接，不依赖系统任何 `.so`，解压即用，零环境坑
- `--enable-openssl`：RTMP 协议必需（RTMP over TLS / 基础握手都走 openssl）

### 3.2 配置指向内置二进制

`ATS/config/test_config.yaml` 的 `rtmp` 段：

```diff
 rtmp:
   stream_url: "rtmp://{pc_ip}/live/cam1"
   stream_duration: 10
   pc_ip: "auto"            # auto=自动检测，或填具体 IP
-  ffprobe_path: "ffprobe"
-  ffmpeg_path: "ffmpeg"
+  # 使用项目内置的静态构建 ffmpeg/ffprobe (tools/ffmpeg/)，不依赖系统安装
+  # 相对路径基于运行时 cwd（python -m ATS.main 在项目根目录执行）
+  ffprobe_path: "tools/ffmpeg/ffprobe"
+  ffmpeg_path: "tools/ffmpeg/ffmpeg"
```

**不改任何 .py 代码**——`rtmp_receiver.py` 的 `_find_ffmpeg()` 本就支持配置指定路径（优先级最高），只需改配置。这正体现了项目"数据驱动"架构的价值：加测试能力不动 core。

### 3.3 相对路径可行性验证

`_find_ffmpeg()` 内部用 `shutil.which(preferred)` 解析路径。`shutil.which` 对相对路径会基于 cwd 解析并校验可执行权限。因入口固定为 `python3 -m ATS.main`（cwd = 项目根），相对路径 `tools/ffmpeg/ffmpeg` 稳定可解析，已验证：

```
shutil.which('tools/ffmpeg/ffmpeg') = 'tools/ffmpeg/ffmpeg'   ✓
RtmpReceiver.check_tools(...) → 缺失项: 无                      ✓
```

## 4. 验证结果

1. **二进制可执行**：`./tools/ffmpeg/ffmpeg -version` 正常输出，确认静态构建、启用了 openssl/x264/rtmp 所需特性。`ffprobe -version` 正常。
2. **依赖检查通过**：`RtmpReceiver.check_tools()` 返回空缺失列表。
3. **dry-run 全绿**：`python3 -m ATS.main --dry-run` 输出 8 模块（含 rtmp）依赖链正常，不再因 ffmpeg 缺失退出码 2。

RTMP 模块的**离线依赖已就绪**，但**真机推流验证尚未执行**（需接好板子、关防火墙、跑 `python3 -m ATS.main --no-interactive-wifi` 完整流程）。真机结果见后续测试。

## 5. 还会再有吗

- **二进制体积**：两个文件共 280MB，占项目空间较大。如需精简，可只保留 ffmpeg（拉流用），ffprobe 缺失时 `verify()` 会自动降级为 `ffmpeg -i` 解析 stderr——但降级解析的时长/分辨率不如 ffprobe 准，建议保留。
- **架构绑定**：该静态包是 x86_64，仅限 64 位 Linux PC。换 ARM/macOS 环境需重新下对应架构的静态包。
- **路径耦合 cwd**：配置用相对路径，依赖"必须从项目根目录用 `python3 -m ATS.main` 启动"。若有人从别处 `python3 /abs/path/ATS/main.py` 启动，cwd 不在项目根，相对路径会失效。当前使用手册与交接文档都统一从项目根启动，风险可控；如要绝对稳妥可改为绝对路径，但会牺牲可移植性。

## 6. 经验沉淀

- **离线受限网络的依赖引入**：apt/pip 连不上时，静态构建二进制是最优解——一个 tar 包解决，无系统库依赖、无 sudo、可随项目走。
- **包类型鉴别**：下 ffmpeg 前先用 `file` 看类型、用 `tar -tJf` 看内容，别被 `.deb`/`.tar.xz` 扩展名骗了（503 错误页也会被存成 .deb；源码包也叫 .tar.xz）。**体积是快速判据**：源码 ~12MB，预编译 ~100MB+。
- **数据驱动架构的回报**：本次新增测试依赖能力，零代码改动，只动配置，dry-run 即可验证。证明 [[ats-architecture]] 注册+配置解耦设计在维护期的实际价值。
