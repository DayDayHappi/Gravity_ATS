# RTMP 推流真机验证打通：服务端 + 拉流参数 + 时序修复

**日期**: 2026-08-13
**改动范围**: `drivers/rtmp_server.py`(新增) + `drivers/rtmp_receiver.py` + `modules/rtmp.py` + `config/test_config.yaml` + `tools/mediamtx/`(新增)

## 1. 问题描述

RTMP 推流模块真机验证持续失败。首次真机测试:`[FAIL] rtmp - 推流启动命令失败`,8 项 7 过 1 失。排查发现是**三层问题叠加**,逐层剥离才见到真根因。

## 2. 根因分析(三层)

### 第 1 层：exec_sync 被 FTP 崩溃刷屏打乱（表层）

serial.log 证据:
```
04:14:19  [W/ftp] service go wrong, now wait restarting...   ← FTP 崩溃循环开始
...       (持续刷屏 2 分多钟,每 1.5s 一次,直到 rtmp 测试)
04:16:31  TX> rtmp_video_start rtmp://10.1.64.35/live/cam1
04:16:31  TX> echo "__EVBTEST_END_6564b7c6__"                ← exec_sync 哨兵
04:16:33  RX< p] service go wrong, now wait restarting...    ← 响应被淹没
04:16:33  RX< rtmp_vid                                     ← 命令回显被截断
```

rtmp 用 `exec_sync`(哨兵定界),哨兵被 FTP 洪水打乱,误判命令失败。photo/video 同类场景已改 `exec_async`,rtmp 漏改。

### 第 2 层：PC 缺 RTMP 服务端（真根因之一）

修完第 1 层后发现更根本的问题:RTMP 拓扑是「EVB 推流到 PC + PC ffmpeg 拉流」,两端都指向 PC 的 1935 端口,**但 PC 上没有任何 RTMP 服务端接收推流**。EVB 推流连接被拒,流根本进不到 PC。

这是 RTMP 一直没验证通过的**真正阻塞**,与代码无关,是测试环境缺失。环境现状:apt 要 sudo 密码、pypi/github 命令行连不上(HTTP 000),和 ffmpeg 一样只能靠离线包。

### 第 3 层：ffmpeg 拉流参数与版本不兼容（真根因之二）

引入 MediaMTX 服务端后,手工闭环测试发现拉流端 ffmpeg 报 `Option not found` 退出。根因:`rtmp_receiver.py` 硬编码了 `-reconnect`/`-reconnect_streamed`/`-reconnect_delay_max` 三个参数,而内置的 BtbN ffmpeg master 构建的 RTMP 协议实现**不接受这组参数**(版本差异),直接报错退出。

### 第 4 层：拉流先于推流退出（时序）

修完参数后,拉流仍失败--这次是时序:脚本原流程「先起拉流端再发推流命令」,但这个 ffmpeg 版本拉 RTMP 时若对端暂无流,会**立即报 I/O error 退出(约 150ms)**,等不到推流上线。`-rw_timeout` 不解决此问题(它是连接超时,不是连接成功后的无流)。

## 3. 修复内容

### 3.1 引入 MediaMTX 服务端（解决第 2 层）

用预编译静态二进制 MediaMTX v1.20.0(`mediamtx_v1.20.0_linux_amd64.tar.gz`,26MB,Go 编译单文件,零依赖)做 RTMP 中转:

```
tools/mediamtx/mediamtx           (53MB 二进制)
tools/mediamtx/mediamtx_min.yml   (最小化配置:只开 RTMP,关闭其他协议)
```

**为何用最小化配置**:MediaMTX 默认配置同时开 RTSP/HLS/WebRTC/SRT/MoQ,多协议冲突导致推流端 Broken pipe、拉流端 I/O error。只开 RTMP 后稳定。手工验证:`is publishing to path 'live/cam1'` 推流成功。

**为何 MediaMTX 而非 nginx-rtmp**:nginx-rtmp-module 是源码模块要编译(需 gcc + pcre/zlib/openssl-dev,环境不具备);MediaMTX 是单二进制解压即用,与 ffmpeg 同属"离线静态包"路线,完美适配受限网络环境。

### 3.2 新增 `drivers/rtmp_server.py`

封装 MediaMTX 的启停:`start()` 起进程并轮询 1935 端口就绪,`stop()` 终止。`available` 属性检查二进制与配置就位。

### 3.3 修复 ffmpeg 拉流参数（解决第 3 层）

`drivers/rtmp_receiver.py` 的 `start()` 命令:

```diff
- # -reconnect*: EVB 推流可能晚于 ffmpeg 启动，连接被拒时自动重连
- cmd = [self.ffmpeg_path,
-        "-reconnect", "1",
-        "-reconnect_streamed", "1",
-        "-reconnect_delay_max", "2",
-        "-y", "-i", url, "-t", str(duration), "-c", "copy", "-f", "flv",
-        self._outfile]
+ # 不用 -reconnect*：当前内置 ffmpeg（BtbN master）的 RTMP 协议不接受这组参数，
+ # 报 "Option not found" 直接退出。拉流晚于推流的时序由调用方保证+重试兜底。
+ # -rw_timeout：给 RTMP 读一个超时，避免推流异常时 ffmpeg 永久挂起。
+ cmd = [self.ffmpeg_path,
+        "-rw_timeout", str(int(duration * 1000000) + 5000000),
+        "-y", "-i", url, "-t", str(duration), "-c", "copy", "-f", "flv",
+        self._outfile]
```

新增 `is_running` 属性:判断 ffmpeg 进程是否仍在跑(拉到无流源会立即退出),供调用方重试判断。

### 3.4 重构 rtmp 模块流程（解决第 1、4 层）

`modules/rtmp.py` 的 `run()`:

- **exec_async 替 exec_sync**:推流/停推流命令改 `exec_async`,不依赖被刷屏打乱的哨兵。expect 宽松正则仅用于尽快返回,不作为成败判据。真正判据是 PC 端 ffprobe 验到流(侧信道,符合设计文档原意)。
- **前置压制 FTP**:run 开头 `ensure_ftp(force=True)` 重发 ftp_server 压制崩溃循环,给干净串口环境。压不住也无妨,exec_async 不依赖哨兵,双保险。
- **先推后拉时序**:改为先发 `rtmp_video_start`、等 3s 上线、再起拉流端(解决拉流先于推流退出)。
- **拉流重试兜底**:拉流端连不上(推流上线晚)时重试 4 次。
- **起 MediaMTX 服务端**:setup 创建 RtmpServer,run 开头 start,teardown stop。

### 3.5 配置

`test_config.yaml` 的 `rtmp` 段加 `mediamtx_path`/`mediamtx_config`(留空=自动取 `tools/mediamtx/`)。

## 5. 还会再有吗

- **EVB 推流命令名可能不符**:文档都写 `rtmp_video_start`,但实测与手册多处不符。若真机仍 FAIL 且 serial.log 显示 unknown command,需查板子实际命令名(msh 输 `rtmp` 按 tab 补全,或 help)。
- **EVB 推流编码格式**:MediaMTX 接收 H264 已验证。若 EVB 推的是 H265/其他,MediaMTX 默认 RTMP 容器(FLV)可能不支持,需确认 EVB 推流编码。这是真机才知道的未知点。
- **MediaMTX 占端口**:1935/8554 等。若与别的服务冲突需改 `mediamtx_min.yml`。
- **防火墙**:RTMP 是 EVB 主动连 PC:1935,需关防火墙(与 FTP 主动模式同理)。

## 6. 经验沉淀

- **根因分层剥离**:RTMP 失败看似一个"推流启动命令失败",实际是 4 层问题叠加(刷屏/缺服务端/参数不兼容/时序)。逐层修+每层独立验证(手工闭环测试)才能见到真根因。表层修复(改 exec_async)掩盖不了缺服务端这个真阻塞。
- **离线环境的依赖引入**:受限网络下,RTMP 服务端和 ffmpeg 一样走预编译静态包(MediaMTX/Go 二进制),比 nginx-rtmp 编译路线省一个数量级工作量。判别:体积(源码~12MB vs 预编译~26MB+)+ 无 configure/Makefile。
- **ffmpeg 参数与版本强绑定**:`-reconnect` 系列参数不是所有 ffmpeg 版本/协议都支持,不同构建(BtbN master vs apt stable)行为差异大。写跨版本命令时对关键参数要做实际版本验证,别假设通用。见 [[rtmp-ffmpeg-bundled]]。
- **时序耦合**:拉流端"无流即退出"的特性要求"先推后拉",且拉流要带重试兜底上线时间不准。这是 RTMP 推拉模型的固有陷阱,文档化避免重踩。
