## 三、遇到的问题与解决（RTMP 四层根因）

RTMP 一直没验证通过，是**四层问题叠加**，逐层排查才打通：

### 第 1 层：exec_sync 被 FTP 崩溃刷屏打乱（表层）
- 现象：`[FAIL] rtmp - 推流启动命令失败`
- 根因：photo/video 后固件 FTP 陷入 `service go wrong` 崩溃循环（每1.5s刷屏），打乱 exec_sync 的哨兵定界
- 解决：rtmp 命令改 `exec_async`（不依赖哨兵）+ 前置 `ensure_ftp(force=True)` 压制刷屏

### 第 2 层：PC 缺 RTMP 服务端（真根因之一）
- 现象：EVB 推流到 `rtmp://pc_ip` 但 PC 没服务端接收
- 根因：RTMP 拓扑需 PC 起 RTMP 服务端中转（EVB publish + ffmpeg play 都指向 PC:1935），环境缺服务端
- 排查网络：apt 要 sudo 密码、pypi/github 命令行连不上（HTTP 000），只能离线包
- 解决：引入 MediaMTX 单二进制（解压即用，比 nginx-rtmp 编译路线省一个数量级工作量）

### 第 3 层：ffmpeg 拉流参数与版本不兼容（真根因之二）
- 现象：ffmpeg 拉流报 `Option not found` 退出
- 根因：内置 ffmpeg（BtbN master 构建）的 RTMP 协议不接受 `-reconnect*` 系列参数
- 解决：`rtmp_receiver.py` 去掉 `-reconnect*`，改用 `-rw_timeout` 防挂起

### 第 4 层：拉流先于推流退出（时序）
- 现象：拉流文件未生成
- 根因：拉流 ffmpeg 连无流源会立即退出(~150ms)，等不到推流上线
- 解决：改「先推后拉」时序（先发 rtmp_video_start 等3s 再起拉流）+ 拉流重试兜底

## 四、已知问题与遗留事项

### 1. ⚠️ 脚本自动跑 RTMP 可能因 `pc_ip` 探测选错网卡（主要遗留）
- 现象：手动用 `rtmp://10.1.90.128/live/cam`（EVB 同网段 IP）成功；脚本 `auto` 探测到 `10.1.64.35` 可能 EVB 连不上
- PC 有多个 IP（`10.1.64.35` 有线 + `10.1.90.128` WiFi 等），`_detect_pc_ip` 可能探到 EVB 不可达的那个
- **解法**：跑测试前确认 EVB 能 ping 通 PC 哪个 IP，把 `test_config.yaml` 的 `rtmp.pc_ip` 写死成那个 IP
- 待办：需在新机器上确认 IP 全貌后定 `pc_ip`

### 2. RTMP 推流命令会卡死板子（固件 bug，手动验证时偶发）
- 现象：EVB 未联网或某些状态下发 `rtmp_video_start`，板子 msh 完全卡死（串口零响应）
- 这是固件 bug，非脚本问题。规避：确保 WiFi 已连 + 摄像头就绪后再发推流命令；卡死需物理重启板子
- 脚本侧已加前置压制 FTP + exec_async，但固件卡死无法脚本规避

### 3. 固件 FTP 不稳定（沿用上份交接，未变）
- 拍照录像后 FTP 常崩溃循环 `service go wrong`，ensure_ftp + 断点续传已处理大部分，极不稳定时重启板子

### 4. ffplay 直连抗乱序帧（待真机验证）
- MediaMTX 时代曾因 `too many reordered frames` 断 ffplay 直连；改 nginx-rtmp 后是否复现待真机验证
- 绕开：判据用 ffprobe 实时探测（不依赖 ffplay），ffplay 仅可选画面确认（无 DISPLAY 自动跳过）；nginx-rtmp 不提供 RTSP，原 RTSP over TCP 选项失效

## 六、环境要求（新机器参考）

- **OS**: Linux x86_64（Windows 不支持串口终端模式 termios/tty）
- **Python**: 3.7+，依赖 `pyserial` `pyyaml`（仅 2 个第三方包）
- **内置工具**: ffmpeg/ffprobe/ffplay 全在 `tools/` 下，无需系统安装；RTMP 服务端用系统 nginx-rtmp（`sudo apt install nginx libnginx-mod-rtmp`，脚本仅检查就绪不启停）
- **串口权限**: 用户在 dialout 组，或临时 `chmod 666 /dev/ttyUSB*`
- **防火墙**: 放行 1024-65535 高端口（RTMP 1935 + FTP 数据端口）
- **网络**: EVB 能路由到 PC 的 IP（多网卡时注意 pc_ip 选对）

> 详见 `迁移指南.md`，一键检查用 `./migrate.sh`。

## 七、给下一位接手者的建议

1. **先跑 `./migrate.sh`**：新机器上一键确认环境，按提示执行 sudo 命令。
2. **RTMP 是唯一需要人工介入的模块**：手动验证已成功，脚本自动跑受 `pc_ip` 探测影响。接手后第一步是确认 PC 各 IP、把 `rtmp.pc_ip` 写死成 EVB 可达的那个，再跑脚本验证。
3. **遇到问题先查 devBugLog**：本次会话的 4 个 RTMP 根因、固件坑、环境适配都有记录。
4. **改代码必须记录**：改 ATS 代码后在 `doc/devBugLog/` 新建 `YYYYMMDD_HHMM_描述.md`，更新 README 索引（规则见 README.md）。
5. **RTMP 调试用 `--terminal`**：手动发命令实时看板子返回，比脚本盲测高效，尤其能看清卡死前有没有输出。
6. **固件 RTMP 命令会卡死板子**：发 `rtmp_video_start` 前确保 WiFi 已连，卡死需物理重启板子。
7. **离线环境引入依赖走静态包**：受限网络下，ffmpeg/MediaMTX 都用预编译二进制，不用编译/不依赖系统库。判别诀窍：源码包~12MB含configure，预编译~100MB+在bin/下有现成二进制。

## 九、2026-08-14 更新：MediaMTX → nginx-rtmp

本次会话之后又做了一次 RTMP 服务端替换，接手者请注意以下**最新状态**覆盖上文对应描述：

- **删除** `tools/mediamtx/` 整个目录（MediaMTX 二进制不再内置）。
- **RTMP 服务端改用系统 nginx-rtmp**：用户已在本地装好（`libnginx-mod-rtmp`，`/etc/nginx/rtmp.conf` 配 `application live { live on; record off; }` 监听 1935）并手动验证通过。脚本**不 subprocess 启停 nginx**，`rtmp_server.py` 改为「仅检查 1935 就绪」，未就绪提示 `systemctl start nginx`。
- **验证方式改为 ffprobe 实时探测**：`rtmp_receiver.py` 去掉 ffmpeg 存盘逻辑，改用 ffprobe 实时探测 `rtmp://<pc_ip>/live/cam`（探到 h264 + 分辨率即 PASS），ffprobe 升为必需依赖。可选 ffplay 画面确认（无 DISPLAY 自动跳过）。
- **★ 关键时序**：ffprobe 探测必须在 `rtmp_video_stop` **之前**（探测实时流，stop 后必失败），与上文"先 stop 再 verify 存盘"相反。
- **cam1 → cam 统一**：推流地址统一为 `rtmp://<pc_ip>/live/cam`。
- **migrate.sh 第3步**：去掉 mediamtx 检查，新增 nginx-rtmp 就绪检查（`nginx -t` syntax ok + `ss -tln :1935`）。
- 详见 `doc/devBugLog/20260814_*_MediaMTX换nginx-rtmp.md`。

上文第三节"RTMP 四层根因"中第 2 层"PC 缺 RTMP 服务端 → 引入 MediaMTX"的历史叙述保留作背景，但**当前方案已改为 nginx-rtmp**。
